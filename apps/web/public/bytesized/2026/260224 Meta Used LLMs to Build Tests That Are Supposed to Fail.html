Meta Used LLMs to Build Tests That Are Supposed to Fail

The tests that were built to fail

TLDR

Most test generation tries to make tests pass. Meta built a system where the whole point is to make them fail, on the code change you’re about to land, before it lands. Try it Now!

There’s a mental model most engineers carry about automated tests: you write them, they pass, they stay green, they protect you from future regressions. That’s the game. Coverage goes up, confidence goes up, you sleep better.

Meta just published a paper out of FSE 2026 that inverts this completely.

Their system generates tests that are designed to fail. Not because they’re broken. Because the code change you just submitted is the bug.

They call it Just-in-Time catching. The idea: at diff submission time, automatically generate a test that passes on the parent revision but fails on your change. If it fails, either the test is wrong (false positive), or you introduced a regression. Figure out which one. If it’s the latter, fix it before it reaches production.

The framing sounds simple. The execution is not.

Why Your Tests Can’t Do This

Standard test generation, the kind that’s been shipping at Meta and Google and everywhere else for years, targets the implicit oracle. Crashes, exceptions, null pointer dereferences. The tests capture existing behavior and yell when it changes.

That works fine for hardening. You generate a test, it passes, it lives in the repo, it fails if someone later breaks the thing it covers.

Catching is different. You don’t have the luxury of the implicit oracle. You need the general oracle, what should this code actually do, according to its intent, not just what does it currently do. That’s an inherently harder problem. It’s the Oracle Problem in software testing, which researchers have been wrestling with for 40 years.

Before LLMs, everyone would have told you this was unsolvable at scale. You can’t infer intent from code alone.

Turns out you can get pretty far with it.

The Baseline Is Worse Than You Think

Before building purpose-built catch workflows, the team measured how often existing hardening workflows accidentally produce catching tests as a byproduct.

The answer: 0.2% of the time.

That’s the coincidental catch rate. Generate a test meant to harden the parent revision. Occasionally, by sheer luck, that test also fails on a child revision with a regression. 0.2%.

Even TestGen-LLM, Meta’s production coverage-guided LLM test generation system, only generates weak catches (tests that fail on the diff, pass on the parent) about 0.9% to 2% of the time when applied to the parent. That’s the baseline you’re fighting against.

The point: if you want catching tests, you have to build for catching tests. Hardening workflows don’t accidentally do this well.

Diff-Awareness Is the Whole Game

The two purpose-built workflows both share one property: they know about the diff. This sounds obvious, but it’s the load-bearing distinction.

The first approach, “Dodgy Diff,” treats the incoming change as if it were already a mutant, a potentially buggy version of the parent. It runs a mutation-guided LLM test generator against the diff version of the class, trying to produce tests that distinguish its behavior from the parent’s. No judgment on intent. Just: assume this change might be wrong, generate tests that would expose that.

Result: weak catches for 4% of diffs. 2.5% catch rate per test generated. Both roughly double the hardening baselines.

The second approach, “Intent-Aware,” goes further. It first asks the LLM to infer what the diff was trying to do, then infers what could go wrong during that attempt, then constructs mutants representing those specific risks, then generates tests to kill those mutants on the parent. The tests that also fail on the actual diff are harvested as catching candidates.

Result: weak catches for 7.9% of diffs. 6.4% catch rate per test generated.

Almost double Dodgy Diff, with fewer total tests generated. The intent-aware workflow generates more targeted tests and lands them at higher rates. Quality over volume.

What “Weak Catch” Actually Means

This distinction matters and the paper is careful about it.

A weak catch is a test that fails on the diff and passes on the parent. That’s it. It doesn’t mean the diff has a bug. It means the behavior changed. Could be intentional. Could be a regression.

A strong catch is a weak catch where the behavior change is a genuine bug, a true positive according to what the code was actually supposed to do.

Getting from weak to strong is the hard part. Every weak catch that isn’t a strong catch is a false positive that lands in an engineer’s queue and wastes their time. At scale, false positives are existential. A system with a 5% true positive rate will get turned off. Nobody will tolerate the noise.

Meta’s answer to this is a combination of three assessors.

Three Assessors, One Problem

RubFake (Rule-Based False-positive Killing Environment) is deterministic. It searches for specific patterns in the test code, the execution trace, and the diff. Patterns like: the test runner itself crashed (infrastructure issue, not a bug), the test is asserting on private methods (LLM overreach), the test uses reflection (inherently brittle), the mock is broken (LLM generated it wrong). These patterns correlate strongly with false positives. When they’re present, discard the candidate.

TP Prob uses Llama-3.3-70B with token probability scoring. Binary classification: is this test failure unexpected given the diff? The normalized log-probability of the “yes” token gives a confidence score from -1 to 1. High confidence of “no” means false positive. High confidence of “yes” means worth looking at.

Bucket Med is an ensemble across Llama, Gemini, and Claude Sonnet — each model classifying into High/Medium/Low likelihood of a true positive. Median across the ensemble. Consensus judgment.

The three assessors don’t strongly agree with each other. Spearman correlation between the two LLM-based measures is about 0.26. Between either LLM measure and the rule-based approach, it’s barely measurable.

That low correlation is actually the point. They’re not measuring the same thing. RubFake catches specific structural false positive patterns with certainty. The LLMs catch semantic misalignment that no rule can express. Together, they cover different parts of the false positive space. Run all three, use them in concert. Don’t expect consensus — expect complementarity.

Combined, the assessor pipeline reduces human review load by 70%. What would have required a team of four reviewers now requires one.

Production Results

From mid-September through end of October, 41 engineers were reached out to with a simple question: “This behavior changed in your diff, was that intentional?”

8 confirmed bugs. 19.5% true positive rate, as experienced by the engineers who received the signal.

Of those 8, 4 would have caused serious production failures had they landed.

Let that sit for a second. From 41 reach-outs — less than two per working day — 4 critical failures were intercepted before production.

The reach-out mechanism is deliberately simple. The engineer isn’t shown a test case and asked to debug. They’re told: “this expression used to evaluate to true, it now evaluates to false — intended?” Most of the time, the answer takes seconds. False positives are dismissed in a few minutes. True positives are recognized immediately because the engineer literally just wrote the code.

This is the right interface. Show the behavior change, not the test. Ask about intent, not test failure. The goal isn’t to make engineers read generated test code, it’s to prompt them to think about whether their change did what they meant.

The Uncomfortable Implication

Here’s what this paper is really saying, even if it doesn’t say it directly:

Your PR review process is not catching a meaningful fraction of the serious bugs you’re shipping.

Meta has 3.5 billion users. They have world-class code review. They have existing automated test generation at massive scale. And from 41 targeted reach-outs on high-risk diffs, they still found 4 failures that would have been severe.

Code review is good. Hardening tests are good. They’re not sufficient.

The bugs that slip through aren’t the ones anyone was looking for. They’re the boolean that flipped the wrong direction. The container that’s unexpectedly empty. The RBAC check that now evaluates differently for a role nobody thought to test. Things that look correct, that pass all existing tests, that reviewers don’t catch because nobody was specifically hunting for them.

Just-in-Time catching hunts for them specifically, at exactly the moment when the engineer has maximum context on the change.

What the Numbers Don’t Tell You

A 19.5% true positive rate sounds low. In any other context, you’d reject a system that’s wrong 80% of the time.

But measure it differently: out of 41 interruptions, 4 prevented production disasters. The false positives took a few minutes each to dismiss. The true positives saved potentially hours or days of incident response, data corruption cleanup, or worse.

The math works because the cost of false positives is engineered to be low, not because the precision is high.

That’s a deliberate design choice, and it’s the one that makes this system viable at all. Most false positive reduction efforts focus on making the system more precise. Meta focused on making false positives cheap to dismiss. Same outcome, engineers tolerate the signal, achieved from a completely different direction.

Where This Goes Next

The paper is upfront about what’s still weak. The coincidental catch workflow was discontinued in November 2025, the baseline was too low to justify. The intent-aware workflow is better than dodgy diff on a per-diff basis, but the gap isn’t enormous, and neither covers more than 8% of diffs with a weak catch.

Richer context will help. The current intent inference uses only the diff code, title, and summary. There’s discussion threads, task descriptions, related diffs, historical patterns. None of that is in yet.

The assessors have some discriminating power but aren’t close to optimal. The correlation between them is low enough to suggest there’s a lot of room for improvement in the combined signal.

And coincidental hardening is a useful side effect that hasn’t been fully exploited yet. When the catch workflows run, they generate thousands of passing tests as a byproduct — tests that never fail on the diff and can be harvested as hardening tests. 7,987 passing tests in a single month, generated as a byproduct of catch attempts. That’s not nothing.

The Pattern to Take With You

This isn’t really about catching tests. It’s about when you look for bugs.

Most tooling looks for bugs after they’ve been written and landed. Static analysis, code review, hardening tests — all of them operate on existing code. Catching tests operate at submission time, before the code lands, while the author still has full context.

The shift in timing changes everything. The diff author knows more about what the code was supposed to do than anyone ever will. They know it right now. Ask them now.

The harder version of this insight: the earlier in the development cycle you find a bug, the cheaper it is to fix. That’s not a new idea. What’s new is that LLMs have made it possible to generate semantically meaningful catching tests at diff submission time, at scale, cheaply enough to justify the false positive overhead.

The Oracle Problem isn’t solved. But it’s no longer an excuse to not try.
