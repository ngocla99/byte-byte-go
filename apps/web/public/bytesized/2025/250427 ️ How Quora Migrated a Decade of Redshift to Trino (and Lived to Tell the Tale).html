🚨 TL;DR

Over a decade, Redshift became tightly woven into Quora’s data systems, powering dashboards, A/B testing, and ad-hoc analytics. But as scale grew, so did pain: spiraling storage costs, constant firefighting, and architectural complexity.

In 2022, they committed to migrating everything to Trino. The journey involved auto-converting thousands of SQL queries, shadow-validating results at scale, optimizing joins manually, and ultimately cutting 50% of their costs.

This edition breaks down why Quora abandoned Redshift, how they pulled off the migration, and what you should watch out for when modernizing critical systems.

🧱 Why Redshift Worked (At First)

When Quora started scaling, Redshift seemed perfect:

  • 🔥 Fast small queries: Ad-hoc analysis without heavy tuning

  • ⚡ Simple setup: Managed service, SQL native

  • 📈 Powerful for OLAP: Dashboards, product metrics, A/B tests

  • ✏️ Relational features: Easy updates/deletes compared to S3/Hive

But these early wins hid ticking time bombs.

💣 What Went Wrong

1. Complexity Explosion
Managing Redshift and Spark and S3/HDFS meant:

  • Constant data duplication

  • Different teams using different SQL dialects

  • Schema changes triggering cascading failures

  • Tooling and monitoring fragmentation

2. Storage Death Spiral
Using Redshift DS instances (compute + storage bundled) created an ugly trap:

  • Storage shortages despite unused compute

  • Only way to add storage? Buy more nodes (and waste money)

  • Constant "VACUUM" jobs needed to free space

  • Split-table strategies needed for long-term retention

3. Cost Overruns
Scaling Redshift required constant node additions, emergency provisioning, and manual maintenance—all of which drained engineering time and budget.

🚀 Why Trino?

Quora needed a query engine that could:

  • Read data straight from S3 Hive tables

  • Handle analytical SQL workloads

  • Be open-source, extensible, and self-hosted

  • Integrate smoothly into their Spark/S3 stack

Trino fit the bill. It was already in limited use—and it was fast, flexible, and free from storage lock-in.

🛠️ How They Migrated (Without Losing Their Minds)

🔍 Step 1: Full Query Observability

Custom Redshift query logging captured:

  • Full SQL text

  • Table dependencies

  • Query runtime

  • Call location (Python module + function)

No "unknown unknowns" left behind.

📋 Step 2: Double-Write All Tables

Every Redshift table was mirrored to a Hive equivalent via automated copy jobs.
This guaranteed no missing data during the migration—and decoupled data prep from query rewriting.

⚙️ Step 3: Automate SQL Conversion (Twice)

  • First attempt: Regex-based rewrites (DATEDIFF → DATE_DIFF, etc.)

  • Reality: Regex melted on complex queries (nested casts, lateral aliases).

Pivot: Adopted SQLGlot, an open-source SQL syntax tree converter:

  • Parsed full query trees

  • Handled deep rewrites safely

  • Added custom rules for quirks like Trino’s stricter type enforcement

🧪 Step 4: Shadow Pipelines for Validation

  • Every migrated query ran side-by-side with the original Redshift version.

  • Results were auto-compared, tolerating minor float rounding drift.

  • Alerts for any non-trivial data mismatches, triggering manual investigation.

⚡ What Surprised Them

1. Query Performance Cliff
Some migrated queries ran 10x slower in Trino—because of bad join planning.

Root Cause: No table statistics = bad cost-based optimization.

Fix:

  • Run ANALYZE on big tables to generate Trino stats

  • Rewrite JOIN orders manually where needed

  • Bucket Hive tables and define sorted_by indexes for faster access

2. Updates and Deletes Got Harder
Redshift = easy in-place table updates.
Trino on S3 = full partition rewrites required.
Result? Longer write times and higher downtime risk.

3. Autoscaling Was Mandatory
To hit their SLA for daily A/B tests, Quora had to triple Trino cluster size—temporarily.
They built Airflow triggers to pre-scale clusters before peak jobs, then shrink afterward.
Saving costs without missing deadlines.

🧠 What Quora Learned (And So Should You)

  • Multiple storage systems will kill your agility. Consolidate early.

  • Storage/computation coupling (like Redshift DS nodes) is a silent budget killer.

  • Regex will always fail at serious query rewriting. Use syntax trees.

  • Auto-validation at scale saves you from silent data corruption.

  • Table stats are life or death for modern query optimizers.

  • Assume in-place updates may not exist in your future system. Design accordingly.

🧠 How to Plan Migrations Without Meltdowns

Most migrations fail because the transition wasn't survivable.
Here’s how to design a migration process that doesn’t blow up your team or your customers.

1. Start with Observability, Not Code

Before you rewrite a single line:
✅ Build full telemetry into the old system.
✅ Track every query, table, workload, and dependency.
✅ Measure system behavior, not just assumptions.

At Quora, they didn’t migrate blind.
They logged every Redshift query’s origin, structure, and resource usage.
That’s how they found "invisible" dependencies — critical tables touched by ad-hoc scripts or old Airflow jobs no one remembered.

🔍 Rule: If you can’t see it, you can’t migrate it safely.

2. Double-Write > Big Bang

Many teams are tempted by a "big bang" cutover. It’s almost always a mistake.
Instead:

  • Double-write data into both systems early.

  • Shadow-run queries on the new system behind the scenes.

  • Compare outputs without affecting production users.

Double-writing costs extra storage and pipeline complexity upfront.
But it makes cutover boring instead of catastrophic.

🔥 Best practice: Your migration should feel boring and anticlimactic to users. If it’s exciting, you planned it wrong.

3. Validate Outputs, Not Just Inputs

It’s not enough to say "the query ran."
You need to prove:

  • The results match within an acceptable tolerance.

  • Performance is within target SLA windows.

  • Downstream consumers are still happy (dashboards, alerts, ML pipelines).

At Quora, they built shadow Airflow DAGs that:

  • Ran both old Redshift and new Trino versions.

  • Compared outputs row-by-row with float-tolerant checks.

  • Alerted engineers only when real issues appeared.

This caught migration bugs before users ever noticed.

🧠 How to Rebuild Joins, Buckets, and Indexes for Speed

Once you migrate, you’ll realize something uncomfortable:


💬 Query plans don’t survive platform changes.


Your old performance tricks may now be your new bottlenecks.

1. Cost-Based Optimizers Need Stats

Trino’s query planner relies heavily on table statistics.
Without them, it guesses wrong — leading to:

  • Distributed joins that explode memory usage.

  • Scan-heavy plans that take 10x longer.

  • Queries that work fine on Redshift but crash on Trino.

✅ Before you migrate serious workloads:

  • Run ANALYZE on all large Hive tables.

  • Generate row counts, min/max values, distinct counts.

Without stats, Trino assumes the left side of the JOIN is smaller — and that assumption will hurt you.

2. Reorder Joins Intelligently

In systems like Trino (and Presto, and others),
👉 Small table should build the hash table.
👉 Big table should probe.

If you LEFT JOIN a big table on a small table without stats, you could OOM the cluster.

🔄 If stats are missing, rewrite manually:

  • Flip LEFT JOIN to RIGHT JOIN.

  • Use subqueries to manually control join order if needed.

3. Use Buckets and Sorted Data Layouts

In Redshift, every table is naturally sorted by a SORTKEY.
In Hive/S3/Trino setups? Tables are just piles of Parquet files unless you tell them otherwise.

🏗️ You should:

  • Create bucketed tables with sorted_by columns.

  • Choose sort keys that match common WHERE clauses.

Result?

  • Faster lookups.

  • Smaller files to scan.

  • Better partition pruning.

You can't just port SQL—you have to port data layout strategies too.

🧠 How to Future-Proof Your Data Architecture

Redshift looked modern once too.
Future-proofing isn’t about predicting the perfect stack — it’s about designing for survivability and change.

1. Avoid Storage-Compute Lock-In

Anything that bundles storage and compute (e.g., classic Redshift DS nodes) will eventually hurt you at scale.

✅ Prefer architectures where compute and storage scale independently.
✅ Build systems where adding storage doesn’t mean wasting compute—and vice versa.
(S3 + Trino is a good example.)

2. Design with Migrations in Mind

Every system you build today will someday be legacy.
Prepare by:

  • Standardizing schema management early (use Glue, Metastore, Alembic, or Liquibase).

  • Isolating system-specific features behind abstraction layers.

  • Building observability into everything: query tracing, table lineage, schema evolution logs.

🔄 Your replacement project in 5 years should already have breadcrumbs to follow.

3. Treat Metadata as a First-Class Citizen

Systems like Hive, Iceberg, Delta Lake?
They work because they own the metadata.

✅ Invest in consistent table formats, catalogs, and lineage tracking.
✅ Make metadata portable across query engines.

Your query engine might change (Presto → Trino → something else).
Your data layout and metadata strategy is what gives you mobility.

4. Simulate Failure Before Reality Forces You

🔥 Regularly run chaos drills:

  • Expire certificates.

  • Rotate encryption keys.

  • Break network access to S3 buckets.

  • Change timestamps into the future.

Ask:

  • Can you still query?

  • Can you recover?

  • Can you detect the problem before users call you?

You don’t design resilience by accident, you rehearse it.
