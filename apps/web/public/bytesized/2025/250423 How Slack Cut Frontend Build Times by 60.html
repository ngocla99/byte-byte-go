In large engineering orgs speed to deploy can be the difference between flow and frustration. At Slack, the DevXP team spotted a subtle but costly inefficiency in their CI/CD pipeline: frontend builds were running even when no frontend code had changed.

The result? Wasted compute, slower merges, and gigabytes of redundant data clogging up AWS S3.

Let’s break down how they turned this silent productivity killer into a 60% efficiency gain without writing any brand-new tools.

🚀 TL;DR


Slack engineers optimized their E2E testing pipeline by skipping unnecessary frontend builds. They used git diff to detect relevant code changes, reused recent assets via an internal CDN, and cut build frequency by 60% saving time, compute, and terabytes of cloud storage.

Here’s what we’ll cover:

  1. What Happened

  2. The Fix - Don’t Build What You Don’t Need

  3. What Made This Hard?

  4. The Results

  5. Lessons For Devops and infra teams

1️⃣ 🛠️ What Happened?

Slack’s main monorepo runs full end-to-end tests before merging any code. This covers everything from backend logic to the frontend UI. But there was a catch:

Every PR triggered a full frontend build. Even if the changes were in backend-only files.

🕐 Each frontend build took ~5 minutes
📦 Each artifact was nearly 1GB
📈 Multiply that by hundreds of PRs per day

You get:
❌ Redundant builds
❌ Slower pipelines
❌ Expensive cloud usage

2️⃣ 🧠 The Fix: Don’t Build What You Don’t Need

Instead of overhauling their system, Slack made two smart tweaks:

Step 1: Check Before You Build
They used git diff to detect whether a PR touched any frontend files. If not, the pipeline skipped the build.

Step 2: Reuse What You Already Have
They fetched a recent, still-in-production build from AWS S3 and served it via an internal CDN. This meant:

  • No new build

  • No storage bloat

  • No time wasted

⚡ Average decision time: under 3 seconds
📉 Build frequency: down 60%

3️⃣ 🧱 What Made This Hard?

Scaling this across a monorepo with 100,000+ files came with challenges:

  • Efficient Diffing – git handled it well, but the logic had to be airtight.

  • Artifact Management – Finding a valid, fresh asset in a sea of builds required smart naming and indexing.

  • Pipeline Integration – The new system had to plug cleanly into existing tools, not break things.

And it had to work without developer intervention. Always.

4️⃣ 📈 The Results

The gains were dramatic:

  • ⏱️ Build Time Cut by 50% – From ~5 mins to ~2 mins

  • ☁️ Storage Savings – Several terabytes of S3 usage avoided per month

  • ⌛ Dev Time Saved – Hundreds of hours monthly across the org

  • 🧪 Lower Flake Rate – Fewer builds = fewer flaky test variables

They also discovered old, untouched legacy systems in the process—turning optimization into exploration.

5️⃣ 🧭 Lessons for DevOps and Infra Teams

Here’s what Slack’s experience teaches us:

1️⃣ Optimize the Boring Stuff
Slow pipelines don’t make headlines, but they drag everyone down. Optimizing them lifts all boats.

2️⃣ Reuse Intelligently
Caching and asset reuse isn’t sexy, but it’s incredibly effective when done right.

3️⃣ Don't Overbuild
Conditionally skipping work is often better than speeding up the work.

4️⃣ Look for “Innocent” Inefficiencies
Just because something works doesn’t mean it’s good. Slack’s old system didn’t fail. It just slowed everyone down.

5️⃣ Think of DevXP as Infrastructure
CI/CD, build systems, test stability these aren’t chores. They’re productivity engines.

🚀 Bottom Line:


Slack saved time, money, and brainpower not by building a shiny new system, but by questioning the default behavior of an existing one.

Sometimes, the fastest path forward starts by skipping the path entirely.
