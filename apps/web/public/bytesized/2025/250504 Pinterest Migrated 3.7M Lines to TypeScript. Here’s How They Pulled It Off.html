📦 Pinterest Migrated 3.7M Lines to TypeScript. Here’s How They Pulled It Off

A breakdown of Pinterest’s tooling, automation, and lessons from rewriting their frontend at scale

In eight months, Pinterest rewrote the backbone of their web infrastructure. Not for fun, but for survival.

They migrated 3.7 million lines of code from Flow to TypeScript in a single coordinated rollout. It was a systemic transformation touching everything from CI pipelines to how internal pages were routed and served.

Let’s break down the strategy, the landmines, and what you can steal from their playbook.

🚨 TL;DR

Pinterest had used Flow for typed JavaScript since 2016. By 2023, that decision aged out: Flow stagnated, TypeScript won the ecosystem, and hiring Flow developers became painful.

They pulled off the migration using a “big bang” approach, with aggressive automation, battle-tested codemods, and airtight testing. The result: a better developer experience, faster builds, fewer type bugs and a TypeScript codebase that scales.

They’ve open-sourced their tools and shared lessons. If you’re still on Flow (or stuck on legacy tech), this is the blueprint.

🧭 Why They Chose TypeScript

Pinterest didn’t switch because Flow was broken they switched because TypeScript offered tangible advantages across the board:

  • Hiring: TS skills are everywhere. Flow? Almost nowhere.

  • Tooling: TypeScript support in editors, linters, and language servers is miles ahead.

  • Ecosystem: OSS libraries and community tooling now assume TypeScript.

  • Language Features: TS supports conditional types, inference tricks, and const assertions that Flow simply doesn’t.

  • Momentum: Even Meta is leaning more into TypeScript. The writing was on the wall.

Pinterest had achieved 100% Flow coverage, meaning no gradual transition left. It was all or nothing.

Over time, TypeScript became the industry’s go-to, a shift clearly visible in its dominance across npm download stats.

🏗️ Planning a Big Bang Migration

This project was a structured replacement, one where every file was transformed, tested, and reconnected to the wider ecosystem.

They split the work into three key phases:

  1. Setup – Get the TypeScript compiler, linters, and build tooling ready

  2. Conversion – Use codemods to transform Flow syntax to TypeScript

  3. Integration – Update every system that assumed .js, from test runners to internal page routing

Every step had its own edge cases. Every subsystem had assumptions that now broke.

⚙️ Converting Millions of Lines (Without Going Insane)

Pinterest automated the conversion using an extended version of Stripe’s flow-to-typescript codemod. But codemods don’t cover everything.

They had to patch:

  • $ReadOnlySet, $Partial, T[K] syntax

  • Conditional intersection types like (A | B) & (C | D)

  • Incorrectly handled Flow functions like ?() => void

  • Comment semantics (@ts-expect-error vs eslint-disable-next-line ordering)

They also extended ESLint to catch React/DOM type confusion (React.Node vs Node) and used autofix rules to eliminate unused or weak types.

Every missed case was logged, fixed, and committed as a reproducible patch.

🧬 Migrating Generated Types Without Breaking Contracts

Pinterest relies heavily on generated types:

  • Apache Thrift for backend RPC types

  • OpenAPI for REST interfaces

  • Relay for GraphQL fragments and hooks

Each had to be upgraded in lockstep:

  • Thrift enums needed as const to enable TS to infer exact string values

  • OpenAPI switched to openapi-typescript, with a wrapper to preserve type shape

  • Relay had to be rewritten around new React hook typings

In many systems, a mismatch between TS and Flow type shape could silently break production — so they treated the shape compatibility as critical infrastructure.

📁 Breaking Assumptions: JS Filename Mayhem

File extensions aren’t just aesthetics. Pinterest’s internal tools, webpack configs, testing systems, and monitoring dashboards all assumed .js files.

They had to:

  • Update 100+ places that used glob patterns like *.js

  • Patch in-house tools like Metro (used for flaky test tracking)

  • Maintain handler IDs used in logging and routing without breaking alerting dashboards

  • Shim interfaces so .js extensions still worked in reporting, even though .ts was used in builds

This work wasn’t glamorous — but it’s the kind of migration debt that sinks timelines if ignored.

🔁 Transpilation Without Breaking the Build

Pinterest already used Babel to strip Flow types. Now they needed it to strip TypeScript — with identical output.

They validated:

  • Byte-for-byte diffs between Flow output and TS transpilation

  • Custom Babel plugins were updated to understand TypeScript ASTs

  • CI pipelines and build steps worked identically post-migration

This let them deploy the TypeScript branch to production shadow traffic — weeks before the official cutover.

🧪 How They Knew It Worked

Big migrations need bigger validation.

  • Daily rebases and dry runs: They rebuilt the TS branch from main every day to catch new drift.

  • Three full rounds of QA: End-to-end tests and manual validation.

  • Canary deployments: They shipped TS to a subset of users, watching for behavioral regressions.

By the time they merged, they had over 60 clean passes through the automation pipeline. It wasn’t a surprise, it was rehearsed.

🛠 Open Source Contributions

Pinterest didn’t hoard their migration tooling. They contributed back:

  • Support for edge-case Flow syntax

  • ESLint patches for TS compatibility

  • Automation scripts for codemod + error suppression + formatting

You can find it on GitHub under flow-to-typescript, with enough polish to reuse in your own org.

🧩 Lessons Worth Stealing

If you’re planning a major migration, these takeaways apply no matter what you’re switching from:

1. Automate early and often.
Run your codemod daily. Catch conflicts before they snowball.

2. Codemods won’t catch everything.
Patch the gaps and isolate manual fixes to a single commit.

3. Filename assumptions are deep.
Your build, test, and logging systems will all have hardcoded paths. Surface them early.

4. Validate like production depends on it.
Because it does. Test at every layer — output diffs, UI behavior, and downstream integrations.

5. Don’t wait for the perfect moment.
You’ll never get it. Start rehearsing the cutover now.

🧾 Final Word

Pinterest’s migration wasn’t just about switching type checkers. It was a company-wide move to a better DX foundation, powered by thoughtful automation and relentless validation.

They didn’t ask “can we migrate?”
They asked “what would need to be true to make this safe?”

And then they made it true, one codemod, patch, and rebase at a time.
