Real-world programming workflows augmented by AI

There are bugs that scream when they break. Then there are bugs that whisper, quietly degrading performance, eating file handles, and lurking in the dark corners of your codebase.

Resource leaks in Java fall into that second category. You won't notice them until your thread pool chokes or your app fails to open a file. At scale, they're not just nuisances, they're systemic risks. And at Uber scale, they show up by the hundreds.

Fixing them sounds easy: just close your BufferedReader. But in reality? The fix is often manual, error-prone, and thankless.

So Uber turned to generative AI to automate the whole thing, and caught the attention of developers worldwide who've been fighting the same battle.

🧩 The Problem: “You forgot to close it.”

In Java, failing to release resources like files or streams causes leaks. Sure, tools like SonarQube flag these, but fixing them is another story.

Historically, engineers relied on try/catch/finally blocks, but forgetfulness (or just fatigue) meant many resources never got closed. Then came try-with-resources, Java’s syntactic sugar that ensures safe cleanup.

But in a sprawling microservices codebase, retroactively migrating leaky code is expensive, and automating the fix is hard:

  • You can’t close resources that are returned from a method.

  • You can’t blindly refactor without introducing new bugs.

  • You have to ensure build integrity and test pass rates.

And that’s where Uber’s FixrLeak enters the picture.

⚙️ The System: AST-First, AI-Second

FixrLeak isn’t just an AI wrapper. It’s a pipeline. Here’s how it works.

  1. SonarQube flags the leak

  2. Tree-sitter parses the function to build an AST

  3. FixrLeak inspects scope: Is the resource confined to the function? Returned? Stored in a field?

  4. If safe, it generates a prompt, sends it to GPT-4o, and swaps in the fixed code

  5. The new function is tested, rebuilt, validated, and submitted as a pull request

Critically, FixrLeak only acts on functions where the resource lifetime is local, a design constraint that avoids 90% of potential false positives.

That tight constraint makes the system high precision, low drama which is exactly what you want from automation embedded in CI.

✅ Results That Actually Matter

Out of 124 resource leaks detected:

  • 12 were in deprecated code

  • 102 were valid for FixrLeak analysis

  • 93 were fixed fully automatically

  • All PRs passed builds and tests

  • Code reviewers typically only had to click “Approve”

This isn’t a proof-of-concept. It’s an operational system improving code quality every week at one of the world’s largest Java shops.

🤖 Why GenAI Alone Wasn’t Enough

You might be tempted to think: “Just feed the function to GPT-4 and let it fix it.”

But without AST analysis, you’ll run into:

  • Resources closed prematurely

  • Invalid refactors that break test logic

  • Changes that look right but aren’t semantically safe

By leading with static analysis and scoping the problem well, FixrLeak plays to GenAI’s strengths without letting it run wild.

The lesson here isn’t “use AI.”
It’s: Use AI within a carefully constrained system.

🧠 What Senior Engineers Should Take Away

This goes way beyond being a handy tool. It's a complete blueprint.:

  • Use static analysis to select safe targets for automation

  • Combine LLMs with deterministic pre-checks and post-checks

  • Accept that AI is probabilistic but design systems around it that aren’t

  • Automate the boring 80% and leave the hard edge cases for humans

  • Don’t just build tools, build pipelines that ship fixes at scale

FixrLeak also shows the power of focusing on scoped wins. Rather than aiming to fix every leak, it aims to fix the easy ones, reliably and continuously. That’s where the compounding value kicks in.

📍 What’s Next?

Uber’s Programming Systems group is expanding FixrLeak to:

  • Support inter-procedural analysis (leaks across method boundaries)

  • Detect leaks using GenAI, not just fix them

  • Extend to languages like Go, which lack robust leak detection tools

  • Build richer semantic models of code behavior before fixing anything

This is the future: real-world programming workflows augmented by AI, not replaced by it.

🎯 Final Word

FixrLeak shows what happens when AI meets software engineering discipline. Not hype. Not hallucinations. Just useful automation, quietly improving one of the oldest, most overlooked problems in Java development.

And for the rest of us? This is a reminder:

If you’ve got recurring bugs and structured code patterns,
you’ve probably got a FixrLeak of your own waiting to be built.
