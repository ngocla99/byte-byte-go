When a Foreign Key Crashed Heroku

How a Simple Schema Bug Took Down Heroku, and How the Immediate Fix Made It Worse

TL;DR

On June 8, 2023, Heroku suffered a multi-hour outage that broke every customer-facing surface (the Dashboard, CLI, and API) while customer apps continued running.

The cause? A small oversight in database schema design.

A foreign key field used a data type too small to reference the primary key it was linked to. This mismatch worked for a long time until the primary key exceeded the limit. Then everything broke. And fixing it triggered a second outage.

It’s a case study in how one small misalignment in your database schema can take down a platform.

🚨 Incident Summary

Duration: 15:06 – 18:57 UTC, June 8, 2023
Impact:

  • 1h45m: No new deployments or logins

  • 2h3m: Full API outage (CLI, Dashboard, slugs, webhooks — all unusable)

  • Running customer applications were not affected

🔍 What Happened?

At 15:05 UTC, a PostgreSQL foreign key constraint failed due to a data type mismatch: the foreign key column was defined with a smaller type (e.g., INTEGER) than the primary key it referenced (e.g., BIGINT). Once the primary key values crossed the threshold, creating new authorizations (and by extension, deploying) failed.

The on-call team responded quickly with a migration to update the foreign key to the correct type, but this schema change had a hidden cost: it wiped internal Postgres statistics, which the query planner uses to make execution decisions.

Without those stats, query performance collapsed. The API, already in recovery mode, fell over completely. This made a bad situation even worse. Engineers had to switch the system into read-only mode to stabilize it while they rebuilt the stats.

By 18:24 UTC, queries returned to normal. At 18:57 UTC, the API was back in full read/write mode and the incident was closed.

🧠 Root Causes

1. Schema Mismatch Between FK and PK

This might sound obvious but, foreign keys must match the data type of the primary key they reference or you risk silent failure when IDs grow as they did in this case

2. No Type Limit Monitoring

There were no checks to detect when values in a column were approaching the limit of their defined data type (like an INT getting close to 2,147,483,647).

3. Post-Migration Blind Spot

Changing the column type cleared Postgres planner statistics, but the migration playbook didn’t include steps to analyze or refresh those stats.

4. Cascading Effects

The platform’s authorization layer was tightly coupled to deployment and API routing logic. When auth broke, everything above it failed — webhooks, slugs, CLI, Dashboard.

🧰 The Cascade

Data type overflow → Auth creation fails → Deployments and login break → Migration starts → Query planner stats wiped → Query times explode → API outage escalates → Read-only recovery mode → Stats restored → Full recovery

🤨 Lessons Learned

Heroku’s engineering team is rolling out several changes — and there are broader takeaways for everyone managing systems at scale:

1. Schema Type Consistency

Always match foreign key types to the primary key. If you use BIGINT for primary IDs, every FK should use the same, no exceptions.

2. Proactive Limit Alerts

Add monitoring that flags columns approaching their max value. Set alerts at 70%, 90%, and 99% of capacity, especially for incrementing IDs.

3. Stat-Preserving Migrations

PostgreSQL can suffer massively from stats loss after ALTER TABLE. Your migration playbook should always include an ANALYZE or equivalent to refresh the planner.

4. Staging Can’t Just Mean “Empty”

Most test environments don’t simulate real-world load or data skew. This kind of performance regression won’t show up in staging unless you mimic prod-scale traffic.

5. Loose Coupling Between Authorization and Runtime

A broken auth layer shouldn’t bring down the deployment engine, dashboard, and all control plane activity. Critical systems need failure boundaries and not shared failure modes.

📚 Bigger Picture: Why These Failures Happen

In complex systems, it’s rarely the flashy stuff that brings things down. It’s a forgotten column type. A quiet default. A single line in a migration script. These invisible cracks only matter when scale exposes them.

This is why schema design needs to be treated like interface design. Small misalignments now can break big things later.
And in systems like Heroku, where databases underpin identity, deployments, and configuration, the blast radius is huge.

This wasn’t a case of bad luck. It was a gap in resilience thinking, the belief that things will keep working because they always have.

🏗️ What Heroku Implemented to Avoid Recurrence

  • FK/PK type check tooling to block unsafe schema designs at CI time

  • Data type saturation monitors to avoid hitting hard limits silently

  • Migration safety upgrades to rebuild query stats post-change

  • Incident playbook improvements to define when/how to shift APIs to read-only without breaking client expectations

🏁 Bottom Line

This incident shows how subtle schema mistakes can ripple outward, turning into full-system outages, even while apps appear healthy.

For engineering leaders and architects:

  • Watch your data types like you watch your APIs

  • Assume migrations will break things and then build safety nets

  • Decouple critical paths like auth and deploy from each other

  • Never let your observability stack be blind to internal planner behavior
