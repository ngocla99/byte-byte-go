Why “Monitoring” Alone Isn’t Enough

Monitoring is like checking your vitals at the doctor. It tells you if your heartbeat is irregular or your blood pressure is high. But when something’s wrong, you need more X-rays, MRIs, or blood tests to figure out the root cause. Observability is the full diagnostic toolkit, enabling you to dissect, understand, and fix the problem.

In distributed systems services can be scattered across microservices, databases, and queues, so at times traditional monitoring can’t keep up. Metrics alone might show a latency spike, but without logs and traces, you’re left guessing:

  • Is it a network issue?

  • A database lock?

  • A slow external API call?

Metrics

Metrics are time-series data points that show how your system behaves over time. They’re lightweight, real-time, and perfect for spotting anomalies. But metrics without context are like breadcrumbs without a trail.

Going Deeper

Raw metrics are a starting point. The real value lies in how you analyze and interpret them. For instance:

  • Rate, Count, and Distribution: Instead of just knowing there are 1,000 requests, track their rate per second and their distribution (e.g., 95th percentile latency).

  • Derived Metrics: Combine base metrics for insights, like error rate = (errors / total requests) × 100.

The Challenges of Metrics

Metrics are lightweight, but they’re also shallow. A spike in error rates might tell you there’s a problem but not why. That’s where logs come in.

Logging

Logs are the textual records of events happening inside your system. If metrics tell you that errors are increasing, logs tell you what those errors are.

Structured Logging Is Non-Negotiable

Unstructured logs are like a messy filing cabinet: all the information is there, but good luck finding it. Structured logging, on the other hand, formats logs in a machine-readable way (e.g., JSON). This makes searching and correlating logs across services much easier.

What to Log

  1. Errors and Exceptions: The “what went wrong” moments.

    • Include stack traces, timestamps, and request IDs.

  2. Key Actions: Record significant events like user logins, database queries, or cache misses.

    • Add context: Which user? Which resource?

  3. State Changes: Track when something transitions—service restarts, feature toggles, etc.

Common Pitfalls in Logging

  1. Overlogging: Logging every little detail clutters your system and drives up storage costs. Use log levels (INFO, WARN, ERROR) wisely.

  2. Underlogging: Missing critical context can render logs useless. Always include request IDs or correlation IDs to tie events together.

Logs tell a richer story than metrics, but they’re still missing the bigger picture: How does this error fit into the broader system?

Traces

Distributed tracing is the unsung hero of observability. Traces follow a single request as it travels through your system, showing every service, every database query, and every queue it touches.

How Traces Work

  1. Trace IDs: Each request gets a unique ID, passed along as it traverses the system.

  2. Spans: Each operation (e.g., a database query, API call) within the request is logged as a “span.”

  3. Visualization: Traces stitch spans together into a timeline, showing where bottlenecks occur.

When Tracing Shines

Imagine your metrics show that latency has doubled. Your logs reveal that the database is taking longer to respond. But your traces? They pinpoint which query in the database is slow, which microservice is making that query, and which user action triggered it.

Best Practices for Lead Engineers to Assess Observability Effectiveness

Ensuring that the state of your system’s observability is "good enough" takes continuous evaluation and refinement. As a lead engineer, your goal is to validate whether your metrics, logging, and alerts provide the right level of visibility to detect and resolve issues efficiently. The following best practices will help you assess and improve observability across your systems.

1. Conduct Chaos Testing to Validate Observability Readiness

Chaos testing is a proactive approach to stress-test your observability by introducing controlled failures into your system. Read more about how slack leverages chaos testing here! This practice helps determine if your existing monitoring tools, metrics, and alerts effectively detect and respond to unexpected issues.

How to Implement Chaos Testing for Observability:

  • Inject Failures: Use tools like Chaos Monkey or Gremlin to simulate real-world failure scenarios such as node failures, API slowdowns, or database outages.

  • Observe Metrics and Alerts: Ensure that critical issues are promptly detected by existing dashboards and alerts. Verify if alerts are firing at appropriate thresholds and providing actionable insights.

  • Evaluate Logging Adequacy: During the failure, analyze log entries to check if they contain enough detail (e.g., timestamps, correlation IDs, error codes) to facilitate root cause analysis.

  • Iterate Based on Findings: If critical failures go undetected or take too long to identify, refine your logging strategy, update thresholds, and improve alert descriptions.

Key Questions to Ask:

  • Are failures detected within an acceptable time frame?

  • Do alerts provide enough context to take action without further investigation?

  • Is logging detailed enough to track down the root cause without ambiguity?

  • Are redundant or missing logs creating blind spots?

2. Assess Metrics Coverage and Granularity

Effective observability relies on capturing the right metrics at the right level of granularity to identify trends and anomalies before they escalate into incidents.

Best Practices for Evaluating Metrics:

  • Coverage Check: Ensure critical system components (APIs, databases, infrastructure) have well-defined metrics covering performance, reliability, and resource utilization.

  • Granularity Assessment: Metrics should have sufficient resolution to capture transient issues. For example, tracking API latency at P90 and P99 percentiles can reveal performance bottlenecks often missed by average response times.

  • Correlation of Metrics: Cross-reference related metrics (e.g., CPU spikes with request latencies) to ensure they align and provide a holistic system view.

  • SLO/SLI Validation: Confirm that your metrics align with service level objectives (SLOs) and service level indicators (SLIs) to measure real user impact accurately.

Key Questions to Ask:

  • Do your metrics and dashboards reflect real-world performance degradation?

  • Are metric thresholds based on historical data and aligned with business needs?

  • Are there any blind spots where critical data is missing?

3. Audit and Optimize Alerting Strategies

Alert fatigue can hinder your team's ability to respond to incidents effectively. A well-structured alerting system should prioritize actionable, meaningful alerts without overwhelming engineers.

Best Practices for Effective Alerts:

  • Avoid Noise: Regularly review alerts and eliminate redundant or low-priority notifications that do not require immediate attention.

  • Use Dynamic Thresholds: Implement intelligent alerting mechanisms that adapt to trends instead of relying solely on static thresholds.

  • Ensure Escalation Paths: Alerts should have clear ownership and predefined escalation paths to avoid confusion during incidents.

  • Tune Alerting Sensitivity: Balance between false positives and missed incidents by analyzing past alert effectiveness.

Key Questions to Ask:

  • Are critical issues detected without excessive noise?

  • Do alerts contain enough actionable context?

  • Are alerts properly categorized by severity and urgency?

4. Improve Logging Practices for Better Observability

Logs serve as the first line of defense in troubleshooting, but logging too much or too little can create challenges.

Best Practices for Effective Logging:

  • Ensure Contextual Logging: Include meaningful metadata such as request IDs, user IDs, and correlation identifiers to track events across distributed systems.

  • Log at Appropriate Levels: Use standardized log levels (DEBUG, INFO, WARN, ERROR) and ensure they align with operational needs.

  • Structure Logs for Searchability: Use structured logging formats (e.g., JSON) to facilitate querying and automated analysis.

  • Retention and Storage Policies: Define log retention policies to strike a balance between cost and compliance.

Key Questions to Ask:

  • Do logs provide enough detail for rapid issue diagnosis?

  • Is there a clear distinction between operational and debugging logs?

  • Are logs easily searchable and aggregated across services?

5. Leverage Post-Mortems to Drive Observability Improvements

Post-mortems are invaluable for learning from incidents and identifying gaps in your observability strategy. Learn exactly how to in our previous editions "Writing Post-Mortems A Tech Lead’s Guide To Learning From Failure” and “The ChatGPT Outage: What OpenAI’s Post-Mortem Revealed“.

Best Practices for Writing Effective Post-Mortems:

  • Root Cause Analysis (RCA): Focus on identifying not just technical failures but also observability gaps that contributed to delayed detection or response.

  • Actionable Insights: Clearly define observability-related action items, such as adding new metrics, refining alert thresholds, or improving log coverage.

  • Blameless Culture: Encourage open discussions without finger-pointing to foster a culture of continuous improvement.

  • Follow Up: Assign ownership to observability improvements and track progress to ensure issues are resolved.

Key Questions to Ask:

  • Did the existing observability stack help detect the issue promptly?

  • Were engineers able to diagnose the problem efficiently using available data?

  • What observability gaps were identified, and what actions can close them?

Key Metrics to Monitor and Alert On

API Services

  1. Latency (Milliseconds)

    • Measure request/response times at various percentiles (P50, P90, P99) to identify performance bottlenecks.

    • Granularity: Track per endpoint and per HTTP method (GET, POST, etc.).

    • Unit: Milliseconds (ms).

  2. Availability (Percentage)

    • Track uptime as a percentage over time (e.g., 99.9% over 30 days).

    • Measure error rates (4xx, 5xx HTTP codes) as a percentage of total requests.

    • Granularity: Daily/hourly breakdown to identify patterns.

    • Unit: Percentage (%).

  3. Service Health (Ratio)

    • Monitor request success/failure ratios to detect anomalies.

    • Key metric: Ratio of 2xx responses to total requests.

    • Granularity: Aggregate over hourly/daily windows.

    • Unit: Ratio.

  4. Resource Usage (Absolute and Percentage)

    • Observe CPU utilization (%), memory usage (MB/GB), and request concurrency levels.

    • Granularity: Per container/pod or host instance.

    • Units: Percentage for CPU, MB/GB for memory.

Front-End Website

  1. Page Load Time (Milliseconds)

    • Breakdown into key phases: DNS resolution, TCP handshake, server response, DOM processing, and full load.

    • Granularity: Capture metrics per page, per device type, and geographic region.

    • Unit: Milliseconds (ms).

  2. User Experience (Rates & Time)

    • Engagement: Track session duration (seconds), time on page (seconds), and click-through rates (CTR %).

    • Bounce Rate: Percentage of single-page visits without interaction.

    • Interaction Latency: Measure time-to-interaction (TTI) in milliseconds.

    • Granularity: Per page and user segment.

  3. Errors (Absolute Count and Rate)

    • Monitor client-side JavaScript errors, API failures (per endpoint), and unhandled exceptions.

    • Track error rate as a percentage of total interactions.

    • Granularity: By browser, device, and region.

  4. Resource Optimization (Count and Size)

    • Measure third-party script load times, number of requests, and overall payload size (KB/MB).

    • Monitor render-blocking resources.

    • Granularity: Per page and component.

Databases

  1. Query Performance (Milliseconds and Count)

    • Identify slow queries by tracking execution time at P50, P90, P99.

    • Monitor queries per second (QPS) to assess system load.

    • Granularity: Per query type (SELECT, UPDATE, DELETE).

    • Unit: Milliseconds (ms), Queries Per Second (QPS).

  2. Connection Health (Absolute Count and Percentage)

    • Track active connections vs. maximum allowed.

    • Monitor connection errors per second.

    • Granularity: Per database instance.

  3. Storage Usage (GB and IOPS)

    • Monitor disk I/O operations (read/write ops per second).

    • Track available vs. used storage capacity (GB).

    • Granularity: Per table or partition.

  4. Index Efficiency (Percentage and Count)

    • Track index hit ratio (% of queries utilizing indexes).

    • Monitor unused or redundant indexes to optimize storage.

    • Granularity: Per table and index type.
