A Beginner’s Guide to Clocks, Causality, and Ordering in Distributed Systems

Why does something as simple as reading the time become a hard problem for distributed systems?

On a single computer, every event can be measured against one clock, so the order of the events is never in doubt. However, a distributed system, where work is spread across many independent machines, lacks a shared reference. Each machine can read time from its own hardware clock, but those clocks do not stay aligned. Network Time Protocol (NTP) tries to bring the clocks together, but it cannot eliminate the problem.

This becomes a real problem whenever correctness depends on the order in which things happened. If events on different machines are ordered by comparing timestamps, a small difference in the wrong direction can change the result. For example:

  • An update that happened later can be discarded in favor of an earlier one, because clock differences gave the earlier write the larger timestamp, and the newer data disappears with no error raised.

  • Logs gathered from several machines can place an effect before its cause, which makes tracing a problem much harder.

  • An operation that depends on a correct order, such as granting access only after the change that authorized it, can act on stale information.

In this article, we look at these ideas in detail:

  • Why a machine’s own clock is a poor basis for ordering events, and how close synchronization can realistically get

  • What it means for one event to have happened before another, and why some pairs of events have no defined order

  • Logical clocks and vector clocks, and what each one can and cannot determine

  • Why the order of events matters in practice, for replication, auditing, and debugging

  • Hybrid logical clocks and the problem they were designed to solve

  • How a globally distributed database such as Google Spanner approaches ordering at scale

Clock Drift

The most direct way to order events across machines is to mark each event with the local time and compare the timestamps. However, this approach fails because the clocks themselves do not keep the same time.

A machine’s wall-clock time, the everyday calendar time it displays, comes from a small quartz oscillator on the hardware. No two oscillators run at exactly the same rate, and their rate shifts with temperature and age. The effect is tiny in isolation (on the order of a few parts per million), but it accumulates. Therefore, two machines left alone will drift apart second by second.

NTP tries to solve this by periodically checking a more accurate source and adjusting the local clock toward it. As mentioned, that correction narrows the gap without closing it. For reference, over the public internet, machines synchronized with NTP are typically held within a few milliseconds of the reference, and on a local network, the difference can be kept under a millisecond [2].

A few milliseconds may sound close enough to ignore. It is not, once a system handles thousands of events per second. Within that window, many operations occur on different machines, any of which might be marked out of order relative to when they actually happened. Two writes to the same record, arriving a millisecond apart, can carry timestamps that place them in either order depending on which machine’s clock was momentarily ahead.

Also, drift is only half of the difficulty, because the same clock can also seemingly run backward. Let’s investigate how.

Clock Jumps

A wall clock is not guaranteed to move only forward. NTP not only speeds up or slows down the local clock. When the local clock has drifted far enough, a correction can set it to an earlier value, which steps time on that machine backward. Leap seconds (the occasional extra second added to civil time to keep it in line with the Earth’s rotation) can produce a similar backward step.

This is not just a theoretical concern. On the first day of 2017, a leap second was added at midnight, and a piece of software at Cloudflare computed the gap between two timestamps and produced a negative number. The code had been written on the assumption that time only moves forward, so a negative gap was treated as impossible, and the program failed when it occurred. The result was a period of errors affecting part of Cloudflare’s DNS traffic until the code was patched to handle a backward step [3].

Because of this, most operating systems provide two separate clocks:

  • One is the time-of-day clock, which tracks calendar time. This is the clock that NTP adjusts, and it can move backward.

  • The other is the monotonic clock, which only ever increases and is meant for measuring how much time has passed on one machine. Its value carries no calendar meaning and cannot be compared between machines.

The takeaway is that a clock that cannot be relied on to move forward is a poor basis for determining the order of events. The challenge is to define order without depending on any single clock reading.

Causal Ordering

The only ordering a distributed system can establish for certain is determining which events could have influenced which other events. This is the idea Leslie Lamport introduced in 1978, and it does not depend on reading a clock at all [1].

The relationship is called happened-before, and it exists in three situations:

  • If two events occur on the same machine, the earlier one in that machine’s own sequence happened before the later one.

  • If one event is the sending of a message and another is the receipt of that same message, the sending happened before the receipt.

  • Lastly, the relationship between events carries across chains. In other words, if event A happened before event B, and event B happened before event C, then event A happened before event C. This means that anything connected by such a chain has a definite order.

If no chain of this kind links two events, the two events are called concurrent.

Concurrent does not mean that two events occurred at the same physical instant. It means that neither event happens before the other in the system’s causal ordering. There is no chain of local execution steps and message exchanges through which either event could have influenced the other. In other words, the system cannot causally order them, even if the timestamps show that they occurred an hour apart. Conversely, two events separated by only a microsecond may be causally ordered if program order or a message chain connects them.

This means two things:

  • Causality is the one order a distributed system can establish without trusting a clock.

  • Concurrency is an important condition that the system has to account for.

Let us now look at the concept of logical clocks.

Logical Clocks

A single counter per machine is enough to number events so that the numbers never contradict the happened-before relationship. In Lamport’s 1987 paper, this number is called the Lamport timestamps [1].

The rule is that each machine keeps a counter, which is incremented on every event. When a machine sends a message, it attaches the current value of its counter. When a machine receives a message, it sets its counter to the larger of its own value and the value carried in the message, and then increments it once more. This guarantees that if one event happened before another, the first event’s number is smaller than the second’s.

Let us understand using a simple example:

  • Machine A sends a message with its counter at 2.

  • Machine B, holding a 1 of its own, receives it, takes the larger of 1 and 2, adds one, and arrives at 3.

  • A later message from B (triggered by the message from A) is stamped 4. It reaches machine C holding a 1, which takes the larger of 1 and 4, adds one, and arrives at 5.

If we read along this chain of events, the numbers always climb. So an event that influenced another always carries the smaller number.

The limit of this approach exists when moving in the other direction.

A smaller number does not necessarily establish that one event happened before another. In the same example:

  • Let’s say that machine A performs one more local step after its message has already left. Nothing about that step reaches machine C.

  • This new local step on machine A has the number 3. However, the previous receipt on machine C holds the number 5, which is higher than 3. Yet, it is clear that neither could have influenced the other, so they are essentially concurrent events.

  • In contrast, machine A’s earlier send event (numbered 2) that went through machine B and indirectly influenced the receipt on machine C (numbered 5). This means that a set of related events and an unrelated set of events can look identical in Lamport clocks.

  • Also, two concurrent events can even share a number, as the new step on A and the earlier receipt on machine B both hold a 3.

To summarize, a Lamport timestamp places all events in a single sequence. This is useful when every machine needs to agree on one order, but it cannot distinguish related events from concurrent ones. Telling those two cases apart requires more than a single number.

Vector Clocks

Giving each machine a list of counters, one entry per machine, produces a timestamp that can help distinguish related events from concurrent ones. This idea, known as Vector Clocks, extends the single Lamport counter into a vector, and it is the mechanism behind conflict detection in several replicated databases, including the design described in Amazon’s Dynamo paper [4].

In this approach, each machine keeps a vector with one slot per machine. At a local event, a machine increments only its own slot. When it sends a message, it attaches the whole vector. When it receives one, it takes the larger value in each slot and then increments its own slot. Comparing two of these vectors gives a richer result than comparing two numbers. For example:

  • One event happened before another when every slot in the first vector is less than or equal to the matching slot in the second, and at least one slot is strictly smaller.

  • The two events are concurrent when neither vector meets that condition against the other, which is exactly the case that a single Lamport counter wasn’t able to detect.

Let’s understand vector clocks using the same earlier example of machine A, machine B, and machine C. We write each timestamp as a vector [A, B, C]. Here are the steps:

  • Machine A sends with [2, 0, 0].

  • Machine B, holding [0, 1, 0], takes the larger value in each slot to reach [2, 1, 0], increments its own slot, and records [2, 2, 0].

  • B later sends [2, 3, 0], which reaches machine C holding [0, 0, 1], and C takes the larger value in each slot to reach [2, 3, 1], increments its own slot, and records [2, 3, 2].

The two comparisons that a single Lamport timestamp could not make can now be made clear. Every slot of the initial send by A [2, 0, 0] sits at or below the matching slot of C’s [2, 3, 2], so the send happened before that receipt. Against C’s [2, 3, 2], a second local step on A holds [3, 0, 0], where the first slot is larger on A while the third slot is larger on C, so neither vector sits at or below the other, and the two events can be considered concurrent.

The cost of this approach is the vector’s size (one entry per machine), which means that the metadata attached to every message grows as the system grows. In a large deployment, this becomes significant, and systems that trim the vector risk discarding the causal information it exists to preserve.

Conflict Resolution

The common rule for conflict resolution is last-write-wins, where the version carrying the larger timestamp is kept, and the other is dropped. It is simple and cheap. However, it can be undermined by clock drift, where a newer write can be accidentally discarded due to clock differences.

See the diagram below:

This is a real issue that databases have run into at times.

For example, Apache Cassandra applies last-write-wins using a timestamp taken from the client or the coordinating node. If that node’s clock is running behind, the write operation it coordinates carries a timestamp in the past. A later update stamped by a lagging node can then be treated as older than a write it should have replaced, in which case it is dropped, and the client still receives a success response. This case is recorded in Cassandra’s own issue tracker, where an update from a node with a slower clock is discarded because its timestamp is smaller than the value already stored [5]. Amazon’s DynamoDB applies the same last-writer-wins rule to resolve conflicts in its global tables, keeping the write with the latest internal timestamp per item [6].

Ordering also matters in two ways that do not involve losing data outright:

  • Logs collected from several machines and merged by timestamp can place a response before the request that caused it, making an incident harder to trace.

  • An operation that depends on an earlier step, such as one that should run only after the record authorizing it exists, can proceed against a stale state when the recorded order is wrong.

The aim, then, is to establish order without the fragility of raw timestamps or the growth of a per-machine vector.

Hybrid Logical Clocks

A hybrid logical clock keeps a physical time reading and a small counter together, which produces an order consistent with cause and effect while staying close to real calendar time. It was introduced in 2014 to connect two approaches used separately until then: physical timestamps favored in practice and causal tracking favored in theory [7].

A hybrid timestamp has two parts:

  • The first is a physical component, held close to the machine’s NTP-synchronized time, so the value remains meaningful as a real time.

  • The second is a logical counter that advances only when two events fall within the same physical instant, which keeps causally related events in order even when the physical readings cannot separate them.

The combination fits within a standard 64-bit timestamp field, never moves backward, and absorbs the small irregularities of NTP in the counter. In other words, it tracks causality in the manner of a logical clock while remaining tied to real time, on ordinary hardware.

This combination is now used across many production databases.

  • CockroachDB maintains a hybrid logical clock on each node and uses it to track causality between related events with less overhead than a full vector [8].

  • MongoDB uses a hybrid logical clock as its cluster time to provide causal consistency across a deployment [9].

  • YugabyteDB uses the same approach, under the name hybrid time, as the basis of its transaction ordering [10].

However, a hybrid clock stays close to real time, but it cannot fully guarantee that its physical component equals true time exactly, and one system takes a different route to make real time itself dependable for ordering.

Bounded Uncertainty

Google Spanner treats the current time not as a single value but as a range guaranteed to contain the true time. It then waits for that range to pass before completing a write. This mechanism is called TrueTime, and it lets Spanner order transactions in a way that matches real-world time across datacenters [11].

Rather than returning one instant, TrueTime returns an interval with an earliest and a latest bound, and the true time lies somewhere inside. The width of that interval is the amount of clock uncertainty at that moment. Spanner keeps it small (generally under ten milliseconds) using GPS receivers and atomic clocks in each datacenter that are constantly checked against one another [11].

The uncertainty is handled directly at commit time through a step called commit-wait. Before a transaction completes, it pauses until its assigned timestamp is certainly in the past, which takes a few milliseconds. After that pause, the timestamp reflects an order consistent with real time, so a transaction that finished before another began is placed ahead of it.

The benefit of this approach is an ordering that agrees with real-time at a global scale, but it also has trade-offs. It requires specialized clock hardware in every data center and adds a short delay to every write. When the uncertainty interval grows (for example, if a time source degrades), the system slows down to preserve correctness.

Other databases make a different trade-off toward similar goals. CockroachDB, for one, retries a read that falls inside its uncertainty window instead of waiting after every write [8].

Design Tradeoffs

No approach we’ve discussed removes the complete cost of ordering events across machines. Each one tries to manage that cost in a different way. The choice among them comes down to what makes sense for a specific system at a specific point in time. Here are some points that can help:

  • Wall-clock last-write-wins is the cheapest to run, but can lose writes when clocks differ.

  • Vector clocks detect concurrency precisely, but carry metadata that grows with the number of machines.

  • Hybrid logical clocks give causal order close to real time on ordinary hardware, without guaranteeing exact real time.

  • TrueTime gives an order that matches real time globally, at the cost of specialized hardware and added write latency

Two points are common to all of them:

  • Firstly, some events are genuinely concurrent, and no clock will order them. Therefore, a system is better built to detect and resolve conflicts than to assume they cannot happen.

  • Secondly, the accuracy of a machine’s clock still matters a lot, because the approaches that lean on physical time depend on that accuracy staying within known bounds.

Summary

In this article, we’ve looked at time, clocks, and ordering in distributed systems in detail. Here are the key learning points in brief:

  • Within a single machine, one clock orders every event, but a distributed system has no shared clock and must work around that absence.

  • Machine clocks drift apart because their oscillators run at slightly different rates, and NTP narrows this difference without ever removing it.

  • A machine’s wall-clock time can also move backward, after a correction or a leap second, which has caused real outages.

  • The order of events across machines comes from cause and effect, captured by the happened-before relationship, not from comparing clock readings.

  • Two events are concurrent when neither could have influenced the other, which is a real condition rather than a sign of the same instant.

  • A Lamport timestamp orders events with a single counter but cannot tell whether that order reflects cause and effect or is arbitrary.

  • Vector clocks can detect concurrency by keeping one counter per machine, at the cost of metadata that grows with the system.

  • Last-write-wins on wall-clock timestamps is simple but can discard a newer write when clocks differ, sometimes with no error reported.

  • Hybrid logical clocks pair physical time with a logical counter, giving causal order close to real time on ordinary hardware.

  • Google Spanner represents time as a bounded interval and waits out the uncertainty at commit time, ordering transactions by real time at the cost of special hardware and latency.

  • No scheme removes the cost of ordering, so the practical choice is to know which trade a system makes and to avoid trusting wall-clock timestamps for ordering when writes can overlap.
