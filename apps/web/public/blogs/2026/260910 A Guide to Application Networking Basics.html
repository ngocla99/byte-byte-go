A Guide to Application Networking Basics

Imagine a simple scenario where an e-commerce web application calls an API endpoint that returns information about a customer order.

At the application level, this looks like a pretty simple operation. But a lot is happening under the hood. First, the client queries the DNS for the IP address linked to the API endpoint. DNS might return the address of a load balancer rather than the address of a specific application server. The operating system then determines how packets should be sent to that IP address. It might choose to send them through the local network, an internet service provider (ISP), or several other routers. The ultimate goal is for the data packets to reach the destination network.

The most common protocol used for this is HTTP. However, before HTTP can send the request, the client usually needs to establish some form of connection with the destination server.

With traditional HTTPS, this means setting up a TCP connection. In this type of connection, the client and server perform a handshake by exchanging some initial packets so that both sides know a connection has been established. The client and server then perform a TLS handshake. Only after this can the HTTP request be sent securely. A load balancer receives it, selects a healthy application instance, and forwards the request. The application performs its work and sends the response back through the same path.

All of this falls under the realm of networking. Due to its ubiquitous nature, networking becomes an extremely important discipline for developers to master. In this article, we will look at the various aspects of networking in detail.

The Basic Vocabulary Around Networking

Before we get into comparing networking protocols, it’s good to understand a few basic terms.

  • IP addresses: It identifies a network destination by telling the network where packets should be delivered. A server might have an address such as 203.0.113.20. Modern systems frequently place proxies, load balancers, NAT gateways, containers, and virtual networks in front of the actual application. Therefore, the IP address seen by a client may belong to a load balancer rather than to the machine that actually runs the application.

  • Ports: While the IP address is used to identify a destination machine, the port identifies the exact service on that particular destination. For example: port 443 is the conventional port for HTTPS. A server listens for incoming requests on a known port.

  • Packets: Applications usually don’t send one large block of data across the network as a single object. The operating system divides the data into smaller units that can travel through the network. These units are known as packets. Different packets may take different amounts of time to arrive. Also, a packet might be lost, duplicated, delayed, or delivered out of order. Transport protocols take care of what should happen in such situations.

  • Latency and bandwidth: Latency measures how long communication can take between source and destination. A round-trip time(RTT) is the time taken by the data to travel to a destination and for a reply to return. On the other hand, bandwidth measures how much data can be transferred during a period of time. A connection can have high bandwidth but high latency. For example, a fast intercontinental connection might transfer a large file efficiently while still taking significant time to start each small request.

Let us now look at the various networking protocols that are commonly used.

TCP: A Reliable Ordered Byte Stream

TCP is the traditional transport protocol behind HTTP/1.1, HTTP/2, database connections, and most implementations of gRPC. Its core promise is that the bytes sent by one application will reach the receiving application reliably and in the same order as they were sent.

The official TCP specification talks about it as a reliable, in-order byte-stream service. Let’s understand what a “byte-stream” really is.

Suppose an application makes two writes:

Write 1: HELLO
Write 2: WORLD

TCP doesn’t promise that the receiving application will perform two corresponding reads. The receiving application might get the data in the following ways:

HELLOWORLD
Or:
HEL
LOWOR
LD

The only thing that TCP preserves is the order of bytes. Protocols such as HTTP and gRPC that are built on top of TCP must define their own structure so that the receiving application can find out where one message ends and the next message begins.

But how does TCP support reliability?

To do so, TCP assigns sequence numbers to data. The receiving application has to provide acknowledgment for everything it has received. If some data is missing, the sender has to retransmit it.

On top of this, TCP also performs two kinds of control:

  • Flow control prevents a fast sender from overwhelming a slow receiving application.

  • Congestion control prevents the sending application from overwhelming the network itself.

While these mechanisms make TCP quite dependable, they also introduce state and waiting.

To set up a TCP connection, we have a three-way handshake process:

  • The client sends a SYN.

  • The server replies with SYN-ACK.

  • The client returns an ACK.

The handshake process sets up a shared connection state. But it also costs network time. If the client and server are geographically distant, this whole handshake process can take up a large chunk of the overall request latency.

TCP is a strong choice to make when every byte matters and application developers don’t want to implement multiple concerns such as loss recovery, ordering, congestion control, and retransmission themselves. Web pages, API requests, database queries, and financial operations generally can’t tolerate missing or randomly reordered bytes.

The major limitation of TCP is that it requires the bytes to be delivered in order. For example, suppose packets containing bytes 1–100 and 201–300 arrive, but the packet containing bytes 101–200 is lost. TCP cannot present bytes 201–300 to the application till the missing bytes are also received. It must wait for the missing data.

This behavior is critical to fulfill TCP’s promise for an ordered-stream of data. However, it causes challenges such as head-of-line blocking.

UDP: Independent Datagrams with Few Guarantees

UDP provides a much simpler service as compared to TCP.

In UDP, an application sends discrete datagrams, and the network makes a best effort to deliver them. UDP does not provide built-in guarantees that:

  • The datagram will arrive.

  • It will arrive only once.

  • Datagrams will arrive in order.

  • The receiving application is ready for the incoming rate.

  • The sender will slow down when the network is congested.

Unlike TCP’s byte stream, UDP preserves datagram boundaries. One sent datagram corresponds to one received datagram if it arrives successfully.

But why would anyone choose fewer guarantees than what TCP offers?

Some applications care more about receiving current information quickly than recovering old information. For example, during a live voice call, receiving the latest audio is useful. Receiving a missing audio fragment several seconds later is generally not a good idea. Real-time gaming platforms can have similar requirements for position updates of the players and NPCs.

UDP is also useful as a foundation upon which a more specialized transport layer can be built. QUIC is the most important modern example. We will look at it in a later section.

It might be tempting to say that TCP is slow and UDP is fast. But that’s a little misleading.

While UDP has less built-in mechanisms, an application that needs reliable delivery must recreate many TCP-like mechanisms itself. Poorly implemented UDP systems can be highly unreliable, unfair to network users, or even slower than TCP.

QUIC and HTTP/3

QUIC is a modern transport protocol built on top of UDP. It adds several features to UDP such as reliability, encryption, congestion control, connection management, and multiple independent streams.

The modern HTTP/3 runs over QUIC.

The main reason for QUIC using UDP is partly because operating systems already have support for UDP. This allowed QUIC’s transport-related behavior to evolve without waiting for a new kernel-level transport protocol to be deployed everywhere. Unlike a plain UDP setup, QUIC provides a lot of transport functionality of its own. Also, TLS is integrated into its default connection establishment process.

A major advantage is that QUIC can support multiple streams without forcing all of them through one globally ordered byte stream. Loss affecting one stream doesn’t normally prevent unrelated streams from progressing. This helps it avoid the head-of-line blocking problem that was present in earlier HTTP versions such as HTTP/1.1 and HTTP/2.

QUIC can also allow a connection to survive during network changes. For example, a mobile device suddenly moving from Wi-Fi to mobile data may change its IP address. This is because a TCP connection is closely linked to its network endpoints. However, QUIC has connection identifiers that can handle connection migration.

The seeming advantages of QUIC don’t mean that every application should replace TCP. UDP can also be blocked or handled poorly by some networks. Even HTTP/3 deployments normally retain HTTP/2 fallback paths.

Why Creating A New Connection is Expensive

Consider a service that creates a fresh HTTPS connection for every request. For each operation, it may need to perform the following steps:

  • A DNS lookup.

  • A TCP handshake.

  • A TLS handshake.

  • The actual request and response exchange.

  • Connection shutdown.

We can cache or optimize some of these operations. But the general pattern is such that it creates higher latency and extra resource consumption. Connection setup also uses CPU, memory, file descriptors, ephemeral ports, cryptographic work, and load-balancer state. The solution is to reuse connections instead of eliminating them.

One of the simplest ways to reuse connections is by keeping them alive with the HTTP keep-alive header.

HTTP keep-alive means that several HTTP requests and responses can use the same underlying connection. HTTP/1.1 uses persistent connections by default. Multiple requests can therefore be carried over one connection rather than establishing a new TCP and TLS connection every single time.

Here’s how a simple sequence of events seems:

  • Create TCP connection

  • Perform TLS handshake

  • Send request A

  • Receive response A

  • Send request B

  • Receive response B

  • Send request C

  • Receive response C

  • Close connection later

Reusing connections gets rid of repeated setup costs and allows TCP’s congestion-control state to mature rather than restarting for every request.

Connection Pooling

Connection pooling is the client-side technique of keeping a managed list of reusable connections to a particular destination.

Suppose an application has to repeatedly call a payment service. Instead of creating a new connection every single time, it can maintain a pool of connections. When a new request arrives, the client can borrow an available connection from the pool. When the operation finishes, the connection returns to the pool.

Some points to keep in mind here are as follows:

  • With HTTP/1.1, a connection normally handles one active request-response exchange at a time. Multiple connections permit concurrent requests.

  • With HTTP/2, one connection can carry many concurrent streams. A client may therefore need only one or a small number of connections per destination.

Databases also use connection pools. But a database connection pool is not the same as an HTTP connection pool. A database connection can contain details like the transaction state, session configuration, temporary tables, or even authentication state. HTTP connections, on the other hand, are normally less application-stateful, especially when requests are designed to be stateless.

A connection pool should also be bounded by a specific limit. If an application creates unlimited connections whenever demand rises, it can end up overwhelming the destination. It can also exhaust local sockets, consume all NAT ports, and overload TLS processing.

On the other hand, a bounded pool can create backpressure. Once all connections are busy, new work waits or fails according to a defined policy.

A practical pool commonly needs:

  • Max number of connections.

  • Max number of idle connections.

  • An idle connection timeout.

  • Max connection lifetime.

  • Pool-acquisition timeout.

  • A limit on the number of waiting requests.

A max connection lifetime is useful even when a connection is healthy. Without occasional rotation, long-lived connections can remain attached to old service instances, miss DNS changes, or create uneven load distribution.

HTTP/1.1, HTTP/2, and multiplexing

HTTP/1.1 and HTTP/2 are based on the same broad HTTP concepts: methods, URLs, headers, requests, responses, and status codes. The main difference is in how the messages are transported. Let’s look at both in more detail:

HTTP/1.1

On a particular HTTP/1.1 connection, requests and responses are fundamentally ordered.

HTTP/1.1 introduced the concept of pipelining, where a client could send multiple requests before receiving earlier responses. However, the server still had to return responses in order.

If the first request took 10 seconds and the second took 10 milliseconds, the second response could still be stuck behind the first. This is called application-level head-of-line blocking. Because of this possibility, clients opened several HTTP/1.1 connections to the same server.

HTTP/2 Multiplexing

HTTP/2 divides communication into frames. Frames belong to logical streams, and each request-response exchange uses its own stream.

Frames from several streams can be interleaved on one TCP connection as shown in the diagram below.

A slow application response on one stream cannot prevent another stream from returning its response. This allows many concurrent requests to share one connection. Therefore, HTTP/2 reduces the requirement for many parallel TCP connections. It also compresses HTTP fields and provides stream-level and connection-level flow control.

The Remaining Head-of-Line Problem

Although HTTP/2 streams are logically independent, they still travel through one TCP byte stream.

Suppose one TCP packet is lost. TCP must recover the missing bytes before presenting later bytes to HTTP/2. Those later bytes might contain frames for several unrelated HTTP/2 streams.

Therefore, packet loss can briefly stall every HTTP/2 stream on that TCP connection. While HTTP/2 solves HTTP/1.1’s application-level blocking problem, it doesn’t solve TCP-level head-of-line blocking.

HTTP/3 addresses this by placing HTTP streams on QUIC streams instead of one TCP byte stream. However, even HTTP/3 cannot remove every form of waiting. Streams still share network capacity and congestion-control state. A saturated server, full worker queue, or overloaded database can cause some head-of-line blocking at the application level.

gRPC’s Transport Story

gRPC makes service communication look like calling a typed method within a program. See the diagram below:

A service definition might describe an operation like this:

GetOrder(orderId) → Order

Tools generate client and server code based on this definition. Messages are commonly encoded with Protocol Buffers. Under its standard transport mapping, gRPC normally runs over HTTP/2.

Each gRPC call receives an HTTP/2 stream. The request metadata travels in HTTP headers. The request and response messages travel in HTTP/2 DATA frames. The final gRPC status is carried in trailers.

The HTTP/2 frame boundaries don’t match Protocol Buffer message boundaries. gRPC adds its own length-prefixed message framing to reconstruct messages. gRPC supports four main communication patterns:

  • Unary RPC: The client sends one request and receives one response.

  • Server streaming: The client sends one request and receives a stream of responses.

  • Client streaming: The client sends a stream of messages and receives one response.

  • Bidirectional streaming: Both sides send streams of messages independently.

HTTP/2 is a natural fit for gRPC because one connection can carry many gRPC calls and because each call can have its own stream. However, there is a load-balancing consequence due to this. For example, suppose a gRPC client opens one HTTP/2 connection to an L4 load balancer. Let’s say that the load balancer chooses Server A for that connection. Hundreds of RPC calls may then become streams inside the same connection. However, from the perspective of the L4 load balancer, these are not separate operations. They are traffic within a single connection. All of them remain attached to Server A.

This scenario can result in an uneven distribution even when there are many separate calls. There are different approaches to handle this:

  • The client can perform service discovery and balance calls across multiple connections.

  • An L7 proxy that understands HTTP/2 and gRPC can route individual RPC streams.

  • Connections can be periodically rotated.

  • The client can maintain connections to several backends.

Every gRPC call should also have a deadline. Without one, a caller may end up waiting indefinitely while resources remain occupied.

NAT and Why It Affects Applications

NAT (Network Address Translation) allows several private devices to share one public IP address. Let’s understand how it works:

Suppose a computer has a private address of 192.168.1.20. It connects to a public service from local port 53142. The home router may create a translation such as:

192.168.1.20:53142
        ↓
198.51.100.10:62001

The public server sees 198.51.100.10:62001. When response packets return, the router consults its NAT table and forwards them to 192.168.1.20:53142.

An outbound packet creates a NAT state. Returning response traffic that matches the state can be routed back to the internal device. However, an unsolicited inbound connection usually has no matching mapping. The NAT device has no clue as to which private machine should receive it.

This is the main reason clients usually initiate connections to public servers rather than public servers directly connecting to clients.

Peer-to-peer applications, video calls, and games sometimes use NAT traversal techniques such as STUN, hole punching, or TURN relays. In some situations, direct communication is impossible, making a relay necessary. T

NAT devices cannot retain inactive mappings forever. An idle mapping may be removed.

This matters for WebSockets, gRPC streams, database tunnels, and other long-lived connections. The endpoints may believe that the connection still exists even though an intermediary has forgotten it.

Periodic application heartbeats can keep a mapping active and help discover broken paths. NAT behavior varies, so heartbeats should be configurable rather than based on one assumed universal timeout. The NAT behavioral recommendations explicitly discuss outbound traffic refreshing mappings.

Summary

In this article, we’ve looked at networking in detail. Here are the key learning points in brief:

  • An application request passes through DNS, IP routing, a transport protocol, TLS, a load balancer, and finally the destination service.

  • TCP provides a reliable and ordered stream of bytes, while UDP sends independent datagrams without guaranteeing delivery or arrival order.

  • UDP is not automatically faster than TCP; it is useful when an application prefers timely data or needs custom transport behavior.

  • QUIC builds reliable, encrypted, multiplexed communication over UDP and allows HTTP/3 streams to progress more independently during packet loss.

  • Reusing connections avoids repeated TCP and TLS handshakes, reducing latency, CPU work, socket usage, and pressure on network infrastructure.

  • Connection pools maintain a bounded set of reusable connections and make excess requests wait instead of opening unlimited new connections.

  • HTTP keep-alive, TCP keepalive, and application heartbeats solve different problems and should not be treated as interchangeable mechanisms.

  • HTTP/2 multiplexes many request-response streams over one TCP connection, reducing the need for several parallel connections.

  • HTTP/2 still suffers from TCP-level head-of-line blocking because one lost packet can temporarily stall every stream sharing that connection.

  • gRPC commonly uses HTTP/2, mapping each RPC to a stream, which makes protocol-aware or client-side load balancing important.

  • NAT lets many private devices share one public IP, but its temporary mappings complicate inbound connections, long-lived sessions, identity, and rate limiting.
