Data Movement Strategies In System Design

Software systems don’t keep information in one place all the time. When a user makes a request to the system, it goes from the application to a server. A database might store the records needed to process it. Also, other components may need to know about any changes.

You need to move data to connect all these separate activities so that they can work as a coherent system.

To manage this movement of data, you need to make decisions about when and how information should travel within a system and outside it. This is where you have multiple strategies that can be used to handle data movement. In this article, we’ll look at the key strategies of data movement along with their benefits. Here’s what we will cover:

  • The source, consumer, and trigger of data movement

  • What is the pull approach

  • The polling approach

  • The push approach

  • The long polling approach

  • Continuous communication with SSE and WebSockets

  • The role of message queues

  • Change data capture for database changes

  • How to choose a data movement strategy

The Source, Consumer, and Trigger of Data Movement

Every data movement has a source that has some information and a consumer needing that information. For example, you might have a weather service that has weather information. A weather application is the consumer of this information.

The difference between data movement strategies occurs based on who initiates the movement activity.

First, in pull on demand, the consumer needs some information and makes the call to fetch that information.

Second, in the case of polling, the consumer keeps checking for data by making repeated calls. For example, you might have an application that checks every few seconds for a report to get ready.

Third, in the case of push, the source decides to publish information when there’s a change. For example, you might have a service that sends a notification when a product is dispatched.

As you can see, the data moves from the source to the consumer in all these cases. The difference is mainly about who causes the data movement to happen. One thing you should note here is that these labels apply only to specific interactions within a bigger system. For example, you can have a system receive some data through push. It might store that data and expose it later to another system through pull. You can also have a source system push some data to another component based on a fixed schedule. For example, sending a nightly export.

What is the Pull Approach

In the pull approach, you fetch the information only when there is a reason to use it. Hence the name “pull”.

Let’s say you have an application that has to display an employee’s profile. When a user opens the profile page, the application asks for the relevant data record. The source component responds with the information, and the interaction comes to an end.

As you can see, this is a very simple example of a pull-based request-response communication. The consumer decides what to request and when to request it. The source component doesn’t need to notify every possible consumer whenever there’s a change to the employee details.

The benefit of this approach is that the work is based on demand. If the user doesn’t open a profile, the application does not need to retrieve it. Also, the consumers can ask for only those fields or records that they need. This means no unnecessary data is transferred.

The downside is that the consumer must wait for the request to travel over the network, the source to process that request, and the response to travel back to the caller. If the source is unavailable for some reason, the call can fail. You can use caching to reduce this dependency. But it introduces caching-related challenges.

Also, a pull-based approach has no automatic awareness of later changes. If your profile page has loaded, its contents remain static even if something may have changed in the source. You need to fetch again.

This makes the pull-based approach a great fit for moving data that is useful at specific moments. For example, opening a document. Or searching a catalog. Or fetching a configuration value. Or asking for a page of results.

The Polling Approach

Polling is an extended version of the pull-based approach. In this, the consumer has no idea when something will change. Therefore, it keeps calling the server for the information.

Let’s say you have a service that generates a large report that can be downloaded. When the user makes a request, the service starts the work of generating the report. It also provides a job identifier to the caller. The calling application can then keep checking the status of the task every few seconds. Each of these checks is a pull request. But repeating those requests to find out what has changed makes the overall behavior known as “polling”.

Polling is pretty simple because the source component can just expose a normal endpoint. It doesn’t need to worry about maintaining a connection to the consumer or initiating a callback. It’s the consumer’s responsibility to call the component.

The frequency of these calls creates a direct relationship between freshness and cost. If you check every 10 seconds, a change that takes place immediately after one check remains undiscovered for almost 10 seconds. However, a change that happened immediately before the next check is discovered fairly quickly. If you assume that changes take place uniformly between successful data checks, the average detection delay is approximately half the polling interval.

Polling is a good fit for some situations. For example, let’s say you have a dashboard that needs to be refreshed every minute. Or you have a report that takes several minutes to generate, and you don’t need to check its status every few milliseconds.

The Push Approach

In the push approach, you let the source component initiate the movement of data. The source component knows whenever a change happens because it has made the change itself.

For example, let’s say you have a payment service that records a successful payment. The service can send that information to a registered application endpoint. A webhook can implement this pattern through an HTTP request to the receiving app.

The push approach removes the need to wait for the next scheduled check. You can avoid a large number of requests that would return unchanged information. However, the responsibility moves to a different place. You need the source component to know where to deliver information. Also, you need a process that can handle unavailable destination components and any failed attempts to deliver data.

One important aspect of a push-based approach is that it can deliver data that a consumer doesn’t need. If you have a source component that publishes every small change to 1000s of recipients, it can generate a good amount of traffic. Push can eliminate the delay due to waiting for the consumer’s next check. But it doesn’t get rid of network latency, batching, congestion, or processing queues.

The Long Polling Approach

With long polling, you can make the pull-based approach respond quickly without the need for continuous checks. In ordinary polling, you ask a question and receive an immediate response. Even when there is nothing new.

Long polling changes what the server does when no data is available. When the consumer asks for updates, the server holds the request open. The server returns the data when the information is available. If a waiting limit expires first, the server returns an empty response. The consumer then sends another request.

Let’s say you have a worker waiting for a background task. Instead of asking an empty queue for work again and again, it can leave an outstanding request. The queue answers when a task arrives in its bucket.

Long polling is initiated by the consumer. But in terms of responsiveness, it can look a lot like push because the server can answer a waiting request quite fast. The cost goes from frequent empty requests to maintaining outstanding requests. You still need to manage their timeouts and other connection issues.

Continuous Communication with SSE and WebSockets

As we talked about earlier, long polling completes a response only when data arrives. There’s another approach that keeps a communication channel open so that multiple updates can go through it.

With Server-Sent Events (SSE), your browser can request an event stream over HTTP. The server keeps the response open and sends events through it as they become available. For example, you can have a build dashboard that displays new log entries as and when they are logged. No need to request the entire log again and again.

In SSE, the browser is responsible for initiating the connection. But the server initiates the delivery of subsequent events. At the app level, this is much like server push. The browser’s “EventSource” interface takes care of the reconnection part. It can also send the last event ID when reconnecting.

WebSockets let you communicate in both directions over an already established connection. For example, let’s say you have a collaborative editing application. It can send a user’s changes to the server while receiving other users’ changes through the same connection. You get two-way communication.

As you can see, WebSockets support push from either side. You can also carry application-level request-response messages.

The Role of Message Queues

Message queues and event streams add an intermediary to the data movement approach. This intermediary is known as the message broker. With a message broker, you get another place to put data. It lets production and consumption happen at different times.

For example, let’s say you have an image-upload service that can submit a task to generate a thumbnail to a queue. A worker processes that task when capacity becomes available. If you configure the queue for durability, the task can remain available even when all the workers are offline.

Using a queue doesn’t determine whether data movement uses a push- or pull-based approach. Different providers use different approaches. For example, RabbitMQ has subscriptions through which the broker pushes messages to consumers. In contrast, Kafka has a different approach in which producers push messages to brokers and consumers fetch messages from brokers.

Change Data Capture For Database Changes

CDC identifies changes made to a database so that other systems can react to those changes based on their requirement. For example, let’s say you have a search index that needs to find out when search records are inserted, updated, or deleted.

One approach checks tables repeatedly for changed rows. On the other hand, log-based CDC reads a database’s record of changes. CDC describes how changes are captured. It doesn’t mean that every stage of the pipeline uses push.

How to Choose a Data Movement Method

There are two types of information that are moved: current state and change history. Before choosing a delivery method, you need to understand what the consumer actually needs.

For example, let’s say you have a room-temperature display that needs to only read the latest temperature. If multiple readings arrive before the screen refreshes, you just need to show the newest reading. However, an audit system might have a different requirement. It may need every relevant change. This includes changes that are later reversed.

Suppose you have a resource that is enabled at the first check. Then, it is disabled and enabled again before the second check. If a consumer polls only the current state, it sees “enabled” twice. It won’t have any knowledge of the intermediate transition. If we poll more frequently, we reduce the opportunity to miss a transition. Still, it doesn’t turn current-state sampling into a complete history.

Combining different data movement approaches can sometimes satisfy requirements more effectively.

For example, one useful pattern is to have a push notification followed by pull retrieval. A document service can announce that a document has changed, and interested consumers can fetch its contents.

This way, you can keep notifications small and let consumers decide whether they need the full document or not. However, the subsequent fetch request may return a newer version than the version that triggered the notification. If the exact version is important, the notification should also identify it, and the source component needs to provide a way to fetch that version.

Summary

In this article, we’ve looked at the top data movement strategies in system design. Here are the key learning points in brief:

  • Every data movement has a source that has some information and a consumer needing that information.

  • In the pull approach, you fetch the information only when there is a reason to use it. Hence the name “pull”. The benefit of this approach is that the work is based on demand.

  • Polling is an extended version of the pull-based approach. In this, the consumer has no idea when something will change. Therefore, it keeps calling the server for the information.

  • In the push approach, you let the source component initiate the movement of data. The source component knows whenever a change happens because it has made the change itself.

  • With long polling, you can make the pull-based approach respond quickly without the need for continuous checks.

  • With Server-Sent Events (SSE), your browser can request an event stream over HTTP. The server keeps the response open and sends events through it as they become available.

  • WebSockets let you communicate in both directions over an already established connection.

  • Message queues and event streams add an intermediary to the data movement approach.

  • CDC identifies changes made to a database so that other systems can react to those changes based on their requirement.
