The Read Path versus the Write Path: Strategies and Techniques

Aug 6
∙

Every application built on stored data performs two kinds of operations against it.

A write operation records a fact, such as a new order, a changed email address, or a deleted comment. On the other hand, a read operation answers a question, such as which orders were placed this week or what should appear on a profile page. A single database on modest hardware can handle both types of operations without much trouble, and a developer need not be bothered about which operation is more common in the application’s context.

However, high traffic can change things. Let’s say a page starts to load slowly. A fix is identified, which is creating an index on the column being filtered. Now, several months later, the same page is slow again under higher load. This time the fix is a cache in front of the query. A year after that, the database saturates during peak hours. This time the fix is a read replica with reporting traffic routed to it. In principle, each fix works, but each one is needed at a different time and for a different reason.

Now, let’s assume that a user updates a profile, reloads the page, but still sees the previous value. The bug does not reproduce locally, and it disappears on its own before anyone can investigate its root cause. However, this behavior can be a direct consequence of some of the other fixes. This is because each of the previous fixes placed a copy of some data somewhere other than its source. But the copy is not updated in sync with the source update. In other words, a seemingly simple fix on the read path can impact how things appear to work on the write path.

In this article, we will look at read path and write path operations and techniques in detail. Here’s what we will cover:

  • Why fast reads and correct writes require opposing data structures

  • Precomputation and duplication, the single operation underneath every read optimization

  • Two different definitions of consistency, and the bugs caused by treating them as one

  • Indexes, denormalization, caching, read replicas, materialized views, purpose-built read stores, fan-out on write versus read, and CQRS

  • For each strategy, its sync mechanism, staleness window, and characteristic failure mode

  • Write-heavy systems, where the ratio inverts and the decisions reverse with it.

Read/Write Asymmetry

Most applications serve far more reads than writes. Even a factor of a hundred to one is quite common, and plenty of systems have even greater differences. For example, a profile record might be updated a few times a year while the page built from it is read on every visit. Therefore, sometimes pushing slightly more work to the write operation might result in much greater savings during the read path due to the frequency distribution.

Ultimately, a single layout of data cannot be optimal for both operations, because the properties that make a write correct are the properties that make a read slow.

Consider what a write requires to be correct:

  • One authoritative location for each fact, so there is no ambiguity about the current value.

  • An order of application, so two concurrent updates produce a defined result.

  • Validation of invariants before acknowledgment, so the data never enters a state the application treats as impossible.

  • Coordination, since all of the above depend on agreement about what happened first.

Now consider what a read requires to be fast:

  • The answer already assembled, so responding involves fetching rather than computing.

  • Copies positioned close to the process asking the question, so distance adds little latency.

  • No coordination, since waiting for agreement adds time to every request.

  • The ability to serve many requests in parallel without them affecting each other.

These are not merely different. They are opposed in pairs, with one authoritative copy set against many copies, coordination against its absence, and computation at write time against computation at read time. A layout tuned for one operation is not the best option for the other operation. Also, a typical order record carries both sets of requirements at once, since it must never be charged twice and its history page must render quickly on a phone.

Normalization Tradeoff

Database normalization is usually taught as correctness. It covers third normal form, the removal of redundant data, and the storage of each fact in exactly one location. Presented that way, a normalized schema looks correct, and a denormalized one looks like a compromise made under deadline pressure.

Normalization is an optimization targeting the write path. Storing each fact in one location makes updates cheap and safe, since there is a single row to change and no possibility of two copies holding different values. A customer changes their address: one row is updated, and every reader sees the new value immediately.

The same property makes reads expensive. Producing an answer that spans several facts requires collecting them at query time, so displaying one order might join the order, customer, product, and address rows on every page load. That cost is relocated rather than removed, and at a hundred reads per write it is paid far more often than it is avoided.

Denormalization is the opposite selection on the same axis. Copying the customer name onto the order row makes that read cheap and the write more involved, since the change has to reach every copy. Nothing in the database prevents those copies from disagreeing, so the responsibility moves into application code.

Consistency and Staleness

Storing the same fact in two locations creates the possibility that the two hold different values. In such a case, it becomes difficult to describe the meaning of consistency. It carries two unrelated meanings:

  • The C in ACID refers to invariants. A transaction leaves the database in a valid state, so if a balance cannot go negative, no committed transaction produces one.

  • The C in CAP refers to agreement between copies, meaning every reader observes the same value at the same moment regardless of which copy is reached.

A system can satisfy the first perfectly while serving reads thirty seconds behind, and that is not a defect.

Staleness is the interval during which a copy holds a value different from the source. The interval begins when the source is updated and ends when the copy catches up. Any read request that arrives between these points returns the previous value, which is stale. Tolerance is often set per field rather than per system. For example, a follower count lagging by two minutes is not such a big deal, while an account balance lagging by two minutes during a transfer is a big issue. Both types of scenarios can exist in the same application.

Eventual consistency is a claim about the end of that interval. It stays unbounded unless something bounds it. This is why mean replication lag provides an indication of things, but is also a largely useless number. This is because long tail lag generates the most issues and bug reports in a production system.

Precomputed Copies

Every technique that makes reads faster performs the same operation. It computes an answer before the answer is requested and stores the result in a way that it can be retrieved cheaply. Indexes, denormalized columns, caches, read replicas, materialized views, and search indexes all do this.

None of them eliminates the work. The work moves in time, usually onto the write path or onto a background process running between the write and the read.

This leads to three questions which distinguish one technique from another:

  • Where the copy is stored, meaning how far it sits from the source of truth

  • What mechanism updates it, meaning who or what carries the synchronization obligation

  • How long it is permitted to disagree with the source

Database Indexes

An index is the copy that lives closest to its source. It is maintained by the database inside the same transaction as the write, so the staleness window is effectively zero and a committed write is visible through the index immediately. This is why adding an index rarely registers as a duplication decision, even though it is one.

The trade-off is write amplification. Every insert, update, or delete touches every index on the columns involved, so ten indexes on a wide table turn one row insert into eleven structural updates. Storage grows, and write latency grows with the index count.

Indexes stop being a net gain on tables where writes dominate, which is why some ingestion systems run with minimal indexing on purpose.

Schema Denormalization

Denormalization moves the task of synchronization out of the database and into application code, making it a strategy where the team, rather than the system, keeps copies matched. The copy lives in a second table or column, and application code updates it. The staleness window depends on the code structure, from zero in the same transaction to considerably longer in a background job.

The characteristic failure of this approach is the update anomaly, where one location holds the new value, and another holds the old one, and no constraint in the database prevents it or reports it. Two things about this strategy often get missed:

  • It is a per-field decision rather than a schema-wide position. Most well-built schemas are normalized nearly everywhere, with a few deliberately duplicated fields.

  • The knowledge required to maintain it decays. Every code path that writes the source has to account for every copy. The responsibility is held by people rather than expressed in the schema.

Denormalization stops being useful when the duplicated field changes frequently relative to how often it is read, which happens locally even inside read-heavy systems.

Application Caching

A cache is a copy with no durability, its own lifetime, and no built-in path by which a change at the source gets propagated to it. This last property is where most of the difficulty comes from.

The three common synchronization approaches answer a single question: When does the cost of updating the copy get paid?

  • Cache-aside pays on the first read after a miss, reading from the database and storing the result, with the window lasting until the entry expires.

  • Write-through pays on every write, updating the cache inside the write path, which narrows the window and slows writes.

  • Write-behind pays later, in the background, with writes reaching the cache first, creating a period where acknowledged data exists in one place without durability.

Invalidation has no general solution. Time-based expiry is simple and leaves the entry stale for up to the TTL. On the other hand, explicit invalidation is correct in principle, but fragile in practice, since every code path that writes has to account for every cache entry derived from that data. Versioned keys avoid the correctness problem, but cost more storage.

There is another failure mode with cache. A cache gradually becomes more and more load-bearing. The hit rate sits at ninety-eight percent and the database quietly loses the capacity to serve full traffic. A deployment then clears the cache, and the absorbed traffic arrives at the database within seconds. Also, caching fits poorly when hit rates are low, since the lookup adds latency without avoiding work.

Read Replicas

A read replica is a full copy of the dataset, updated asynchronously from the primary. The copy is a separate instance, the mechanism is the replication stream, and the staleness window is replication lag.

This lag produces the most common user-visible consequence. For example, a user updates their profile, the write commits on the primary, the page reloads, the read is routed to a replica that has not yet applied the change, and the previous value comes back. There are three fixes to solve this issue:

  • Route reads to the primary for a period after a write, which returns read load to it and requires per-user state.

  • Read from the primary for queries known to follow writes, which couples routing to application logic.

  • Carry a version token and wait for a replica that has applied at least that version, which adds latency and state.

Every replica applies every write, so adding replicas multiplies write work rather than dividing it.

Replicas scale read throughput, but do nothing for write throughput. Therefore, past the point where writes alone saturate a single node, they contribute nothing. The remaining option is partitioning, which splits the data across nodes and is a separate axis. Replication lag is also largest under heavy write load, which usually coincides with peak read traffic.

Materialized Views

A materialized view is a stored result of a query, refreshed on a defined schedule. Compared with a cache, the staleness window is a predetermined number rather than a random property that emerged from traffic. The copy lives in a table, a refresh process updates it, and the window equals the refresh interval.

Choosing the right refresh strategy is the main decision:

  • A full refresh recomputes the entire result. It is simple and expensive to run, which pushes the interval longer and the window wider.

  • An incremental refresh applies only the changes since the last run. It is much cheaper per run and harder to get right, since the logic determining which rows changed has to handle deletes, out-of-order updates, and partial failures.

Materialized views stop making sense when the refresh cost approaches the cost of the query itself, or when required freshness is shorter than a refresh takes.

Specialized Read Stores

Some queries require a physical structure a transactional database does not provide. For example, full-text search, aggregation across hundreds of millions of rows, and traversal of relationships several levels deep each call for a different structure. In such a case, the copy lives in a separate system.

The cost is the creation of such a system, the pipeline feeding it, and the failure modes of the pipeline. Three sync mechanisms are in common use to maintain such a setup:

  • Dual-write has the application write to both stores. It is simple, but it drifts, since a failure on the second write leaves the two permanently out of agreement.

  • Change data capture reads the replication log and applies changes downstream. It is reliable, and it couples the pipeline to the storage engine’s internal format.

  • The transactional outbox writes the change and an event record in one transaction, after which a separate process publishes the event. It is correct, and it adds moving parts.

Silent drift is the characteristic failure. The index falls behind or misses records, no error is raised, and incomplete results look exactly like ordinary ones. Data warehouses are the oldest instance of this pattern, predating most of the other strategies by decades.

Fan-Out Strategies

Fan-out demonstrates that the correct strategy can differ between rows in one table. Consider a timeline built from posts by accounts a person follows:

  • Fan-out on write copies each new post into a stored timeline for every follower as it is published, so the read becomes a single sequential fetch.

  • Fan-out on read stores the post once and assembles each timeline at query time from every followed account.

For an account with a few hundred followers, fan-out on write wins by a wide margin. One post produces a few hundred small writes and every later read is cheap. For an account with ten million followers, the same post produces ten million writes and the write path stalls.

Production systems generally run both. Most accounts are fanned out on write. However, high-follower accounts are stored once, and a timeline merges the precomputed portion with the few accounts handled at read time. The decision is made per account rather than per feature.

Command Query Separation

CQRS, short for Command Query Responsibility Segregation, is the formalization of everything above.

Instead of one model serving both operations, the system runs two. One handles commands, which change state, and the other handles queries, kept in agreement by one of the mechanisms already described.

To make things clear, CQRS does not require event sourcing. Neither does it require two databases, since both models can live inside one.

The cost is that two models have to be kept coherent, and the staleness between them becomes visible to the users. For example, a user who submits a form and does not see the result on the next page is encountering an architectural decision.

Write-Heavy Systems

Some systems invert the read-write ratio completely. Instead of fewer writes and more reads, we have fewer reads and more writes. For example, metrics collection, application logging, event ingestion, and device telemetry take in a continuous volume of writes while serving few reads. Those reads are usually aggregates over a time range rather than lookups of individual records.

Here are a few key distinguishing elements of such a system:

  • Indexing is kept minimal, since index maintenance on every write becomes the dominant cost.

  • Storage is append-only, since appending is far cheaper than updating in place.

  • Sorting and merging happen during background compaction rather than at write time.

  • Read latency unacceptable in an application database is tolerated, since reads are infrequent and usually serve dashboards.

The same divergence appears inside the storage engine. For example, a B-tree keeps data sorted and balanced by updating pages in place, which turns a read into a short traversal and a write into real structural work, including occasional page splits. In contrast, an LSM-tree appends writes sequentially to an in-memory structure flushed to disk periodically, which makes writes fast and makes reads consult several locations, since a key might sit in memory or in any of several files.

Summary

In this article, we’ve looked at read-heavy and write-heavy systems in detail along with their strategies. Here are the key learning points in brief:

  • Most applications serve far more reads than writes, often by a hundred to one, though the ratio varies by table and is measured rather than assumed.

  • The properties that make a write correct are the ones that make a read slow, so no single layout serves both.

  • Normalization is a write-path optimization. Storing each fact once makes updates safe and reads expensive for the same reason.

  • Consistency means two unrelated things. In ACID, invariants hold after a transaction. In CAP, all readers see the same value at once.

  • Staleness is the interval during which a copy holds a value its source no longer holds, with tolerance set per field.

  • Every read optimization computes an answer in advance and stores a duplicate, relocating work onto the write path rather than removing it.

  • Strategies differ along three dimensions, namely where the copy lives, what updates it, and how long it may disagree.

  • Read speed is paid for on the write path, since ten indexes turn one insert into eleven structural updates.

  • Read replicas scale read throughput only, since every replica applies every write. Once writes saturate one node, only partitioning remains.

  • Fan-out shows the right choice can differ per row, with most accounts served on write and large accounts on read.

  • When the ratio inverts, as in logging and metrics ingestion, every decision reverses, confirming these are trades rather than rules.
