Background Work: From Cron Jobs to Distributed Systems

Consider what can happen when someone uploads a profile photo to a web application.

Depending on the use case, the application may resize the image into different sizes. It might run the image through a content check process. It can also push the resized images to a content delivery network for faster access. Lastly, it will also update the user record with the latest metadata. Now, imagine if all of these operations take place during the same picture upload request path. As all of these functionalities are carried out, the user sees a spinning button for several seconds, wondering whether the photo has been uploaded successfully. Needless to say, it would be a pretty poor user experience.

If we move all of that extra work outside the request path, the upload can more or less respond immediately as soon as the image file is stored in an object storage. The image still gets resized, scanned, and distributed, just not in the same flow. This is known as background work, and here are some examples of why it is needed:

  • A user action may have triggered it. For example, someone signs up, and a welcome email goes out.

  • The clock may have triggered it. For example, nightly reports, monthly invoices, hourly cache refreshes.

  • Another system could have triggered it. For example, a webhook arrives, or a file is stored in object storage.

  • Perhaps the sheer volume of work made it worthwhile. For example, some work is naturally cheaper or safer done a thousand items at a time.

Most of the time, teams start with a single scheduled script on a single machine. It can handle a great amount of background work. However, as the system gets bigger and more complex, the amount of background work requires different strategies. In this article, we will look at various such strategies to perform background work in detail.

Why Normal Requests Don’t Work Everywhere

The simplest setup places all functionalities inside the request path. For example, a user clicks a button, the server performs all the work, and then it responds.

For most operations, this is the right approach. Shifting functionality to a queue-based asynchronous system when a direct database write would be enough adds more moving parts and increases the chances of failure. However, there are four places where the normal request-response approach breaks down or does not suit well:

  • Time limits are enforced by uncontrolled infrastructure. For example, load balancers, API gateways, and browsers can cut off requests that run too long. When that limit fires, the client receives a gateway timeout even though the work may have completed successfully, so the client and the server now disagree about what happened.

  • Third-party dependencies set the pace. For example, if a payment provider takes eight seconds to respond, the web server holds a connection and a thread open for eight seconds. Therefore, capacity is now determined by someone else’s latency.

  • Heavy work starves everything around it. A video transcode inside a web process consumes CPU that every other request on that machine needs.

  • Some work has nobody waiting on it. A nightly report has no request to attach to, so there is no natural place for it in a request and response model. Related to this, some work has to happen even if the user leaves the session. For example, closing a browser tab should not cancel an export that the user already paid for.

To put it simply, background work separates the execution of the process from the request. However, a foreground failure can result in an annoyed user within seconds, but a background failure can fail silently, and no one knows that something went wrong.

The Guarantees Provided by a Cron Job

The usual starting point for most setups to get into asynchronous background work is a scheduled script on one machine. This setup involves a single line in a configuration file, a script, and a single server.

The guarantee is that a scheduled script starts a command at the specified time, provided the machine is running, the daemon is running, the clock is correct, and the entry still exists.

However, it provides no notion of whether the command finished, whether it succeeded, whether it ran once or twice, or whether anyone should be told it never ran. This difference between “started” and “completed successfully” is where most scheduled-job incidents live.

Time also causes a second category of problem. Common implementations on Linux treat local clock changes of less than three hours as a special case, so when the clock moves forward, jobs that would have run during the skipped hour run immediately afterwards. This handling applies only to jobs scheduled at a specific time with a granularity coarser than an hour, so jobs using wildcards can genuinely run twice during a fall-back transition. Daylight saving is therefore handled for some job types, on some implementations, but not for others. This explains why mature teams run servers in UTC and convert time zones in application code.

Then there is also the question of missed schedules. Suppose an hourly job exists and the machine is down from one in the morning until five. On recovery, should all four missed runs execute, should one execute, or should all be skipped? A basic scheduled script skips them without sending any notifications.

Cron on Multiple Servers

Adding a second server for redundancy seems like an obvious improvement to the single machine setup. However, in this case, if the scheduling configuration is not properly handled, the same job can run simultaneously on two machines.

The straightforward fix for this is using a distributed lock. Each instance tries to acquire a shared lock before running, and whichever one loses backs off and exits. This works most of the time, but there is some chance of failure as well.

Locks carry a time-to-live. This is because a lock without an expiry can turn into a permanent outage when a machine dies while holding it. However, this expiry also creates the problem. A process can pause at any moment for an arbitrary length of time, whether from garbage collection, CPU throttling, or a long network delay. If the pause outlasts the expiry, a second machine legitimately acquires the lock and starts working, while the first resumes, assuming that it still holds the lock.

This is not an implementation bug as such, and it applies to any system where clients can pause. One fix is that the lock service issues a number that increases with every grant, so that the protected resource can reject any write carrying a stale number. However, it requires the downstream resource to participate, which rules it out for an external provider.

Leader election is the other standard approach, where one machine is designated as the primary and the rest of the machines stand by.

Production implementations run several scheduler replicas that use a consensus algorithm to agree on the current leader, with failure detection and re-election targeted to complete inside a minute. Even that does not fully close the gap, because a leader can crash partway through launching a job, after the launch started but before anyone recorded that it completed.

Recovering correctly in such a scenario requires either that every operation on external systems is safe to perform again, or that the state of every operation can be looked up to determine whether it finished. So even with consensus algorithms, the jobs themselves still need to be designed in a way that they are safe to run more than once.

In a nutshell, no arrangement of servers running scheduled scripts satisfies both “runs even when a machine dies” and “runs exactly once.” Typically, teams that operate at scale prefer to skip a run rather than risk a double run. This is because a cleanup job that runs every five minutes can miss one without a lot of problems, whereas undoing a newsletter sent twice to a large list can be difficult or even impossible.

Schedulers and Execution State

At this level, two things change.

The first involves replacing the basic scheduled script with something that can store state. In this approach, a scheduler has the following features:

  • It records every execution along with its outcome

  • It retries failures according to a policy

  • It answers the missed-schedule question explicitly

  • It lives in version control rather than in one machine’s configuration file.

  • It also forces a decision about what happens when a run is due while the previous one is still going. The options are to allow the overlap, skip the new run, or terminate the running one.

The second change is even more important. The scheduler does not perform the work, and its only responsibility is to determine when work should start. It enqueues a request, and some other component picks that request up and executes it.

This resolves the problem we came across in the earlier section. Several scheduler replicas can coordinate on when to start work while a separate pool of workers handles the actual execution.

Three distinct roles emerge in this particular setup:

  • A broker moves messages between processes. Its concerns are transport, delivery, and acknowledgement.

  • A scheduler determines when work starts. Its concerns are time and triggers.

  • A job system manages the lifecycle of a unit of work, meaning retries, status, results, and failure handling.

These roles could be performed by one product offering all features or different products for each functionality. A job system built on an ordinary database table is as legitimate as one built using a message broker. Relational databases offer row-locking primitives that let multiple workers claim rows without interfering with each other, which is enough to build a queue system.

Queues and Workers

In this setup, producers add work items to a queue, the queue holds them, and a pool of workers pulls items off and processes them. Scaling means adding workers. Producers and consumers no longer need to be available at the same moment, nor run at the same speed. Therefore, a traffic spike accumulates in the queue instead of failing.

Some terminologies related to this type of setup can be a source of confusion, but they can be understood based on how much state each layer stores on the application’s behalf:

  • A queue stores one fact per item, which is whether it is pending, in flight, or done. Once the item completes, that record disappears.

  • A job store stores a queryable row per job with an identifier, a status, a result, and timestamps. This becomes necessary the moment a support agent needs to answer what happened to a specific customer’s export request.

  • A workflow engine retains the complete execution history of a multi-step process. We will cover it in a later section.

Job payloads should carry identifiers rather than whole objects. Data and payload can become stale by the time the job runs. Using an identifier forces a fresh read and removes the chance of stale data. Also, size limits are lower than expected, since managed queue services commonly cap a message at a few hundred kilobytes.

The Handoff Problem

To understand the handoff problem, let us consider a simple example. An order gets saved to the database, and then a job gets enqueued to process it. These are two separate systems with two separate writes. No shared transaction exists between them. This is the dual-write problem, and it can result in three distinct failures:

  • The database commit succeeds, but the enqueue fails. This leaves an order that will never be processed. Since it does not give any warning, this failure is quite expensive because the customer made the payment and nothing happened after that.

  • The reverse can also happen. The enqueue succeeds, and the transaction rolls back, leaving a job that references a row that does not exist.

  • The third case is more subtle. The enqueue succeeds, but a worker picks the job up before the transaction is committed. Therefore, the job queries for the order and finds nothing. Depending on the framework and connection handling, the commit may simply not have landed by the time a fast worker starts executing.

Distributed transactions across both systems would solve this in theory, but most modern brokers do not support the required protocol. The pattern that is mostly used to handle this is known as the transactional outbox pattern.

In this pattern, instead of writing to the database and the queue separately, the application writes the business row and a second row describing the job into a dedicated table. Both writes are done inside the same database transaction. In other words, either both writes are committed, or both get rolled back, since they are in the same database. A separate relay process then reads unpublished rows from that table and publishes them to the queue, marking them sent afterwards.

The relay is basically a new process to deploy and monitor. If it stops, everything still commits correctly, but nothing gets enqueued. Interestingly, the relay can publish a message and then fail before marking the row as sent. On restart, it publishes the same message again. In other words, the outbox pattern guarantees that nothing gets lost, but some messages can get delivered more than once. This is much better than the data getting lost completely.

Leases and Delivery Guarantees

To understand why duplicates happen, let us look at how a worker actually claims a job.

A worker receiving an item does not delete it from the queue. The item stays where it is but becomes invisible to other workers for a fixed period. The common default for this period is around 30 seconds. If the worker finishes and acknowledges the item before that window closes, the item is removed. If the worker dies before acknowledging, the window expires, and another worker picks it up. In this way, the system survives worker crashes without human intervention.

Now consider the case where the worker has not died but is merely slow. Processing takes ninety seconds against a thirty-second window. In such a case, the item becomes visible again at the 30-second mark. A second worker claims it, and two workers are now processing the same item concurrently.

There is no way to distinguish a dead worker from a slow one. Both look identical from outside because both rely on an absence of acknowledgement to make the distinction. A mechanism capable of recovering work from crashed workers will therefore sometimes duplicate work from slow ones.

This results in three delivery semantics:

  • At-most-once acknowledges the item first and then performs the work. A crash during the work loses it permanently.

  • At-least-once performs the work first and acknowledges afterwards. A crash between the two repeats the work.

  • Exactly-once is not achievable end to end.

The reason exactly-once is so tough to deliver is that the actual work and the acknowledgement are two separate operations. A crash can happen between them regardless of which order they occur in. No arrangement of two non-atomic operations survives a crash at an arbitrary point.

This is the reason why service providers instruct applications to be capable of processing a particular message more than once.

Designing for Idempotency

Let us understand what designing for idempotency means in principle.

A job is considered idempotent when it can safely run multiple times with the same arguments, but the application-level side effects happen only once. In other words, a second run should not produce any additional effect. This does not mean that the job cannot run twice. It means running twice causes no further damage.

Four specific mechanisms help achieve this:

  • Prefer naturally repeatable operations. For example, setting a value is safe to repeat, whereas incrementing a counter is not. Writing status = ‘shipped’ produces the same result on the fifth run as on the first, while count = count + 1 does not.

  • Use idempotency keys. A unique identifier is generated for each logical operation and written to a deduplication table protected by a unique constraint. This way the second attempt fails its insert and exits cleanly. It’s important to note that the key identifies an operation rather than an attempt. One key is generated when the logical action begins and reused across every retry. Generating a fresh key per retry defeats the purpose of idempotency key entirely, because each attempt then looks like a brand new operation.

  • Use conditional state transitions. Writing UPDATE invoices SET status=’sent’ WHERE id=? AND status=’pending’ and checking the affected row count is often the cheapest option, because it requires no additional table. Zero rows affected means someone else already handled it.

  • Push the problem downstream where possible. Many payment and messaging providers accept an idempotency key and deduplicate on their side

There are two additional considerations to keep in mind:

  • A job that performs two actions is rarely safe in a uniform manner. Consider a job that charges a card and then emails a receipt. The charge process might be protected by the provider’s idempotency key while the email is not. In this case, a retry after a partial failure will send a second receipt for the same charge. The solution is to either split the job into two, or record progress between the steps.

  • Deduplication records also have a lifetime, which needs to outlast the retry window. A key retained for one hour against a job that retries for twenty-four hours provides no protection for twenty-three of them.

Retries and Dead Letters

With the ability to handle duplicates, retries become useful rather than problematic.

However, the first decision to be taken is what to retry. Network timeouts, connection resets, rate-limit responses, and database deadlocks are transient and worth retrying. On the other hand, validation errors, malformed payloads, and permission failures will fail identically on every attempt while wasting capacity.

Backoff and jitter are the next consideration. Capped exponential backoff reduces client work only slightly under contention. This is because the calls still arrive in clusters. Every client computes the same delay and waits the same amount of time, so backoff only reduces how often clients compete without reducing how many compete in each round.

Adding randomness to the delay fixes the problem. Spreading each client’s retry across a random interval turns the clustered spikes into a roughly constant rate. In a scenario with a hundred contending clients, this cuts the total number of calls by more than half.

Retry budgets help cap the damage. A limit on attempts, on total elapsed time, or on both prevents a permanently failing job from retrying forever. This matters most for poison messages, meaning jobs that fail deterministically because of bad data or a reference to a deleted record. Without a budget, these messages can occupy a worker slot on every cycle indefinitely.

The best approach is to retry these messages a few times based on the retry budget and then put them elsewhere for further analysis. This is where dead letter queues come into the picture.

This mechanism only helps when the queue has a named owning team, an alert on depth, and a documented replay path for pushing messages back through after the underlying problem is fixed. A dead letter queue that is not monitored merely produces false confidence without any safety.

Priority and Fairness

These two get treated as one problem and solved with one mechanism, which is why systems that handle priority well can still deliver terrible experiences.

Priority concerns importance. For example, a password reset going out ahead of a marketing newsletter.

On the other hand, fairness concerns share, meaning no single source should monopolise capacity regardless of how important its work is.

To understand things better, let us consider another example. One customer enqueues four million jobs, all of them perfectly ordinary priority. In this case, the priority logic has no role because there is nothing unusual about any individual job.

Priority gets implemented in two ways:

  • Strict ordering drains queues in a declared sequence, touching a lower queue only when every higher one is empty.

  • Weighted polling assigns each queue a weight that determines the probability of the next item coming from it. For example, weights of two and one produce roughly a two-thirds and one-third split.

Strict ordering has a failure mode called starvation, where low-priority work does not execute during busy periods. The classic remedy is aging, which means a job’s effective priority rises the longer it waits. A second failure mode exists, since strict priority breaks down when the low-priority queue contains long jobs. A worker that picks up a two-hour low-priority job cannot touch critical work for two hours regardless of queue ordering. This is because priority only governs what gets picked next rather than what is already running.

Separate queues usually work better than a priority field on a single queue, because each can be scaled, monitored, and alerted on independently. The trade-off is that polling many queues creates additional load on the backing store.

Fairness comes down to preventing any one source from consuming everything. Here are a few strategies to support fairness:

  • Separate queues per tenant work when there are few tenants, but this approach is not scalable when there are many.

  • Shuffle sharding uses a fixed number of queues and hashes each tenant to a small subset. This way one tenant’s burst affects only the few sharing its shard.

  • Concurrency caps per tenant limit how many workers any single source can occupy at once. Excess traffic above a throttle can be routed to a spillover queue.

  • Sidelining old traffic checks the age of each item on dequeue and moves aged items into a backlog queue worked only after the live queue is current.

That last approach of sidelining might seem because FIFO feels obviously fair. However, under a large backlog, FIFO often produces the worst outcome. Customers facing a delay generally prefer their fresh data processed immediately, with whatever accumulated during the incident handled as capacity frees up. Processing a two-hour-old backlog in strict order means every new item waits behind work that may no longer matter to anyone.

Long Jobs and Short Jobs

The meaningful difference between long and short work concerns the cost of failure rather than the duration itself.

A short job that fails costs nothing to redo, whereas a 4-hour job that fails at the 230th minute costs four hours of wall time, four hours of compute spend, and whatever downstream deadline depended on it.

There are four problems when we mix the two of them:

  • Head-of-line blocking means one video encode stalls a thousand emails queued behind it. Those emails are not slow, but they are waiting. The queue’s overall latency ends up being determined by its longest job.

  • Heartbeats become mandatory. Without them, the lease mechanism from earlier treats a long-running worker as dead and hands its job to someone else while it is still working. The standard approach sets the visibility window above normal processing time and extends it periodically while work continues.

  • Deploys turn into scheduling problems. Container orchestrators typically send a termination signal and then wait a grace period before forcibly killing the process.

  • Checkpointing changes what a retry means. Without it, a failed attempt restarts from the beginning, whereas a job that records progress as it goes can resume from the last recorded point. This matters for more than saving time. If the first step triggers an irreversible external action and the second step waits for it to complete, checkpointing lets a retry skip straight to waiting instead of triggering the action a second time.

Splitting long work into smaller units addresses several of these at once. But once a job records checkpoints, tracks which steps have completed, resumes after a crash, and sends heartbeats to prove it is alive, it starts looking more like a workflow engine.

Durable Execution

Some type of work is not a task at all but a kind of process. For example, charging the card, waiting for warehouse confirmation, waiting up to thirty days for the return window to close, and issuing a refund if the item comes back.

The queue model does not handle this well enough, because the process holds state between steps. It can span weeks, survive multiple deployments, and can fail at a specific step with earlier steps already committed.

Durable execution is the category of system built for such a type of work.

However, even for such a setup, the application code may look entirely ordinary and sequential. Behind it, the engine records the result of every completed step into an append-only log, generally called an event history.

When the process crashes or a worker restarts, the engine replays that history. The function runs again from the top, but every step that already has a recorded result returns the recorded value immediately rather than executing the step again. The code fast-forwards through everything already done and resumes at the first step with no recorded result. While the process waits, nothing runs at all, since the waiting process exists only as rows in a log.

Replay is routine stuff rather than an exceptional situation. Engines cache in-memory state and rebuild it by replaying whenever the cache gets evicted. This is why the constraints imposed by replay are not edge cases.

The first is determinism. Process-level code must produce the same sequence of decisions every time it replays. This rules out operations like reading the current time, generating random numbers, making direct network calls, and iterating over unordered collections. The workflow engines supply deterministic substitutes for time and randomness. Everything unpredictable is moved into separate units. So the process code must be deterministic while the application as a whole does not have to be.

The second constraint is versioning. For example, a process that started in January may still be running when new code deploys in March. Hence, the duration of the longest-running process becomes a code-compatibility window that has to be managed.

The third is that the need for idempotency does not go away, because activities still get retried and still need to be safe to repeat.

One open question around workflows is what to do when a particular step fails, and the previous steps are already committed. The answer is a compensating action, which is basically a new forward operation that logically cancels the earlier one. For example, charging a card cannot be reversed by deleting a row, so the compensation is a refund. This approach is different from a database rollback because between the original action and its compensation, other parts of the system can observe the intermediate state and act upon it.

Summary

In this article, we’ve looked at the progression of background work from simple cron jobs all the way to distributed workflow engines. Here are the key learning points in brief:

  • A basic scheduled script guarantees a start with no execution history, no retries, and no way to report that it never ran.

  • Running the same schedule on multiple servers trades a single point of failure for duplicate execution. Locks reduce the odds of this duplicate execution without eliminating them.

  • Separating the decision of when work runs from the execution of that work is what allows each part to scale and fail independently.

  • Writing to a database and enqueueing a job are two operations that can fail independently. The outbox pattern brings them into one at the cost of having duplicates.

  • Idempotency is a design decision made per job, using an idempotency key, a conditional state transition, or an operation that is naturally repeatable.

  • Retries need error classification, randomised backoff, a budget, and a dead letter queue with clear ownership. Priority concerns which work matters more, while fairness concerns whether one source can consume everything.

  • A scheduled script remains a perfectly good answer when the job is safe to repeat, when a missed run is tolerable, and when someone would notice within a day.

  • A queue earns its complexity when retries, per-job visibility, or independent scaling become necessary.

  • A workflow engine earns its considerably larger complexity when the unit of work is a multi-step process holding state across days and failures.
