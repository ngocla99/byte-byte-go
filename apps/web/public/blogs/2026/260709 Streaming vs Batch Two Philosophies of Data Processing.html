Streaming vs Batch: Two Philosophies of Data Processing

Every system that processes data eventually has to answer one question. When is the data complete enough to be moved to the compute stage?

A program adding up a day’s sales needs to know whether all of today’s sales have actually arrived. For data stored in a file, the answer is trivial because the file has an end. However, for data that arrives continuously and never stops, there is no clean answer, and how a system resolves that gap is the difference between batch processing and streaming.

Batch processing waits for completeness. It collects data up to a natural boundary, a closing time, or a finished file, and then computes over the whole set at once. Streaming prioritizes completeness for speed. It produces answers continuously from data that is still arriving, which means it has to estimate when enough data has come in and handle the cases where that estimate is wrong. This trade-off between completeness and latency is the key consideration when dealing with streaming and batch.

In this article, we will cover the strategies on each side and what each one costs.

  • On the batch side, that means full and incremental loads and large-window aggregation, with micro-batch sitting in between.

  • On the streaming side, the territory runs through tumbling, sliding, and session windows, watermarks and late data, the lambda and kappa architectures, and the often-misunderstood meaning of exactly-once processing.

Boundaries

Let us start with what makes batch relatively easier.

A batch job runs over bounded data, which is just data with a definite end. For example, a file has a last line that signifies its end. Yesterday’s orders stop at midnight. Since the set is finite and closed, a job can read all of it, compute over the whole thing, and produce an answer that will not change, since there is nothing left to add.

Streaming works on unbounded data, a feed that has no end built into it. For example, card payments, clicks on a page, sensor readings, all of it keeps coming with no final record announcing the day is done. Waiting for the whole set is no longer an option, because the whole set never exists at once.

This is where completeness and latency first pull apart.

Bounded data lets a system have both full completeness and an acceptable wait, because the wait ends on its own. Unbounded data forces a choice, since the only path to completeness is to wait forever.

One more thing matters here and pays off later. The moment an event happens and the moment a system receives it are not the same, and on an endless feed, that gap can turn into a significant problem.

Batch

The simplest way to use a boundary is to wait for it and process everything. This is a full load, where each run reads the entire dataset from scratch and builds the result. The appeal is that it is hard to get wrong. If last week’s numbers were off, the next run corrects them automatically, because it recomputes from the source every time. The drawback shows up as the data grows, since reprocessing a year of records to add one day of changes is slow and expensive, and that cost returns on every run.

Incremental load fixes that by processing only what has changed since the last run. Instead of rebuilding from zero, it appends or updates just the new records, which is far cheaper at scale.

The trade-off is in terms of complexity. The job now has to track what it already saw, and corrections to old data can become tricky, since a record that changed last month will not appear among today’s new rows.

A third pattern is big-window aggregation, rolling many records up into summaries over long spans such as a day or a month. These rollups are accurate and cheap to query later, at the cost of freshness, because a daily summary says nothing about the last hour.

All three share one bargain. By waiting for a boundary, batch becomes simple, repeatable, and easy to reason about. What it gives up is time. Every answer describes the last run, not the present moment, which is exactly why fraud systems and live dashboards cannot run on batch alone.

Micro-batch

The usual complaint about batch is latency, and the first fix is obvious. Why not run the batch process more often? For example, push the schedule from once a day to once a minute, and the results start to feel almost live. Taken to its natural end, this becomes a micro-batch, where the incoming feed is chopped into small fixed intervals, and each interval is processed as its own tiny batch.

Micro-batch is a middle ground between batch and streaming. It keeps the batch model, finite chunks processed to completion, so the simplicity survives. What it adds is freshness, results that lag by seconds or a minute rather than a day. For many systems that claim to need real-time, this is quite sufficient.

The tradeoff is that the latency can never drop below the length of an interval, so a system tuned for one-minute batches cannot answer in one second, no matter what. Running many small jobs also carries overhead that a few large jobs avoid.

Lastly, micro-batch buys most of streaming’s freshness for a fraction of its difficulty, right up until something truly needs sub-second response.

Streaming

Removing the wait entirely gives us true streaming, where each event is handled the moment it arrives rather than gathered into any batch at all.

Every event has two timestamps. There is event time, when the thing actually happened, and processing time, when the system received it. In an ideal scenario, these would match. In a real one, they drift apart because network delays happen all the time. Often, events can arrive out of order, and some arrive well after the moment they describe.

The naive approach is to ignore the difference and use processing time, bucketing events by when they showed up. It might work for demonstration purposes, but it fails in real production scenarios. An event that happened at 8:59 but arrived at 9:01 gets counted in the wrong minute, which can have a big potential impact.

So what is the alternative?

One approach is to group events by event time, which is the moment they truly happened. This keeps the numbers correct. That choice is the right one, but it creates another problem. If events are grouped by when they happened, and some of them arrive late, how does a system ever know it has seen them all?

Windows

The question posed in the previous section brings the concept of windows to the front.

A window is a slice or a bounded chunk of the endless feed so that an aggregate, like a count or an average, has something finite to run on. Without windows, there is no per-minute count, because the stream never ends, and the count would never close. There are three common ways to cut the feed:

  • Tumbling Windows: They are fixed in size and do not overlap, so every event falls into exactly one window. A count of orders for each ten-minute block is a tumbling window. They are simple and cheap, and their weakness sits at the edges, because a burst that straddles a boundary gets split across two windows and can look smaller than it was.

  • Sliding Windows: They are also fixed in size, but they overlap, advancing by a small step. A rolling average of latency over the last five minutes, refreshed every minute, is a sliding window. The overlap gives a smooth, continuous view, which is exactly what trend lines and moving averages need. The cost is that each event lands in several windows at once, so both the compute and the stored state go up.

  • Session Window: This type has no fixed size at all. They group events separated by gaps shorter than a chosen timeout, then close once activity stops. A single user’s burst of clicks before they go idle is a session. This adapts naturally to real behavior, which makes it ideal for anything user-centric, though the windows are dynamic, harder to manage, and dependent on picking a sensible gap.

The takeaway across all three is the same. Windowing is a decision about how to slice time, and different slices produce different truths from identical data.

Watermarks

A window still needs to know when to close. On a feed where events can arrive late, a system cannot wait forever, so it makes an educated guess called a watermark.

A watermark is the system’s estimate that it has probably seen every event up to a certain point in event time, which is the signal a window uses to decide it is done and emit a result.

The important point here is that it is an estimate. A watermark is a bet, not a fact, and like any bet, it can be wrong. When an event shows up after its window’s watermark has already passed, that is late data, an event that arrived after the system had decided it was finished waiting. Late data is not a rare bug. It is the unavoidable consequence of having guessed when to stop.

There are a few ways to handle stragglers.

  • The simplest is to drop late events, accepting small inaccuracies for low latency.

  • A more forgiving option holds windows open a little longer with an allowance for lateness, then updates the result when a straggler arrives, trading some speed for accuracy.

The most thorough option routes late data to a separate correction path that fixes the record after the fact. A long wait makes results more complete but slower. A short wait makes them faster, but needs more corrections.

Exactly-Once

One idea in streaming gets misunderstood more often than any other. The phrase is exactly-once, and it is often considered as a promise that every message reaches the system a single time. But this can be a little misleading since it is not something that comes for free.

Underneath almost every streaming system, delivery is at-least-once, which means a message can be sent more than once. If a machine fails after receiving an event but before confirming it, the event gets resent, and duplicates appear. A system cannot reliably prevent these duplicates.

Exactly-once handles them by making them harmless. The processing is built to be idempotent, meaning applying the same event twice produces the same outcome as applying it once, so a duplicate changes nothing. A payment recorded under a unique transaction ID will not be counted a second time, even if its event arrives twice.

There is a sharp limit here. This guarantee holds inside the processing system and ends the moment a result crosses into an external database, an email service, or any outside system. Past that boundary, making writes idempotent becomes the caller’s responsibility again.

Architectures

Windows, watermarks, and exactly-once each solve a single problem. Combining them into a full system raises a larger question.

Should a pipeline run streaming alone, or run batch and streaming together?

Two well-known answers, lambda and kappa, take opposite positions.

Lambda architecture runs two layers side by side. A batch layer reprocesses all the data slowly and produces accurate results, while a speed layer handles recent events with low latency, and the two merge when someone reads the output. The strength is that the batch layer acts as a dependable source of truth, and reprocessing history is straightforward. The weakness is duplication. The same business logic has to be written and maintained twice, once for batch and once for streaming, in two different systems that tend to drift apart and disagree.

Kappa architecture removes the batch layer. There is a single streaming path, and when reprocessing is needed, the system replays the stored event log from the beginning through the same streaming code. The strength is one codebase and one mental model, with nothing to keep in sync. The weakness is that replaying a long history through a streaming system can be slow and expensive, and not every computation expresses naturally as a stream.

Selection

With the strategies laid out, the practical question is which to use in a given situation.

The first thing to ask is how fast a result loses value. A fraud decision is worthless an hour later, which calls for streaming. A monthly invoice is fine the morning after the month closes, which is batch territory.

The second thing to ask is whether a provisional answer that gets corrected later is acceptable, since streaming trades a final number for a fast one, while batch hands back a settled number after a wait.

Each approach has a point where it stops making sense. Batch breaks down when tomorrow is too late to act. Streaming breaks down when completeness cannot be negotiated, such as a financial close where being approximately right is not allowed, or when large reprocessing happens often enough to make streaming-only painful.

The cost runs against intuition. Streaming is always on, paying for a running system around the clock, while batch pays in bursts that spin up, finish, and shut down. Low latency is another consideration.

A reasonable default for most work is to start with batch or micro-batch and move to streaming only when a concrete latency requirement justifies the cost, rather than reaching for it because it feels modern.

Summary

In this article, we’ve looked at batch and streaming in detail. Here are the key learning points in brief:

  • The choice between batch and streaming is one decision about how long to wait before treating data as complete, which is always a trade of completeness and latency.

  • Bounded data has a definite end, so a system can wait for all of it. Unbounded data never ends, so waiting for completeness is impossible.

  • Batch buys completeness by waiting for a boundary, which makes it simple and repeatable, but always a step behind the present.

  • Full loads self-correct but grow expensive, incremental loads are cheap but complicate corrections, and big-window aggregations are accurate but stale.

  • Micro-batch is the pragmatic middle, near-live results with batch’s simplicity, limited by a latency floor equal to its interval.

  • True streaming exposes the gap between event time, when something happened, and processing time, when the system saw it.

  • Windows are mandatory for aggregating an endless feed, and the type chosen, tumbling, sliding, or session, changes the answer.

  • A watermark is a bet about when all the data has arrived, and late data is the cost of that bet being wrong.

  • Exactly-once is a promise about effects through idempotency rather than about delivery, and it ends at the system’s boundary.

  • Lambda and kappa are real tradeoffs, duplicated logic versus costly reprocessing, so the newer pattern is not automatically the simpler one.
