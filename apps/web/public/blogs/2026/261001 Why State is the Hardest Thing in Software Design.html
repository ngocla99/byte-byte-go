Why State is the Hardest Thing in Software Design

State is the information a system retains that affects its functionality in some way. For example, a website might keep track of users who have logged in. A document editor remembers the current text. A background worker logs which tasks it has completed and which ones are pending. A database stores the records written to it for as long as needed.

Any useful software usually needs to manage state to carry out its intended functionality. The difficulty is keeping the state correct even as requests overlap, servers are added, machines fail, and software changes are deployed.

Often, the common advice is to “make the application stateless”. But this advice needs explanation. It usually means making particular application servers easy to replace while putting their important state elsewhere. It doesn’t signify a complete absence of state. Understanding such a setup requires looking at why state exists, who owns it, and what happens when it becomes unavailable.

In this article, we will look at why state is the hardest thing in software development and the multiple strategies that developers can use to manage it.

What Is State?

Let’s say there’s a function that converts a temperature from Celsius to Fahrenheit. The function receives a number as input, performs a calculation, and returns a result. It does not need to remember previous calls while doing this calculation.

Now consider another function that has to issue the next ticket number at a service counter. For it to function properly, it must know which ticket number was issued previously. Even if we call it twice with the same inputs, we get different results because the retained state has changed between calls.

This means that state makes an operation depend on something beyond its immediate inputs. It can exist in many places. A variable stored in memory can hold state. So does a file, a database record, a browser cookie, or a message waiting in a queue. At the lowest level, every running program has some sort of state, including variables and active connections. However, in design discussions, the focus on state is usually narrower. It deals with the information that must remain available across requests, across workers, or across failures.

This is why a server can use memory extensively, but still be described as stateless if there is no need for that state to cross a certain boundary.

What “stateless” Means for an Application Server

An application instance is one running copy of an application. A service might have two instances during quiet periods and 20 during busy periods.

If such an instance is considered stateless, it doesn’t depend on information from previous requests retained inside that instance. When a new request hits that instance, it gets whatever it needs from the current request or from other backing services, such as databases. For example, a request might contain a session identifier as input. Any instance of that service can use that identifier to fetch the session details from a shared data store and perform the needed functionality. There is no need for the same instance to have handled the user’s previous request.

This separation between replaceable stateless application instances and stateful backing services is central to the stateless design approach. A common arrangement looks like this:

  • The load balancer distributes incoming requests between multiple instances of a service.

  • All application instances can access the information needed to serve them.

  • Each storage box represents a logical service, which may itself run across several machines.

This makes it relatively straightforward to add instances, replace failed instances, and deploy new versions. There is no need to transfer information between application instances. A stateless instance can still create orders, update documents, and change database records.

The Main Categories of State

There are multiple categories of state that can be generated within a system. Let’s look at them in more detail:

Session State

Session state connects a sequence of interactions with a particular user or client. Some examples include login information, temporary user preferences, and progress through a multi-step form or workflow.

We can implement this by storing a session identifier in a browser cookie and the corresponding information in a shared server-side store. This way, any application instance can use this identifier to fetch the required state and continue the interaction.

Session state often expires, but its acceptable loss depends on the product. For example, losing a login session means that the user needs to log in once again. On the other hand, losing an hour of carefully entered information is more disruptive to the user experience. It is better to store unfinished work in its own saved record, independent of the login session.

Application State

Application state is a broad term for information about the current condition of the application or business process. For example, it can include an auction’s current highest bid, a background job’s status, available inventory, or active feature settings.

The term can vary between contexts. In frontend development, application state may refer to information held by the interface. At the design level, it often refers to business and operational information that is shared across requests. The storage of application state depends on its requirements. For example, the status of a job may need durable storage. However, the estimate of how many workers in a system are currently busy may be temporary.

Calling something application state doesn’t mean that it should be stored in a global variable inside an application process.

Persistent State

Persistent state is something that should survive beyond the execution that creates it. It should survive across process restarts. For example, saved documents, account records, and uploaded photographs.

Normally, we use a database to hold structured persistent state. Object storage is commonly used for holding files such as images, videos, and archives. Persistence is still relative to failure. For example, a file on a server’s disk may survive an application restart but become inaccessible when that server fails. Surviving a machine failure, a storage failure, or the loss of an entire location requires additional arrangements.

Persistent also doesn’t mean permanent. A record can be stored durably, but deliberately deleted the very next day.

Derived State

Derived state is calculated or constructed from other information. Some examples include cached query results, a search index built from documents, and a daily sales total calculated from individual sales.

The authoritative information is often called the source of truth. Derived state makes that information faster or more convenient to read.

Derived state must be rebuilt only when the necessary source information and transformation logic remain available. It can also become stale when the source changes before the derived representation catches up.

Ephemeral State

Ephemeral state has a limited useful lifetime. Some examples are a buffer used while processing a request, a typing indicator, and information associated with a live connection.

Much of this state can be deleted without any harm. A typing indicator can be reconstructed from subsequent activity. An interrupted calculation may be restarted once again.

However, a short lifetime does not automatically make information disposable. For example, a seat reservation that expires after five minutes may still need to survive a server restart during those five minutes.

Lifetime of such a state and its loss tolerance are separate decisions. Information can be temporary in business terms while requiring durable storage during its useful life period.

Where Should State be Stored?

The storage of state depends on several factors such as who needs the information, how quickly they need it, and what happens if it disappears. Here are some common starting points:

  • Application Memory: This is great for storing request variables, temporary buffers, or local caches. It is fast to access, but tied to a single process.

  • Browser or Mobile Device: This storage is suitable for interface preferences, local user drafts, or client-held tokens. It is available locally, but it is also bound to the device and controlled by the client.

  • Shared Key-Value Store: This is ideal for sessions, expiring records, and counters. It is accessible across multiple instances. But durability depends on design and configuration settings chosen by the developers.

  • Database: Best for storing business records, workflow progress, and authoritative information. It supports durable storage and coordinated updates.

  • Object Storage: This is used for storing files, media, exports, and backups. They are suitable for large objects accessed by identifiers.

  • Persistent Volume: This is used for database files or other storage owned by a workload. It can outlive the life of a process, but still needs recovery management

It is important to note here that a shared store is not automatically durable. Also, a durable file is not automatically accessible to another machine. Those are different properties that depend on the system logic.

There is also the question of which storage holds the authoritative version of a value. If a product’s price exists in a database, several caches, and a browser, the system needs a rule that clearly dictates which version can be used to handle a purchase. We can manage several copies only when their roles are clear.

There is also a trade-off with client-held tokens.

A signed token can carry identity information that application instances verify without the need to retrieve a session record on every request. The client carries that information between requests. However, claims within the token can become outdated. Immediate revocation of a token generally requires additional coordination or a server-side check. Signatures also protect integrity rather than making token contents confidential. Moving information to the client changes the system’s obligations.

Sticky Sessions: Keeping Requests Near Their State

Let’s say we have an e-commerce application that keeps a user’s shopping basket in the memory of instance A. If the next request reaches instance B, that instance cannot see the shopping basket. This would result in a very poor user experience.

Sticky sessions, also called session affinity, address this by routing a client’s subsequent requests to the same instance. A load balancer can use a cookie to maintain this association. The attraction of this approach is quite easy to figure out. We have locally stored information that is immediately available, and an existing application can work without moving state to a shared storage.

However, there are consequences of this choice:

  • First, traffic becomes harder to distribute evenly. Some users generate much more work than others. An instance associated with several busy users can remain overloaded while another has spare capacity.

  • Second, adding an instance doesn’t automatically move existing sessions to it. The new instance may receive new sessions while overloaded instances continue serving their established users.

  • Third, affinity doesn’t preserve information when the selected instance fails. The load balancer can send the user elsewhere, but the replacement cannot recover session data that existed only in the failed process.

We also need to handle deployments differently. Removing an instance may require first waiting for existing sessions to finish or transferring their information to a new instance.

Sticky sessions can be a practical choice when preserving locality matters or when adapting an existing application.

Why Moving State to Shared Storage Has a Cost

Moving state into a shared storage service improves accessibility. However, access now crosses a network boundary.

Reading a local variable within an instance requires no remote request. But reading a remote record involves sending a request, waiting for processing, and receiving a response. The application may also serialize the information into a transferable format and deserialize the result.

The number of interactions can have a significant impact. A request that performs several sequential remote reads must wait for each one before continuing. Even calls that are individually quick can create a noticeable delay when arranged in a long sequence.

The amount of information matters as well. It is much cheaper to pass a small document identifier between services than repeatedly forwarding the entire document. For large datasets, moving computation closer to the stored information can be more efficient than repeatedly moving the information.

State also changes while it is being moved from one place to another.

Let’s say a database transfers a customer’s records to another machine. New updates may arrive while the transfer is taking place. This means that just copying the original records is insufficient. The transfer should also account for the latest updates and establish when the new destination becomes responsible.

This is why moving state involves more than copying bytes. It can require catching up with changes, updating routing, and transferring ownership without losing or applying operations twice.

How Shared State Can Cause the Problem of Concurrent Changes

Putting information in a shared database solves the problem of access to a common location. However, correct updates still require suitable rules when it comes to multiple changes. The hardest state-related problems often involve several components trying to change related information while each component sees only part of what is happening.

For example, let’s say the warehouse has one item remaining for a particular product. Two requests to purchase that item arrive close together. Both read the stock count as one, both approve a purchase, and both write the new count as zero.

The final remaining count looks correct, but two purchases have been approved for just one item. The issue is that reading the value, making a decision, and writing the result were separate steps, which can cause other work to intervene between them and cause this mess.

A database should instead perform a conditional update. We should reduce the stock only if sufficient stock still exists. That check and update must happen as one indivisible operation. Other situations may require constraints, locks, or a transaction isolation level that protects the relevant business rule. Merely placing several statements inside a transaction can’t provide every possible concurrency guarantee.

Ownership helps make the rules manageable. An inventory service might be responsible for all inventory changes, with other services requesting changes through it. That service can have multiple instances.

Why State Makes Scaling Harder

Scaling computation and scaling stored information are completely different games.

To better understand the difference, consider independent image-processing jobs. If each worker can retrieve its input and save its output independently, additional workers can process additional images. A new worker doesn’t need the private history of an existing worker to do its job.

In contrast, a new database machine needs a lot more preparation. It must receive relevant data, learn which requests it should handle, and participate in the system’s consistency and recovery arrangements.

One option to do so is replication, which maintains additional copies of information. Replicas can improve availability. In suitable designs, they can also serve some read traffic. However, making another copy doesn’t automatically divide the work of handling writes to that information.

Another option is sharding, which divides the dataset into separately managed portions. For example, customer records might be distributed using customer identifiers. Different shards can then handle different parts of the workload.

Sharding introduces decisions about data placement, request routing, and operations that cross shard boundaries. While adding a shard, we may need to transfer existing data. Poor distribution can leave some shards much busier than others.

Also, some type of state resists division. For example, thousands of users may all be competing for the same auction item or updating the same popular record. Distributing unrelated records across more machines does little to remove contention around that one record.

Scaling down has similar obligations. Before removing a stateful worker instance, the system may need to transfer its responsibilities or save its progress.

All of these reasons explain why increasing the number of application instances can stop helping after a certain point.

Why Stateful Recovery Requires More than Restarting a Process

A replacement application process can start from the same code and configuration. However, recovering a stateful component also requires us to restore an acceptable version of its information.

There are several distinct problems.

Recovering Recent Information

Replication can provide another copy when a machine fails, but that copy may be behind.

With asynchronous replication, a primary can acknowledge a write before another copy has received it. If the primary is lost during that interval, the promoted replica may lack an acknowledged change.

In contrast, synchronous replication waits for confirmation from replicas before acknowledging the write. Depending on the configuration, that confirmation may include durable storage on another machine. This provides stronger protection against particular failures, while adding waiting time and dependencies on replica availability.

The design needs to set explicit expectations for acceptable data loss and recovery time. These are commonly expressed as the recovery point objective (RPO) and recovery time objective (RTO).

Determining Who May Accept Updates

An unreachable server is not necessarily dead. It may be running behind a broken network connection. If another server takes over while the original continues accepting writes, both may act as the authoritative writer. This causes a split-brain problem.

Systems need a reliable way to determine leadership of a specific instance and prevent an old owner from continuing to make accepted changes. Depending on the design, this can involve consensus protocols and fencing, which rejects operations from an owner whose authority has expired.

Recovering From Incorrect Changes

Replication preserves copies of changes, including mistakes that may have been made. For example, an accidental deletion can also propagate to replicas.

Historical backups and retained change logs provide a different recovery capability of returning to an earlier state. Some databases support restoring a base backup and replaying archived changes to a selected recovery point.

Therefore, a healthy recovery setup considers both infrastructure failure and damage to the information itself.

Unfinished Work is Also State

We can have a request that fails from the caller’s perspective even though the operation succeeded.

Let’s say a client requests a new report-generation job. The server creates the job successfully, but the response is lost. The client waits, times out, and retries. If the retry creates another job, the system now performs the work twice.

One solution to this is to use an idempotency key, which is an identifier representing the intended operation. The server records the identifier with the result. A retry carrying the same identifier can simply retrieve the existing result rather than doing the entire task again.

However, recording that identifier and applying the corresponding database change must be coordinated. Otherwise, a crash can leave the operation completed without the existence of the duplicate-detection record.

Derived State Can Be Recoverable and Critical

A cache is often described as disposable because its contents can be recreated when needed. This talks about information recovery, but it doesn’t establish that the system can operate comfortably while recovery happens.

Let’s say most requests normally obtain results from a cache. If that cache disappears, those requests will reach the underlying database instead. However, the database may be unable to handle the sudden increase in requests.

Similarly, a search index might be reconstructible from stored documents while still taking hours to rebuild. The documents remain intact, but search may be unavailable during that time.

In other words, being able to reconstruct information is quite different from being able to maintain the service while doing so.

Recovery planning activities may include gradual cache rebuilding, controlling concurrent requests, preserving useful snapshots, or temporarily reducing functionality.

Derived state also needs freshness rules. A cached article summary may tolerate some delay. However, a cached permission decision may require much tighter controls. The acceptable behavior follows from the type of information involved.

Deliberately Stateful Application Components Can Be Appropriate

Keeping active state near the code that uses it can be a sensible design.

A multiplayer game server may hold a match’s current state in memory because positions and interactions change rapidly. If we send every small change through a remote database, we could add substantial communication overhead which can ruin the gaming experience. Such a design needs a defined owner for each match and a clear failure policy. The game might save checkpoints, replicate selected updates, reconstruct from recorded events, or accept that some matches end when their server fails.

A long-lived connection also belongs to a particular running process while it is active. If that process fails, reconnecting needs a new connection and possibly restoring subscriptions or replaying missed messages. Application-level recovery must account for that connection state.

State affects deployments as well. A new code version may introduce a new stored format while older instances are still running. Both versions may temporarily need to read and write compatible information.

Summary

In this article, we’ve looked at state management in detail and why it is so challenging. For each piece of state, the following questions can help make the design more precise:

  • Who owns the authoritative version? It establishes which component decides whether a change is valid.

  • Who needs to access it? It helps distinguish information needed by one request, one user, one worker, or many services.

  • How long is it useful? It defines the expiration or retention policy of the piece of state

  • What failures must it survive? It can help formulate and consider process restarts, machine failures, and broader outages separately.

  • Can it be reconstructed? This helps identify the required inputs and the time reconstruction takes for a piece of state.

  • How stale may a reader’s view be? It helps connect the answer to the decisions made using that information.

  • What happens when updates overlap or requests repeat? It helps specify concurrency and retry behavior.

  • What happens when the state’s owner moves or disappears? It helps define strategies for transfer, recovery, and handling unfinished work.
