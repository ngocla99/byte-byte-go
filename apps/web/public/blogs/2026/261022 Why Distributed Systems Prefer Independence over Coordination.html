Why Distributed Systems Prefer Independence over Coordination

In a distributed system, you have components running in separate processes or machines. These components could be application services, database replicas, or even background workers.

Since in distributed systems, we divide the system into so many components, it’s pretty common that one component may need to talk to another component to get something done. It may also have to wait for the other component’s response. You can think of coordination as this talking between components. For example, you may have one service waiting for another service to approve a request. Or a database waits for acknowledgment from its replicas. Or a worker waits for a lock.

In this article, we’ll look at why coordination is a challenge for distributed systems. Here’s what we will cover.

  • Why coordination becomes a challenge

  • How coordination increases in a system

  • How to reduce coordination

  • Strategies to handle coordination

Why Coordination Becomes a Challenge

To be clear, coordination is critical for a system. It gives you important guarantees about the behaviour of the system. For example, coordination stops two customers from booking the same seat. It keeps data replicas in sync with each other.

But coordination over a network can become a challenge. In a single process, you can easily coordinate access to shared data. However, across a network, a big problem appears. Let’s say you have a service that sends a request to another service and doesn’t get back any response. The receiving service might have crashed before processing the request. Or it might still be working. It might have completed its part of the job, but the response got lost on the network.

The services talking to each other cannot distinguish whether there’s a delay or a genuine failure. One of the ways to deal with this uncertainty is to use a timeout. With a timeout, the calling service can decide when it has waited long enough for a response.

There are many different coordination protocols to deal with this uncertainty. But they all have some costs.

First, you have latency. Let’s say you have an operation that needs three network round trips to carry out its job. Each round trip takes 40 milliseconds. This means that you have to wait for a minimum of 120 milliseconds before the operation can finish. Even if you make the three round trips parallel, the operation has to wait for the slowest response. To summarize, coordination is a big reason for latency.

The second cost is availability. Let’s say you have a service with enough CPU and memory to complete its task. But it cannot do so because it needs something from another service, which is not reachable. So, in a way, the first service is also unavailable. Sure, coordination also helps improve availability. For example, replication makes sure that the failure of a single database instance doesn’t bring the application down. This also connects with the CAP theorem.

The third cost is throughput. Let’s say you have multiple workers that take care of requests. But each worker has to acquire the same exclusive lock on a dependency and hold that lock for 10ms. The other workers have to stay in the queue and wait for this dependency to be available. Hence, the impact on throughput even though you’ve put in more computing capacity.

The fourth cost is complexity. Once you have several components involved in doing something, the complexity goes up. The failure recovery must deal with multiple intermediate states. One component may have finished something. Another might have failed. A machine that is recovering from failure may have outdated information.

How Coordination Goes Up

The need for coordination between components goes up because of familiar mechanisms used to solve other problems. For example, think of mechanisms like database locks, transactions, consensus, and synchronous calls. They all increase coordination because they control when an operation may continue and when it’s stopped. Let’s look at them in more detail.

Locks

As you might know, a lock gives an operation temporary exclusive access to a resource. For example, you can have two requests that are trying to modify the same reservation. If there’s no exclusive access, these requests might end up overwriting each other’s changes. You can put a lock on the database row to make these requests go through one by one. Or you could also lock the entire table. The scope of the lock that you choose can impact the cost of coordination.

One good way to reduce the impact of locking is to use optimistic locking.

In this approach, you can have the application read a record with a version number, apply the change, and submit that change only if the version number is still the same. If another operation has modified the record in the meantime, its version number would’ve changed. In such a case, the update should fail. This way, you can avoid holding a lock while processing the record. Of course, you still need to have an atomic check when applying the update. Also, too many conflicts can lead to lots of retries.

Transactions

A database transaction groups a bunch of changes into a unit. All the changes in the unit are committed or aborted together.

For example, let’s say you want to move an item from one storage location to another. For this, you would decrement the count value in one record and increment the count in the other record. If both steps are part of the same transaction, you can prevent the issues that might arise from having only one change committed.

A great way to keep coordination in control is to have local transactions where one database takes responsibility for a specific rule.

Consensus

Consensus protocols are used for keeping database replicas in sync. But they can also increase coordination.

For example, a consensus protocol like Raft commits changes only after a majority of replicas have acknowledged them. This means that in a group of three replicas, you need at least two replicas to talk to each other for things to keep working. Otherwise, the system may become unavailable.

Synchronous Service Calls

You can also have higher coordination in simple application code.

Let’s say you have a document upload service that applies multiple checks to a document after it is uploaded by a user. For example, it might scan the document for viruses. Or generate a new thumbnail. Or indexing for search. Let’s say all these checks are made by specific services. And you can access the document only after all the checks have gone through. As you can see, each check contributes to the completion time for the upload. Ultimately, you end up with much higher coordination.

Of course, some dependencies can be mandatory for the task. For example, you might have a security requirement saying that the document can’t be made available to the users before the system has finished scanning for viruses. However, you can generate thumbnails and index for searches later on as well.

How to Reduce Coordination

Before you can reduce coordination in a system, you need to define what “correctness” means for your system. This can be done by defining invariants for the system.

You can think of an invariant as a rule that should stay true even after concurrent operations and failures. For example, a seat can have at most one confirmed owner.

Now let’s consider another case in which two devices can record which articles have been read by the user. You can combine the data from both devices without the need to first pick one device and then the other. Both of these operations can go through independently with no impact on the end goal.

If you can’t do that, it means that the design needs more coordination. Let us now look at some strategies that you can use to reduce coordination.

Marking Clear Ownership

One of the easiest ways to bring down the need for coordination is to reduce how much of the system needs to be involved in a decision.

For example, let’s say you have many services that can directly modify a customer’s subscription data. In such a situation, each service has to understand the changes made by the other services. They need to also guard against interference from other services. This is a high coordination situation.

However, if you give one service clear responsibility for everything related to subscription data, it can solve a lot of problems. Sure, coordination may be needed inside the service. But you don’t have to worry about unrelated services coordinating with each other for a task that has nothing to do with them.

There are multiple ways to divide ownership. You can divide based on customers. Or accounts. Or functionality. However, a customer or record with a high traffic footprint can still create bottlenecks.

Eventual Consistency

For a lot of operations, we don’t need to update every copy of the data immediately. Let’s say, when a user changes the bio in their social media profile, you can update the authoritative record first. However, you can cache the profile pages or update the search index later on. These other replicas or copies of the data will be eventually consistent.

Eventual consistency means that if you stop new updates, all replicas of the data will eventually have the same data if the network is available. The time it takes for each replica to reach the same point is called replication lag.

The main advantage of eventual consistency is that you can complete the original operation without having to wait for every replica to catch up to the same point. The trade-off is that stale reads can happen during the replication lag.

Asynchronous Messaging

You can reduce coordination between components using asynchronous messaging. This lets one component store tasks for another component so that those tasks can be done later.

Let’s say you want to trigger a welcome email to the user when they create a new account on your website. If the email sending service is not available when a user registers, your application can still create the account and store the request to send the email later on when the email service becomes available. These requests can be stored in a queue. Queues are a great way to handle temporary outages of the email service or absorb a burst of requests.

To implement such a feature, you need to make sure that the database update and storing the request in a queue stay connected. A naive way to go about this is to update the account information in a database and then publish a message to the email service straight away. However, if the account service crashes between those steps, the account gets created, but the welcome email is never sent to the user.

The transactional outbox pattern solves this problem. In this pattern, you make the account service update the account details and create the outgoing event in the same database transaction. Later on, you can have a separate event relay publish the committed events to the messaging system. This way, you can try publishing the email message as many times as you want. Of course, the consumers should be able to handle duplicate delivery.

Idempotency

As we saw in the previous section, you can have duplicate events and deliveries. This is important to make sure that no event gets lost.

This is why you need to design idempotent operations. Such an operation has the same effect irrespective of whether it’s called once or multiple times. For example, let’s say you have an operation that creates an invoice for an order. No matter how many times you call it, only one invoice should be created for one order.

You can use a stable operation ID to find out if a request is a duplicate. Using the ID, the service can find out if the same request was processed earlier. If yes, it can return the existing result instead of generating a new invoice.

Sagas

Some business processes need coordination between multiple services to get the job done.

Let’s say you have a travel reservation workflow that books a flight and a hotel. In such a case, you can’t get both of these things done inside one transaction. Saga helps break the process into a series of local transactions. Each transaction is committed separately.

But you need to compensate for an action in case there’s a failure. For example, if your flight reservation is successful, but the hotel booking fails, you need to cancel the flight as well. Cancelling the flight is a compensating action in this case.

You can implement a saga using two approaches: orchestration or choreography. Orchestration is the approach in which a central authority manages the workflow. Choreography is the approach where services react to events without a central authority.

Summary

In this article, we’ve looked at the coordination challenge in distributed systems. Also, the various techniques to reduce coordination while making sure that the application does its job without issues.

Each technique has its use. Ownership helps you define which components are part of a decision. Eventual consistency lets you propagate data across multiple replica components while keeping coordination overhead down. Other techniques, like messaging, let consumers handle tasks later, and idempotency makes it safe to manage duplicates.

Some design tips that can help developers make suitable decisions about coordination are as follows:

  • First, you need to state the invariant in a precise manner so that you can identify when something happens that violates this invariant.

  • Second, keeping ownership boundaries small can help you reduce impact.

  • Third, you need to be clear about how retries will work, how duplicates will be handled, and so on.

To design a good distributed system, you need to think about how coordination can be a problem and how you can mitigate it. Such a system should be able to make independent progress on a task when correctness is needed. Also, it should coordinate whenever correctness needs it.
