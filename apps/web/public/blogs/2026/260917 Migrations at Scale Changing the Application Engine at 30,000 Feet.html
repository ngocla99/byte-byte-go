Migrations at Scale: Changing the Application Engine at 30,000 Feet

Consider a hypothetical scenario in which an online shopping platform has become extremely successful. It has outgrown its original database. This causes order histories to load very slowly. Maintenance takes much longer than it used to. And engineers spend way too much time managing the workload and the system’s limitations.

The engineering team behind this system wants to replace the database and migrate the data to a new database that promises better performance. But you cannot take a popular online store offline to make the switch. Customers are always placing orders, changing addresses, and requesting refunds. The shop can’t be shut down just like that.

This scenario offers a glimpse of the main challenge inherent in production migrations. How do you change a working system while still running the service that people depend on? At scale, copying existing data during such migrations can take days. Also, many supporting applications may depend on the component being replaced. Every intermediate step needs to work while ordinary business continues.

In this article, we will look at how migrations work at scale and the key strategies that can help make it as efficient as possible.

What Exactly is Being Replaced?

It’s not like data is the only thing that needs to be migrated. There are different types of migrations that are possible in any system.

  • Database Migration: It changes where data lives or which database system manages it. For example, moving between PostgreSQL servers changes the hosting arrangement. On the other hand, moving from MySQL to PostgreSQL also creates differences in data types, queries, and supported behavior.

  • Schema Migration: It changes the structure within a database. A schema defines tables, columns, data types, and relationships. For example, adding a delivery address column or separating subscriptions into their own table changes the schema without replacing the database server.

  • Service Extraction: A service extraction is used for moving a responsibility out of a larger application into a separately running service. For example, taking out the functionality of inventory management into an independent service instead of remaining inside the store’s main application. This sort of migration can change communication, data ownership, and failure handling.

  • Cloud Migration: This type of migration moves workloads between hosting environments. A protocol migration changes the rules or formats that components use to communicate, such as introducing a new message format between services.

Many of these changes overlap. For example, extracting inventory functionality could involve a new service, database, as well as a protocol. Separating those changes where practical makes failures easier to understand.

Old and New Coexisting

Since migration at scale isn’t an instantaneous process, we need to have a way for the old and new system to coexist.

How can this be accomplished?

In the online store example we mentioned earlier where the order data needs to be migrated, we can start by identifying every reader and writer of order data. Reads retrieve information, while writes create, update, or delete it. The web application is just one dependency. Background workers, reporting jobs, and support tools may also access the order data.

Once we have all this information, we can introduce a new database access layer through which application code can request operations such as retrieving an order. This layer can select either database using configuration switches. These switches are commonly known as feature flags.

Initially, the old database remains the source of truth. It determines the valid state of each order. The new database version just receives a copy of that state. If the two databases disagree on certain data, we have a point of investigation to check if the migration is working as expected.

This ownership rule regarding the old database being the source of truth is really important because we can’t have two copies of data with conflicting versions. For example, one database accepting a cancellation while the other initiating a shipment can create a business problem. Having a clear authority makes the temporary system easier to understand and control. At any point, we can also stop the migration activity without impacting the existing system.

Preparation of a migration includes an agreement on success conditions. For example, in the case of our online store, every accepted order should remain available, customers should see the correct delivery status, and checkout response times must remain acceptable.

How to Keep New Changes Flowing to the Replacement

During the migration, we need to keep changes flowing to the replacement seamlessly. For example, in our online store example, just copying an order’s details once is insufficient because customers can change it afterward. The migration process needs a reliable way to carry those later changes to the new database version.

One approach to do so is dual-write, which makes sure that the changes reach both databases. However, separate database writes can fail independently, creating a mismatch. For example, the old database might save a new address while the new database is unavailable. An application crash between the two writes can create the same inconsistency. Calling both databases doesn’t magically make their updates atomic.

The transactional outbox pattern is really useful in this scenario. In this pattern, the application saves the business update and a record describing the change in a single transaction inside the old database. A background worker then delivers the recorded change and retries failures. Since the update and delivery record are committed together, a crash after commit doesn’t erase the required change.

Another common approach to propagate changes is CDC (Change Data Capture). In this pattern, a standalone process follows the source database’s change log and forwards all changes to the new database. This approach can capture changes without adding a second write to every application operation.

Both asynchronous approaches accommodate a delay between the source update and its arrival at the destination. We can measure this replication lag and also monitor failed deliveries. A stream that is running but falling further behind cannot support a safe handover simply because it remains connected.

Bring the Existing Data Across Safely

The new change stream can handle ongoing activity. But existing old orders still need to be migrated to be able to use the new database. Backfill is the process that populates the new database with historical data.

Backfill must cooperate with newer updates. Suppose a copied order says “processing,” but a later change says “shipped.” If the newer change arrives first and the historical copy overwrites it afterward, the new database incorrectly moves the order backward in its lifecycle.

A safe setup to handle this loads the coordinated snapshot first, retains changes made during copying, and then replays them from the recorded position. Setups that copy and apply changes concurrently need other protections, such as version checks. Deletions need similar care so that copying historical data does not recreate a deleted record.

It is better to copy manageable batches and save checkpoints. After a crash, the process resumes instead of restarting. Operations also need idempotency, which means that repeating the same operation must have the same effect as performing it once. For example, retrying a copied order should update the same record, not create another order.

Version checks or ordering are critical to handle stale updates. For instance, a worker can save an order successfully and crash before recording its checkpoint. Restarting may repeat that batch. This is an expected problem that the migration design must be able to handle. We should not have to manually delete the duplicate record.

One caveat here is that copying can consume resources that are needed by other clients. Therefore, we need to throttle it using some sort of rate limiting. When response times deteriorate, copying slows or pauses. Catching up also requires spare capacity. If the old database is producing changes faster than the new database can apply them, the backlog will grow even after the historical copy finishes.

How to Prove That the New System is Consistent with the Old One

While a completed backfill establishes that the copying process finished its assigned work, verification establishes whether the replacement database can be trusted.

To make sure, we need to check record identities, values, and relationships. Comparing row counts for equality is insufficient because the two databases could contain different sets of orders. Business checks add another layer. Order totals should agree with items and discounts, and deleted addresses should remain deleted. Detailed migration validation can compare corresponding source and destination rows.

Comparison processes should also account for replication delay and representation changes. A temporary mismatch may disappear when the new database catches up to the old one. Different address formats may express equivalent information. We need to compare corresponding versions or recheck differences after synchronization.

While it is valuable to know that data in the new database matches data in the old database, it cannot prove that every business rule is correct. Both implementations might share a defect. We need to also use other cases, rare order states, and performance checks to complement comparisons against live traffic.

The dual-read process involves checking both implementations at the time of read. In a shadow read, the old database still supplies the actual customer’s response while the new database provides a comparison result. When a customer requests their recent orders, we can compare both answers without making the candidate answer authoritative.

However, these shadow reads also consume capacity, and we need to be mindful of that. Techniques such as sampling, time limits, and isolation prevent the comparison from slowing normal requests. A different dual-read strategy tries the new database and falls back to the old database when needed. However, blind fallback can hide defects or return deleted information.

Let the New Database Take Over Gradually

It is better to shift to the replacement database serving real customers in a gradual manner.

After comparisons establish a strong level of confidence, we can start moving customer reads. First, we can move internal users to the new database. Next, we can aim for small customer groups followed by progressively larger groups. This is similar to the canary rollout where a limited number of users experience the new implementation before wider adoption happens.

Rolling out to stable groups makes it easy to investigate potential issues because the same customer follows the same route across requests. We can then watch error rates, response times, database load, and business outcomes such as completed checkouts. Promoting the new database to the main one depends on acceptable behavior under a significant level of traffic. For example, a good result at one percent of traffic doesn’t establish that the new database is good enough to handle every user. Some resource-related issues might only appear when the traffic goes above a certain threshold. Resource limits may appear only as traffic increases. Each increase in the traffic percentage migrated provides a new observation point, with explicit conditions for stopping the rollout before more customers are affected.

Additionally, freshness of data requires specific attention. A customer might update an address in the old database and immediately read the previous address from the new database because replication was delayed. This violates read-your-writes consistency, the expectation that a successful update appears in subsequent reads.

The application therefore keeps freshness-sensitive reads on the old database or waits until the new database has applied the relevant update. At this stage, returning reads to the old database remains relatively straightforward because the old database still accepts every authoritative write.

Hand Over Writes At a Controlled Boundary

There is a point in every system migration where the responsibility has to be transferred to the new system, whether it is a database or a service. Cutover is that point.

A migration plan can have separate cutovers for reads, writes, and customer groups. Transferring writes is especially consequential because the new database becomes the source of truth for the accepted business state.

For a system design with one authoritative writer, the handover needs a clear boundary. At this boundary point, the system stops admitting writes to the old database, lets accepted operations finish, and prevents outdated processes from continuing to write there. This prevention is called fencing. We can’t just think of it as changing a flag if an old worker continues to have access to the old database.

We need to then confirm that the new database has applied every change through the old database’s final committed position before admitting authoritative writes to the new database. Identifier generators, permissions, and other database objects also need preparation. Just copying rows alone doesn’t establish readiness.

This feeds into the requirement behind zero downtime. Some migration services require a write interruption during promotion. An application designed for coordinated handover may instead hold requests briefly or queue them durably, with safe retries and accurate acknowledgements. A queued request cannot be described as a completed update before it completes.

How to Keep a Recovery Path After the Switch

Rollback helps move back to a previous implementation when the new implementation behaves badly. However, the rollback plan has to be created near the beginning of the project, even though it might only be used at the switch or cutover point.

Once the new database accepts writes, the old database can become outdated immediately. Suppose the new database accepts 10K orders and then develops a serious problem. Redirecting traffic to an unchanged OldDB makes those orders disappear from the application’s view. In other words, keeping the old server running doesn’t keep its contents current.

A workable rollback plan explains how accepted changes reach the old system. A tested reverse replication path can maintain the old database to the latest state during a defined rollback period. Returning authority still requires controlling writes, applying remaining changes, and fencing the database that gives up ownership.

Some changes cannot be reversed cleanly. The new database may support some type of data that the old database cannot represent. We may need to delay those capabilities until the rollback period ends or prepare to repair the new system while still keeping it authoritative. This is an approach called rolling forward.

Backups provide another recovery mechanism. But a backup contains old data. Preserving data created after a backup has been taken requires retained changes and a recovery process. We need to have a plan that specifies acceptable recovery time and data loss.

Before the real handover, we need to rehearse the recovery process with representative data. This rehearsal should include writes accepted by the replacement and confirm that they survive the return to the old setup. A routing switch that doesn’t account for those writes is only a partial test of rollback.

Change the schema without breaking existing callers

Consider a scenario where the online store renames a column from “name” to “display_name” without changing its meaning. An immediate rename breaks application instances still expecting name.

The expand, migrate, contract pattern creates a compatibility period. Here’s how it works:

  • First, add “display_name” while retaining name.

  • Deploy code that maintains both fields. Check for every older writer.

  • Backfill existing values without overwriting newer changes, verify them, and move reads to the new field.

  • After old dependencies and rollback needs disappear, stop maintaining the old field and remove it. This is also called parallel change.

During deployment, an older application instance may still update only name. The new field therefore cannot immediately be trusted for every customer. We need to replace or accommodate those writers, finish the required copying, and verify consistency before relying on “display_name”. Deployment order is part of the migration’s correctness.

Structural compatibility doesn’t eliminate database load or locking. A schema operation may wait for a lock, scan records, or rewrite a table. Its execution characteristics still need checking on the selected database and operation.

Replace An Application One Functionality At A Time

Service extraction transfers a business responsibility into a separately running component. For example, the online store might route inventory requests to a new inventory service while its original application continues to handle orders and shipping.

This gradual replacement is known as the strangler fig pattern.

In this pattern, a routing layer lets callers keep using a stable interface while individual capabilities move to a new home behind it. Eventually, the original implementation has no remaining responsibilities and can be retired without any issues.

Moving data ownership requires more care than moving request routing. For reference, creating an order and reserving stock might previously occur in one database transaction. After extraction, a network request between those actions can fail. The design needs an explicit reservation workflow and a way to release inventory when an order cannot proceed. Both implementations must not independently reserve the same stock during comparison.

The strangler fig is one member of a broader family:

  • Branch by abstraction puts interchangeable implementations behind an interface within an application.

  • Blue-green deployment prepares two application environments and switches traffic between them.

  • Canary rollout limits initial exposure.

Each supports incremental change, while data synchronization and compatibility still need their own design.

How the Same Approach Applies to Cloud Migration

A cloud migration expands the boundary to an operating environment.

The destination needs application servers, data, uploaded files, queues, permissions, secrets, and monitoring. Components without durable local state are generally easier to redirect. On the other hand, components with sessions or files require a state-transfer plan.

Both environments may receive traffic during the transition because name-resolution results can be cached and connections can remain open for some time. However, data ownership must stay coherent throughout that overlap. Transfer bandwidth and production load also determine how quickly the move can proceed.

A protocol migration creates a similar overlap between senders and receivers. Receivers commonly gain support for both formats first. Senders continue using the old format until all the necessary receivers understand the new one, then switch gradually. Old support remains while older clients or retained messages still require it.

Summary

In this article, we have talked about the process of migration at scale and the various strategies that can help. Here are the key learning points in brief:

  • The migration is complete when old dependencies, temporary switches, and duplicate maintenance paths can be removed safely.

  • There are different types of migrations: database, schema, and service.

  • Since migration at scale isn’t an instantaneous process, we need to have a way for the old and new systems to coexist.

  • During the migration, we need to keep changes flowing to the replacement seamlessly. The outbox pattern and CDC are two approaches that help with this.

  • Moving all website traffic does not establish that a monthly report or an infrequently used support tool has also moved. The observation period must cover relevant operating cycles and delayed work.

  • Retirement includes removing obsolete access, stopping unnecessary synchronization, and checking that backups, recovery procedures, and monitoring now cover NewDB.

  • Leaving temporary infrastructure indefinitely adds cost and makes future changes harder to understand. Each remaining dependency needs an owner and a clear condition for removal.

  • For a small application, a tested maintenance window may be simpler than prolonged coexistence.

  • Online migration requires duplicate infrastructure and additional operational work. The appropriate strategy follows the interruption users can tolerate and the team’s ability to operate the transition reliably.
