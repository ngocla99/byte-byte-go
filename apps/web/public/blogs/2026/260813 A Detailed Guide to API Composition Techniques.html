A Detailed Guide to API Composition Techniques

In a service-based architecture, a single product screen showing a user profile, that user’s five most recent orders, the delivery status of each order, and a short list of recommendations requires data from four separate services. Each service stores only its own data, so none of the four services returns the full set on its own. In other words, the caller issues four separate calls, and merges the resulting four responses in the structure needed for the user interface. This merging step is API composition, and it exists in every system where data is split across more than one service.

The code that performs this merging can run in several places. It can run inside the mobile application, on a server in the datacenter, at a CDN edge location, or inside one of the four services. Putting a server between the mobile application and the four services adds a network hop, which sounds like it should cost extra time. However, it usually reduces total load time instead, because a round trip between a phone and a server on a weak mobile connection can take a few hundred milliseconds, while a round trip between two services inside the same datacenter takes a fraction of a millisecond. To put it simply, trading four expensive round trips for one expensive round trip plus four cheap ones is often a large net saving.

However, latency is only the first tradeoff. The place where the merge operation runs also determines what happens when one of the four services is unavailable, how much of the response can be cached, and which team has to approve a change before the screen ships.

In this article, we are going to dive deep into the area of the API composition problem and the patterns associated with it. Here’s what we will cover:

  • The API composition problem

  • Client-side composition

  • Over-fetching and under-fetching

  • Composition, aggregation, and orchestration

  • API gateways

  • Backends for Frontends

  • GraphQL as a composition layer

  • Edge composition

  • Availability and caching tradeoffs

  • Versioning across multiple frontends

  • Ownership of the composition layer

The API Composition Problem

Splitting data across services removes an option that a single database provides for free. Within one database, a query can join across tables and return everything a screen needs in a single result. Once orders live in one datastore and user profiles live in another, that join has nowhere to run, because the query does not span network boundaries. A system that separates data by service has basically decided to compose the data elsewhere.

Also, services are organized around durable business capabilities such as users, orders, and pricing, because a service boundary is expensive to move once teams and datastores have been built around it. Screens, on the other hand, are organized around user journeys that are subject to change as the requirements evolve.

A composition point is any code that fans out to several sources and merges the results into one response. It is a broad definition that can cover a frontend component running four fetches, a gateway calling three services, a GraphQL resolver, or an edge worker stitching fragments together. All four perform the same operation, but they execute in different locations.

One point to note here is that the phrase “API composition” also belongs to a narrower query pattern in the microservices architecture, where a composer calls the services owning the data and joins the results in memory instead of maintaining a separate read model. However, we are talking about it on a more general level.

Client-Side Composition

The default location of composing data is the client, because it requires no additional infrastructure. For example, a mobile application issues multiple requests, waits for the responses, and assembles them in a view model. Nothing has to be deployed, and no new service has to be created, which is why this arrangement often becomes the first choice.

However, there are three trade-offs to this:

  • Multiple round trips over the slowest network in the system, since the connection between a phone and a datacenter is far worse than the connection between two services inside it.

  • Retry logic, timeout handling, and every combination of partial failure is built into application code and sits alongside rendering logic that has nothing to do with data fetching.

  • Very little observability, because the failures occur on individual devices rather than in a system that can be queried.

Mobile carries an additional constraint. Application code ships to devices that cannot be updated on demand, so a defect in the merge logic can keep running on installed versions for months, while a server-side merge can be corrected and deployed in an afternoon.

None of this makes client-side composition wrong. For a single screen calling two services over a good connection, it is usually the correct answer. The cost becomes more noticeable as calls per screen multiply and fetching logic becomes more complex.

Round Trips

Two components play a key role in making up the time a request takes:

  • Transfer time scales with the number of bytes moved.

  • Round-trip time is a fixed charge per request. It is charged again for every request that waits on a previous one before it can start. Also, it varies enormously by network boundary.

Here’s how the round-trip time varies in different scenarios:

  • Between two services inside a datacenter, a round trip costs well under a millisecond.

  • Between a phone and a server on a good mobile connection, tens of milliseconds.

  • On a congested or weak mobile connection, a few hundred milliseconds.

  • Between regions, roughly fifty to a hundred and fifty milliseconds depending on distance.

Looking at these measurements and the components, it can be deduced that removing thirty unused fields saves a small amount of transfer time. However, removing one round trip on a mobile connection saves more than that. Likewise, removing three round trips saves considerably more.

This is not to say that over-fetching and under-fetching are not real problems. The payload size does dominate in specific situations such as image-heavy responses, low-end devices, and metered data plans. However, for most screens on most connections, the number of round trips is the more important factor.

HTTP/2 multiplexing tries to change this, since several requests share one connection without blocking each other. However, it does nothing for chains where each call waits on the result of the last, and it does not move retry handling out of application code.

Composition Patterns

Two arrangements of the same set of calls can produce very different results. For example:

  • Aggregation issues independent calls at the same time and merges the responses. Total latency approximates the slowest single call, and a failure in one branch does not prevent the others from completing. Four parallel calls at forty milliseconds each finish in roughly forty milliseconds.

  • Orchestration sequences calls where each depends on the result of the last. An order lookup returns a customer identifier used to fetch the customer record, which returns an address identifier used to fetch the address. Total latency is the sum of the chain where every step is a place where the whole operation can stop, and the same four calls now finish in roughly one hundred and sixty milliseconds.

Most real composition points combine both arrangements. A first call resolves identity or entitlement, and a parallel fan-out follows once that result is available.

Availability Math

Merging four responses also merges four sets of failure conditions.

If a composed response requires every upstream call to succeed, its success rate approximates the product of the upstream calls. For example, five services at 99.9 percent availability each compose to roughly 99.5 percent. In annual downtime, the difference is between 8.8 hours and about 44 hours. Also, this assumes that failures are independent, which is not strictly accurate, since shared infrastructure and correlated traffic spikes cause failures to cluster.

The multiplication only applies when every call is required. A product page cannot render without the product record, but it might render perfectly well without the recommendations block depending on how the page is designed. Having this sort of insight about a system allows a developer to sort dependencies into required and optional. The optional dependencies can then be given shorter timeouts, cached defaults, or empty fallbacks to keep the response available even when some optional dependency is down.

There is no fixed rule as to what the returned response should be when there is a partial failure. Here are a couple of approaches:

  • Returning an error for the whole request is simple and predictable, but it produces worse availability numbers.

  • Returning the available data with the missing parts marked improves availability. However, it creates a combinatorial problem for the client, which now has to handle every combination of present and absent fields.

Teams disagree about which produces fewer incidents.

Caching Tradeoffs

Composition and caching pull against each other, but its effects remain hidden when a system is small.

For example, a response containing one product record is identical for every requester. It sits in a CDN, a shared cache, and a browser cache, and a high proportion of requests for it never reach the origin. Fine-grained resource endpoints cache well for that reason.

On the other hand, a composed response assembled for one user at one moment behaves differently. It contains that user’s orders, that user’s delivery statuses, and recommendations generated for that user. Nothing else can use it, so the cache hit rate approaches zero and every request travels the full path to the services behind it.

The benefit of composition is fewer round trips, but the trade-off is in terms of cache hits. The choice depends on how much of the response is personalized. For example:

  • A catalogue browsing screen made almost entirely of public data can perform better as several cached fine-grained requests than as one composed request that no cache can serve.

  • An account dashboard where every field is user-specific has nothing to lose from composition, because none of it was cacheable to begin with. The ratio of personalized to public content is the number worth measuring before deciding.

API Gateways

A gateway is a single entry point in front of many services, handling concerns that every request needs regardless of which client sent it. This includes functionalities such as authentication, rate limiting, TLS termination, routing, request logging, and metrics collection. Centralizing these common features prevents each service from implementing them separately and inconsistently.

Many gateways also compose by calling multiple services and returning a merged response. The distinction here is what the composition is organized around. For example, merging generic resources, such as returning a product record together with its current stock level, is infrastructure work that any client can use. However, building a response that matches one specific screen is product work, and once a gateway contains product logic for one client, it has become a shared product layer.

This is where the coordination cost starts to rise. Every client team now needs changes in a component every other client team depends on. Requests queue behind each other, and a release for one client can affect another. The team operating the gateway becomes an approver for product decisions it has no context on, which is not an ideal state to be in.

Backends for Frontends

A backend for frontend is a server-side layer dedicated to one client and owned by the team that builds that client. It converts domain-organized service responses into the structures one particular client renders. For example, a web layer and a mobile layer might call the same four services, but return quite different responses, because the two screens display different things.

The defining property of the BFF is that the layer is not shared. Everything else follows from that. A team owning its BFF layer changes the response format without the need to discuss things with other teams, ships on its own schedule, and does not queue behind another client’s release.

The obvious cost here is duplication. Two layers calling the same four services will contain similar code. The standard recommendation in such scenarios is to extract the common parts into a shared library. However, a library used by two teams is a shared dependency with its own release cycle and approval step, which reintroduces the coordination cost that the split removed. Duplication between layers is often the cheaper of two imperfect options.

Some points to keep in mind can be as follows:

  • Response formatting, field selection, and client-specific defaults can be duplicated freely.

  • Business rules, pricing calculations, and authorization decisions belong in the services that own them and should never be duplicated.

Ownership is where this pattern most often goes wrong.

If a separate platform team operates the layer, client teams still file tickets and wait, which reproduces the original problem with an extra step. The counterargument is that, since these layers require on-call rotations, capacity planning, and security reviews, a client team without that experience can end up running a production service poorly.

Also, there are a couple of more failure points worth considering:

  • A layer serving one client that only forwards requests adds a deployment for no benefit.

  • A layer accumulating business rules becomes a second system of record.

GraphQL Composition

GraphQL moves the merge into a query layer where the client specifies the fields it requires and the server assembles a matching response. In such a setup, a single endpoint replaces many. Also, a client needing three more fields can simply change its query rather than requiring changes to the service. Decoupling client releases from server releases is the strongest argument for the approach.

The work of merging data moves into resolvers, which are basically functions responsible for fetching one part of the result. A resolver for a customer field runs whenever a customer is requested. However, a query returning fifty orders, each with a customer, runs that resolver fifty times, producing fifty upstream calls where one batched call would suffice. This is the N+1 problem. The standard solution is to collect the calls made during a single query and issue them together.

Caching undergoes changes as well in this approach. A REST endpoint has a URL, and a URL can be cached by a CDN, a proxy, or a browser without any application involvement. A single GraphQL endpoint receiving arbitrary query documents cannot be cached that way, so response caching moves into the application layer and becomes entity-level or field-level caching. That is more code and more operational surface than an HTTP cache header.

Arbitrary field combinations can also make load unpredictable, since the set of queries the server will receive is not known ahead of time. Query cost limits, depth limits, and pre-registering an approved list of queries all address this. The last of those recovers predictability by removing some of the client freedom that motivated the approach.

Lastly, GraphQL Federation splits one large graph into subgraphs owned by service teams and composes them at a router. It collapses the integration count from the previous section. However, operating it requires detailed knowledge of downstream services, which tends to place ownership with platform teams.

Edge Composition

The fourth approach runs the fan-out at a CDN point of presence close to the user. First-byte latency is the best available in this approach. Also, stitching together mostly cacheable fragments works well there, since much of the content can be served without contacting the origin.

However, there are constraints.

Edge runtimes offer limited compute and a restricted set of APIs compared with a normal server environment. More significantly, internal services are usually not reachable from the edge without crossing the public internet, which can increase the latency. Also, fanning out to four origin services from an edge location thousands of kilometres away produces four expensive round trips, which is the situation client-side composition already had.

Edge composition performs best when a large proportion of the composed content is public and cacheable. It performs worst when most of the response is personalized and assembled from services sitting behind an internal network.

Versioning Constraints

Every consideration so far has been technical. However, the constraint that most often decides the outcome is not technical, but related to versioning.

Web clients update when a page reloads, so a contract change reaches every user within minutes. Mobile clients cannot be forced to update, and installed versions can keep calling the version they shipped with for months or years. Third-party integrations are stricter again, frequently covered by written stability commitments and deprecation windows measured in quarters.

One contract serving all three scenarios is dependent on the pace of the most constrained consumer. For example, removing a field that a two-year-old mobile version reads means breaking that version or waiting for installs to age out.

There are three solutions to this, and each has a trade-off:

  • Versioning composed endpoints is simple to reason about, but it multiplies the number of endpoints that must keep working indefinitely.

  • Never removing anything and only adding new fields is the most common approach in practice, but it produces responses carrying fields that have not been used for years.

  • Client-specified field selection moves the problem to field-level deprecation, which requires usage tracking to establish when a field is unused.

Differing release cadences are also why per-client layers appear at all. A shared API blocks client teams, so the layer splits per client. Integration points multiply as clients and services both grow in number. A unified graph collapses that surface, and operating it moves ownership toward a central team, at which point client teams are waiting again.

There are five questions that can help make the decision:

  • How many round trips does a solution remove, and over which network?

  • Which upstream calls are genuinely required, and what happens to the rest during a failure?

  • What proportion of the response is personalized?

  • How quickly can each client change its contract?

  • Which team can carry the operational load for the layer?

Summary

In this article, we’ve looked at the API composition problem and its strategies in detail. Here are the key learning points in brief:

  • Composition follows from splitting data across services, because no query language crosses a network boundary. A composition point is any code that fans out to several sources and merges the results.

  • Services are organized around business capabilities and screens around user journeys, and the two never align.

  • Client-side composition is the default placement, running over the slowest network with the least observability.

  • Round-trip count dominates latency more often than payload size, which is why adding a server hop often reduces load time.

  • Aggregation runs calls in parallel and costs roughly the slowest branch, while orchestration chains dependent calls and costs the sum.

  • Requiring every upstream call multiplies availability downward. Sorting dependencies into required and optional keeps a composed response usable during failures.

  • Composed personalized responses cache poorly, so composition trades cache hits for fewer round trips.

  • A gateway becomes a shared bottleneck once it holds product logic for one client.

  • A backend for frontend works because it is not shared, which makes duplication between layers a deliberate trade.

  • GraphQL relocates the merge into resolvers and brings N+1 batching, application-level caching, and unpredictable load with it.

  • Release cadence sets the outer limit, since clients that cannot be forced to update make their contracts effectively permanent.
