Schema Evolution: Changing the Contract Without Breaking What Runs

A schema change is usually one of the most difficult types of change for a software system. However, it might look quite small and simple in review. For example, it might be something as simple as a column being renamed, or a new field being added to a particular event, or a response payload dropping a field that was not being used.

To make matters more complicated, the migration goes smoothly and cleanly during the staging phase, but unrelated services and components start failing as soon as the change is deployed to production. On investigation, it is found that nothing was wrong with the migration itself. But it took effect while two versions of the application were still running against the same database, and only one of those versions referenced the modified schema.

This situation is common with schema-related changes. It is also not limited to the deployment window. For example, rows written years ago can get produced by application code that has since been replaced. The messages sitting in a queue were published before the current version of the consumer was written. Mobile app versions from eighteen months back are still installed on real devices and still calling the API. In each case, data written under a particular schema version is read under a different version, resulting in multiple issues.

In this article, we will look at schema evolution and strategies for the same. Here’s what we will cover:

  • Why more than one schema version is always in play at the same time

  • Backward and forward compatibility

  • Which changes break consumers, which do not, and the qualifiers that decide it

  • Expand and contract migrations

  • Schema registries and their use

  • How the same problem differs across databases, APIs, and event streams

  • Versioning strategies and deprecation timelines

Version Overlap

A running system does not contain a single version of its code due to the following reasons:

  • Rolling deploys: New instances start while old instances are still serving traffic. Both types of instances read and write the same database and queues until the rollout finishes.

  • Stored data: A row written multiple years ago was serialized by code that no longer exists in the repository, and no deployment can upgrade it.

  • Third-Party Clients: Installed mobile versions and partner integrations keep calling the old API version for years even after a newer version ships.

  • Asynchronous messages: A message is written at one time and read at another, sometimes much later, and sometimes twice if a topic gets reprocessed.

Only the first reason is temporary in nature. The other three reasons make version overlap a permanent feature of the system rather than a brief inconvenience during releases. This is the reason better deployment tooling does not remove the problem. Also, issues caused by schema changes don’t show up during staging, since a staging environment runs just one version of the application against recent test data.

Compatibility Direction

Compatibility is not just a property of the schema. It is also a property of a pair of versions together with the direction of data access.

There are four combinations of producer and consumer version:

  • First is old code reading old data.

  • Second is new code reading new data

  • Third is backward compatibility, which means new code can read data written by old code. It reaches back toward data that already exists.

  • Fourth is forward compatibility, which means old code can read data written by new code. It covers older code coping with data produced after it was written.

The guarantee a schema change provides determines the deployment order of the components. For example:

  • A backward compatible change requires consumers to be upgraded first, since the new consumer handles both the old data in circulation and the new data arriving later.

  • A forward compatible change lets producers go first, since existing consumers can already process the new output.

Compatibility checks also tend to compare a proposed schema only against the previous version, so a chain of valid changes can produce a schema that cannot read the oldest records.

Schema Resolution

Decoding a record involves two schemas rather than one: the schema the data was written with and the schema that the reading code was compiled against. The decoder uses the following two rules:

  • A field present in the data but absent from the reader’s schema is discarded.

  • A field present in the reader’s schema but absent from the data is populated with the default declared in that schema.

These two rules support most compatibility guarantees. Adding a field with a default is safe because the default value is substituted for records written before the field existed. Without a default, there is nothing to substitute.

Field identity introduces a second variable, since some formats match fields by name and others by number. For example:

  • JSON and Avro match by name, so a rename is processed as a deletion followed by an addition, and old data no longer resolves to that field.

  • Protobuf matches by number, with the name serving as a local label, so a rename does not cost any bandwidth on the network. The tradeoff is that reusing a number previously assigned to a different field causes old data to decode into the wrong field. This is why retired numbers can be reserved permanently.

Breaking Changes

It becomes easy to classify once the resolution rules are clear, provided the qualifiers stay attached to it.

Some changes are safe almost everywhere:

  • Adding a field is safe when it is optional and carries a default, since the decoder can put a default substitute value for records written before the field existed.

  • Adding an entirely new endpoint, table, or topic is safe because no existing code references it. A nullable column behaves the same way, since earlier rows are left with no value and are not treated as an error.

  • Accepting a wider range of input than before is safe for the same reason, because callers already sending valid data keep working unchanged.

The breaking changes fall into two groups. The first removes something a reader depends on. For example:

  • Deleting or renaming (if the format matches fields by name) a field that a consumer reads, since the decoder resolves it as a deletion followed by an addition.

  • Making an optional field required also has the same effect, because it invalidates every write process that left the field blank.

The second group redefines a field that stays as it is. For example:

  • Changing the type or its cardinality (single value to a list) of a field breaks readers written for a specific type of value even though the name of the field wasn’t changed.

  • Narrowing validation rejects input that used to be accepted, which breaks the callers still sending it.

  • Change of units or meaning under an unchanged name, because the record decodes cleanly and no error is reported.

Lastly, enum values can fall into both groups. Adding a value is additive and passes nearly every automated check, but a consumer with an exhaustive branch over the enum will fail or take an incorrect path when an unfamiliar value arrives. Ultimately, safety depends on how consumers were written, which the producing service cannot inspect.

One question that might pop up at this point is this: Why is adding a field to an API response almost always safe, while adding one to an API request can break every caller?

Both of them are additive changes, both amount to one line in a schema file, and both look nearly identical in review.

The answer is that input contracts and output contracts break in opposite directions. For data flowing inward, meaning requests and commands, adding a required field is breaking because existing callers will not send it, while removing a field is usually safe because unneeded input can be discarded. On the other hand, for data flowing outward, meaning responses and published events, adding a field is usually safe because unrecognized fields are discarded during decoding, while removing one is breaking because consumers may be expecting that field.

Expand-Contract Migrations

Knowing that a change is breaking does not remove the need to make it. However, it changes the sequencing, since a breaking change has to be decomposed into steps that are each safe to deploy on their own. For example, a change about renaming a database column runs in the following manner:

  • Add the new column as nullable. No code references it yet, so the change is invisible to the application and easily reversible.

  • Deploy code that writes to both columns. Reads still take place from the old column, so new rows carry the value twice while older rows carry it once.

  • Backfill the existing rows. This copies the value into the new column for every row written before the previous step.

  • Verify that both columns agree. A mismatch means the dual write or the backfill missed something. It costs far less to find this out now than later.

  • Deploy code that reads the new column. Writes still go to both, so reverting the deployment restores the old read path immediately.

  • Deploy code that writes only to the new column. The old column stops receiving values, so rolling back more than one step leaves a gap.

  • Drop the old column. This is the only step that cannot be undone without restoring from a backup.

Each step has to be compatible with the one before it. This is because rolling back more than one deployment during an incident is rarely practical. The first three steps are the expand phase, the middle three the migration phase, and the last three the contract phase.

The middle steps depend on writing the same data to two places. Within one row of one database, this is quite straightforward, because a single statement can update both columns atomically. However, across separate systems, such as a database and a search index, there is no shared transaction, so one write can succeed while the other fails, resulting in divergent copies. The outbox pattern can handle this by recording the intent to perform the second write into the same transaction as the first, after which a separate process dispatches those records. Also, change data capture removes the second write from the application by deriving it from the database’s own change log.

The backfill step has an alternative. Instead of converting every row up front, the reading code can convert old records as it meets them. Backfilling is a bounded one-time cost with operational risk on large tables, while converting on read is cheaper. But it also leaves the code handling both formats for as long as unconverted records remain.

Schema Registries

A schema registry stores schema versions centrally and checks proposed changes against previous ones before they reach production. There are three parts to this process:

  • Schemas are stored by subject with a version number and a short identifier, which the producer embeds in every message instead of the full schema.

  • A consumer reads the identifier, retrieves the writer’s schema, and resolves it against its own.

  • At the time of registration, the registry compares the proposed schema against previous versions and rejects anything that violates the configured rule.

The registration check is the key value addition of this process. Without it, an incompatible change will surface only when a consumer fails in production. With this check in place, the producer’s deployment fails immediately and reports which rule was violated. At this point in the change process, the failure has a minimal cost.

Despite the advantages, there is a limit to what any such check can catch. For example, a field whose units change from cents to dollars, or seconds to milliseconds, can keep the same name and type. It passes every automated check. However, downstream calculations then produce results wrong by a factor of a hundred, with no error raised anywhere. The common defense mechanism for such scenarios is to name fields based on their units and add a new field instead of redefining an existing field.

Versioning Strategies

Databases, APIs, and event streams present the same problem when it comes to versioning:

  • The first is how much control a team has over the code that reads its data

  • The second is how long data written under an older schema survives.

Different scenarios vary when dealing with this problem:

  • Internal service APIs: Callers are known, and requests are transient, so a coordinated breaking change across the affected teams is workable.

  • Public APIs: Callers cannot be enumerated. The client code written against a version can persist for years, which pushes toward explicit versions and formal deprecation windows.

  • Mobile clients: Old application versions can stay installed on devices indefinitely, so the server side should remain compatible with releases that were shipped years earlier.

  • Relational databases: A team controls all of the code. Every row ever written is still readable, which makes expand-contract mandatory.

  • Event logs: Consumers can be deployed independently, and messages can be reprocessed from the beginning. This pushes toward registry enforcement and a declared default on every field.

API versioning splits into two families that have opposite trade-offs.

  • Explicit versioning attaches an identifier to each version and permits incompatible redesigns. This comes at the cost of maintaining every version still in service.

  • Additive-only evolution never bumps a version and permits only non-breaking changes. This avoids proliferation but makes early design decisions permanent.

Deprecation Timelines

The final step of any migration is removal of the old stuff. In practice, it frequently does not happen and is pushed aside for more pressing priorities. Here are some reasons:

  • Removal produces no visible improvement, so it competes poorly against work that does.

  • The outcomes are that nothing happens or that something breaks, which makes the risk asymmetric.

  • Confirming that nothing reads a field requires usage data at field and endpoint level, which many teams do not collect.

  • Nothing fails if the step is skipped, so there is no signal that it was skipped.

The result is visible in even many mature codebases.

Columns exist that have been null for years, endpoints remain in service for a single caller nobody has identified, and event fields marked as deprecated are still populated because no producer is confident enough to stop populating them.

A few practices can help make the removal of unnecessary schema elements a reality:

  • Instrumenting field-level and endpoint-level usage can turn the argument into a measurement.

  • Agreeing on a removal date during the expansion schedules the work while the context is still fresh

  • Treating removal as part of the original work rather than a follow-up ticket keeps it attached to the developer who understands it.

Window length has no correct answer.

Short windows force migration, but can generate conflict with the teams affected. On the other hand, long windows are easier to agree to and reduce urgency, but much of the migration lands in the final week. The real failure is when there is no window at all. In that case, nothing is going to make the removal happen, and the schema would end up with technical debt.

Summary

In this article, we’ve looked at the concept of schema evolution in detail. Here are the key learning points in brief:

  • More than one version of the code is always running. Stored rows, queued messages, and installed clients make this permanent rather than a deploy-window issue.

  • Compatibility is a property of a pair of versions plus a direction, not of a schema by itself.

  • Backward compatibility means new code reads old data, and forward compatibility means old code reads new data. Anchoring on the new version keeps them apart.

  • The compatibility guarantee determines deployment order, with backward-compatible changes requiring consumers to be upgraded first and forward-compatible changes allowing producers to go first.

  • Decoding uses two schemas. Unrecognized fields are discarded, and missing fields are populated from the default declared in the reader’s schema.

  • Adding a field is safe only when it is optional and has a default, and adding an enum value is an exception automated checks will not flag.

  • Input contracts and output contracts break in opposite directions. Adding a required field breaks requests, and removing a field breaks responses.

  • A breaking change becomes a sequence of deployable steps, each compatible with the one before it. Rollback remains available until the final removal.

  • Structural checks validate field names, types, and presence. But they cannot detect a change in units or meaning.

  • The removal step is skipped often enough that its cost should be planned at the start. However, below a certain scale, the process can be more expensive than the problem.
