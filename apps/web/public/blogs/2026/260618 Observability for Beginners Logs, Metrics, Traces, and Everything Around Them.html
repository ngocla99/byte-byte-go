Observability for Beginners: Logs, Metrics, Traces, and Everything Around Them

A running service generates events constantly.

Requests arrive, functions run, errors appear, and each one is a thing that happened at a specific time with a specific context and a specific outcome.

Logs, metrics, and traces are three ways of looking at this same stream. A log captures one event as a line of text, a metric counts or aggregates many events, and a trace links related events as they move across services. Most of the concepts in observability, including cardinality, sampling, and correlation, are consequences of this structure.

In this article, we will look at the basics of observability in detail with concepts like logs, metrics, and traces explained in detail.

Events

An event is a structured record of something that happened in a service, with three core components:

  • A timestamp records when it happened.

  • A set of context fields captures the surrounding conditions, including which service produced it, which version of the code was running, which user or session it was tied to, and which endpoint or function was involved.

  • An outcome describes what actually happened, whether that is a success or failure, a latency number, a return value, or an error code.

Consider one example. A user with ID 4127 sends a request to the /checkout endpoint of a payments service running version 2.14. The request takes 380 milliseconds and returns a 500 error.

That single event can appear in three different places. As a log entry, it might be written out as a structured line capturing all of those fields. As a metric, it contributes a “+1” to a counter for failed checkout requests, and the 380 millisecond value is added to a latency histogram. As part of a trace, it becomes one span in a larger tree showing how the checkout request flowed through the payments service, the database, and any downstream services.

Each view comes with its own strengths and tradeoffs. In the sections that follow, we look at each one in turn in more detail.

Logs

Logs are the most familiar of the three. A log is a record of one event, written out in a form that a human can read later. Most developers have spent a lot of time searching through them, looking for a clue about why something went wrong.

There are two broad approaches to writing logs:

  • An unstructured log is a free-form line of text, often built by concatenating strings together. It reads naturally to a human, but treats every log entry as opaque text, which means asking later questions like “how many requests from user 4127 errored in the last hour” requires hoping that the right substring appears somewhere in the text.

  • A structured log carries the same information as a record with named fields. The user ID is a field called user_id, the latency is a field called latency_ms, and so on. Once a log is structured, it can be queried, filtered, and aggregated the way structured data normally is.

Log levels are a related concept. Most logging libraries support levels such as DEBUG, INFO, WARN, and ERROR. The intent is that DEBUG is for details useful during development, INFO is for normal operational events, WARN is for things that are not yet wrong but worth knowing, and ERROR is for actual failures. Levels become useful when a team uses them consistently, because they then act as a runtime verbosity control. A noisy DEBUG stream can be enabled while investigating a problem and turned back off afterward, without changing the code.

There is a limit to how much logging helps. Past a certain volume, logs become noise that drowns out their own signal, and storage costs start to matter significantly. The practice of choosing what to log is at least as important as the choice of logging library.

Metrics

Metrics emerge when the question shifts from what happened in a single event to how often events occur across a larger population.

A metric is an aggregation, normally a counter that increments, a gauge that holds a current value, or a histogram that summarizes a distribution. Where logs let us read one event at a time, metrics answer questions like “what is the current error rate across all requests” without scanning anything.

Most metric systems allow dimensions, sometimes called labels or tags, to be attached to a metric. A request counter might carry dimensions for the endpoint, the HTTP status code, and the region. Each unique combination of dimension values becomes its own separate time series in the underlying storage. A counter with one dimension that has six possible values produces six time series. Adding a second dimension with fifty values brings the count to three hundred, and adding a third dimension with ten values pushes the total to three thousand.

This is the property called cardinality, and it is an important concept to understand about metrics in practice. When the dimensions are low-cardinality and bounded, such as status codes, regions, or environment names, the time series count remains manageable. When someone adds a dimension that is high-cardinality and unbounded, such as user IDs, session IDs, request IDs, or anything that grows with traffic, the time series count can grow by a factor of millions within hours.

The storage and query cost scale with the number of distinct series, not with the number of metric points written. This reflects the architecture of time-series databases, which store one numeric value per timestamp per series and are optimized for that pattern, rather than any pricing decision.

The practical point is that high-cardinality context belongs in logs or traces, not in metrics, regardless of how convenient it would feel to tag every metric with the user ID and slice the dashboard by customer. Cost overruns in observability typically trace back to a developer adding a label that seemed harmless at the time.

Traces

Metrics describe how often things happen across all requests, while tracing addresses what happened to one specific request as it moved through several services.

A trace is a tree of related events called spans. Each span represents one unit of work, normally a function call, an outbound network request, or a database query. Spans have parent-child relationships, so a trace forms a tree showing how one inbound request fanned out into all of the work it triggered downstream.

For this to work across services, every service in the chain has to agree on the same identifier for the request. That identifier is called a trace ID, and propagating it (normally by passing it through request headers as the request moves from one service to the next) is called distributed context propagation. Without that propagation, the spans from each service remain isolated and unrelated. With it, all the spans from one request combine into a single tree, no matter how many services touched the request.

Real systems produce more requests than any tracing backend can afford to store. Sampling is the practice of deciding which traces to keep. There are two broad approaches, and they involve different tradeoffs.

  • Head sampling makes the decision at the start of a request, before anything interesting has happened. The decision is normally based on the trace ID itself, which means all services in the chain agree about whether to record this trace, and the system is cheap to operate. The cost is that some of the traces thrown away will turn out, in hindsight, to have been the interesting ones.

  • Tail sampling makes the decision after the trace finishes, when its complete shape is visible. The system can keep all errors, all slow requests, and a random sample of the rest. The cost is that every span has to be buffered until the decision is made, which is operationally more involved and more expensive at runtime.

Monitoring

These three views of an event stream raise a question about purpose, since the answer determines how the data gets used.

Monitoring is the practice of checking known conditions on known systems. Common monitoring checks ask whether the database remains reachable, whether the error rate stays under one percent, or whether the queue depth holds within its normal range. Each of these is a question that someone thought to ask in advance, encoded as a check that runs continuously and pages someone when the answer goes wrong.

Observability is the broader ability to ask new questions of a system, including questions that nobody anticipated when the system was built. When something behaves strangely for one specific user in one specific region after a deploy, monitoring will not have a check for that exact case. Observability is what lets a team interrogate the running system, slice the data by dimensions that were not predicted to matter, and find the answer.

The relationship between the two is that monitoring is a subset of what observability data enables. Mature systems need both. A team that treats observability as a replacement for monitoring will be caught the first time a routine check that would have fired three months ago no longer exists. A team that treats monitoring as sufficient will be caught the first time something unusual happens that nobody anticipated.

Alerting

Alerts exist to bring human attention to situations that require it. A useful filter is the 3 am test. If an alert fires at 3 am, would there actually be something for the responder to do about it, and would the situation be serious enough to justify being woken up?

Most alerting setups fail this test because they alert on causes instead of symptoms. Common examples include alerting when CPU climbs above 85 percent, when memory exceeds 80 percent, or when disk usage approaches capacity. Each of these conditions can be true without anything actually being wrong from the user’s perspective, and each can be false while something serious is happening that does not show up in those particular numbers.

The mature pattern is to alert on what users actually feel, such as latency on the main user-facing endpoints, error rate on critical flows, and request success rate on the operations that matter to the business. When one of those signals goes wrong, something problematic is happening, and the responder has somewhere meaningful to start the investigation. Causes such as CPU and memory still earn their place, but as evidence to investigate once a symptom alert has already brought someone into the situation.

The distinction matters a lot. Teams that page on causes end up with an on-call rotation full of false positives, and the consequences are familiar. Developers can stop reading alerts carefully. Important alerts get missed, and burnout follows. Alert fatigue is a measurable phenomenon and one of the most common contributors to slow incident response and to engineers leaving on-call roles entirely.

Dashboards

Dashboards consolidate the views that a team needs to reference repeatedly.

A useful dashboard answers a specific question that someone actually asks regularly, such as how the latency profile of the checkout flow compares to last week, or what request volume looks like for a particular service in a given region. Questions of this kind have answers that are worth pinning to a screen.

A useless dashboard is built in panic during one incident, packed with every chart that seemed possibly relevant at the time, and then left untouched. Within a few months, nobody looks at it. The team has accumulated visual clutter that no longer maps to any question anyone is actively asking. By that point, the dashboard has become useless.

The approach that works is to treat dashboards as frozen questions rather than as data exhibits. Before adding a panel, the test is whether someone will repeatedly want to ask the question that the panel answers. If the answer is yes, the panel earns its place. If the answer is that it seemed interesting once, the panel is not very useful.

A related observation is that the questions worth freezing into dashboards change as the system itself changes. Teams that take their dashboards seriously revisit them on a regular cadence and prune the panels that have stopped being asked about. Adding panels is easy, but deleting them takes real discipline.

Summary

In this article, we have looked at observability in detail.

Here are the key learning points in brief:

  • Logs, metrics, and traces are three views of the same underlying stream of events. They are projections of the same data, taken at different levels of aggregation and stitched together by different identifiers.

  • Structured logging changes what can be done with logs later, because named fields can be queried, filtered, and aggregated in ways that free-form text cannot.

  • Log levels are a runtime verbosity control, and they only work as intended when a team uses them consistently.

  • Cardinality is the structural property that decides what belongs in metrics. Each unique combination of dimension values becomes its own time series, and high-cardinality dimensions can multiply the count by orders of magnitude.

  • High-cardinality context belongs in logs or traces, not in metrics, regardless of how convenient it would feel to tag everything by user or session.

  • Distributed tracing rests on two ideas. A shared trace ID propagated across services makes spans relatable, and sampling decides which traces are worth keeping.

  • Sampling is unavoidable at any real scale. Head sampling is cheap and consistent across services, while tail sampling keeps more of the interesting traces but is operationally harder and more expensive.

  • Monitoring checks known conditions on known systems, while observability lets a team ask questions that were not anticipated. Mature systems need both, and treating either as a replacement for the other is a mistake.

  • Alerts should fire on what users feel, not on what the system reports about itself. Alert fatigue has a measurable cost on incident response and on the people who carry the pager.

  • Dashboards become wallpaper unless they are tied to specific questions that someone actually asks. The discipline lies in pruning panels that no longer get used, not in adding new ones.
