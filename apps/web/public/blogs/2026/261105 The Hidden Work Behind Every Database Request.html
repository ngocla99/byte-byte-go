The Hidden Work Behind Every Database Request

∙

Mostly, an application’s storage system has to do work only when users make requests to that application.

However, there’s a difference between the work requested and the work that the storage system has to perform. A storage system does extra work as well, which is equally important. It can help you find data quickly, recover data after a crash, or support concurrent transactions. But this extra work also has a cost. For example, the request might involve reading a small record, but it can require fetching many blocks of data. Or when the user requests an update to some value, it can trigger multiple writes in the storage system. Also, if you want to keep the dataset highly available, it might require much more space than the actual size of the dataset.

Read amplification, write amplification, and space amplification show the differences between logical work and physical cost. In this article, we’re going to look at these differences in detail. Here’s what we will cover:

  • What is logical work and physical work in a database

  • Read amplification

  • Write amplification

  • Space amplification

  • The amplifications with B-trees

  • The amplifications with LSM trees

  • How indexes and filters use space to avoid reads

  • How compression helps improve amplifications

  • The role of caching

  • The impact of amplification

Logical Work and Physical Work

You can think of logical work as the work that an application asks the storage system to do. For example, an application might ask for a 128-byte record. Physical work is the work that the system has to do to satisfy that request. For example, the storage engine may need to find that record using an index. It might have to fetch a larger block of data that contains that record and decompress that block.

The application just receives the 128-byte record. But the underlying work done by the storage system is much more.

Three types of amplifications can help you understand the gap in a better way.

First, you have the read amplification that measures how much data you need to read to find the requested data. Next, you have the write amplification that measures how much data you’ve to write to perform the requested write. Lastly, you have the space amplification that takes care of how much space you need to represent the live dataset.

Let’s look at each of these amplification types in more detail.

Read Amplification

In storage engines, you generally organize data into pages or blocks. These are like units for transferring, caching, and managing data. But they are usually larger than an individual field or record.

Let’s say you have a 128-byte record that sits inside a 4 KiB block. If you have to fetch the entire block from storage to get the record, the read amplification factor is 4096/128, which comes to around 32X. In this calculation, we aren’t including any additional reads that might be needed to find the block. For example, you might have an index lookup that first accesses navigation pages before reaching the page that has the actual record.

Read amplification also happens when a query checks many records and returns only a few. For example, an application searching for orders with a particular status might have to scan a large table if there’s no access path. The storage engine has to do a lot of work to find out that most records don’t qualify.

Caching changes the physical cost of read amplification. For example, if you have to access 10 pages that are already in memory, you just need 10 logical page reads. But there’s no need to read from the storage devices. The CPU still has to do the work. However, the storage traffic disappears.

Write Amplification

You might have a database write one record, but this write operation can affect multiple records. For example, the system might have to write recovery-related information, maintain index tables, flush modified pages, and reorganize data.

One common contributor to write amplification is the write-ahead log (WAL). With WAL, your database records a good deal of information to recover a change before the data pages are stored in durable storage. Those pages can be written later. Or multiple modifications can be part of the same page flush request. To summarize, a WAL adds a stream of writes while also enabling efficient batching and crash recovery.

For example, let’s say you have an application that creates 100 MB of logical writes as part of some request. If the database internally generates 700 MB of storage writes to deal with that workload, the write amplification is 7X.

A lot of this write amplification work is done eventually. Some work might happen before the application receives success from the storage engine. But a lot of work might also happen later. A database can acknowledge a write quickly but generate a lot of background I/O afterward.

Space Amplification

Space amplification is when a database stores more than the current records. For example, let’s say you have a database containing 100 GB of logical data, but it might occupy 160 GB after including indexes, metadata, old versions, and unused space. As you can see, the space amplification is 1.6X.

You might think of space amplification as an overhead. But it provides a lot of useful features. As you might already know, indexes provide additional access paths for faster data retrieval. Spare room inside pages helps accommodate future inserts. If we keep older versions of records, the transactions can read a consistent view.

Space amplification is not static. It changes over time. For example, a rewrite or compaction may need both old files and their replacements. Your capacity planning must take the peak possibility into consideration.

The Amplifications with B-trees

We often say that B-trees have read amplification, while LSM trees have write amplification. This is a little misleading. In truth, both structures show all types of amplifications. However, the respective designs have an impact on the trade-offs and costs.

A B-tree organizes keys into a hierarchy of pages. You have internal pages that help narrow the search into an appropriate range. On the other hand, leaf pages contain entries at the bottom of the tree. Each internal page can point to many children so that a large dataset can be managed in a pretty shallow tree.

While doing a lookup, you may need to go through several pages. However, frequently accessed upper-level pages often get cached so that the lookup can be done fast.

Write operations cause their own amplification. For example, if you change a small entry, you may make a much larger page dirty that eventually needs writing. However, buffering can help combine multiple such changes so that a single update doesn’t trigger an immediate full-page rewrite.

When an entry no longer fits, the B-tree may split a page and move the entries around for a better arrangement. It will also update the parent records. These operations can generate additional writes. Also, partially occupied pages result in space overhead.

As you can notice, B-trees do a lot of work in maintaining an ordered structure so that navigating and finding data is fast and easy. The amplification sources depend on the locality of new updates, caching, and page occupancy.

The Amplifications with LSM Trees

Log-structured merge (LSM) trees accept writes in batches and reorganize them later.

In a typical LSM tree implementation, you place the incoming writes in an in-memory structure called a memtable. When the memtable gets full, the storage engine writes the contents from the memtable into a sorted file on storage.

Due to this arrangement, you can turn many small updates into a group of larger, sequential writes. This is why LSM-based engines have strong write throughput.

However, as you can see, updates might result in multiple versions of a data record. Older versions are also kept in files, and the storage engine accumulates several sorted collections. Hence, space amplification.

This increases the cost in multiple dimensions. For example, while reading, you need to check several collections to find the correct version. Older versions take up space. Eventually, the storage engine has to merge files and throw away information that might not be required.

This merging process is known as compaction. In compaction, we read existing files and create replacement files. A record might go through multiple compactions during its lifetime. This is write amplification. In other words, we use an LLM tree for efficient writes, but it still rewrites data many times.

Compaction is also of two types. Level compaction and tiered compaction.

With leveled compaction, your files are arranged into levels. Key ranges within each nonzero level don’t overlap. This places a limit on the number of candidate files for a lookup within a level. To maintain this setup, you need to merge incoming data with overlapping data that’s already stored.

With tiered compaction, you can have several sorted collections coexisting before being merged. This reduces rewriting as compared to leveled organization. But you need to search more collections. Also, more storage overhead.

How Indexes and Filters Use Space to Avoid Reads

Developers have to deal with amplification trade-offs even when they create a new index.

For example, let’s say you have a product query that finds an item using an identifier and sends back its price. A basic index can help locate the row quickly. But you can also have a covering index that includes the price so that the query can get the information directly from the index.

While this removes the need for table access, you need to have an additional structure. If there’s a change in the price, you need to maintain that structure. In other words, saving work related to read requests comes at the cost of storage and update work.

A Bloom filter makes a smaller, more specialized trade. It’s a compact structure that can tell you whether a key is present in a particular collection. If there’s a probability of the key being present, the engine can check further. When used with LSM trees, Bloom filters can help you avoid reading files that definitely don’t have the requested key. Adding more space for the filter can reduce false positives. Also, unnecessary reads. However, making such a filter consumes work.

How Compression Helps Improve Amplifications

The common idea about data compression is that you are lowering space amplification for higher read or write amplifications. That’s not the whole story.

If the same data takes up fewer bytes due to compression, the system has to potentially store less, read less, and write less. You pay the additional cost in terms of CPU time.

The main decision is the size of the compression unit. Let’s say you have a 64 KiB block that is compressed to 16 KiB. Imagine that a request needs a 1 KiB record inside it. A cold read operation might fetch the compressed 16 KiB block and decompress the full 64 KiB. As you can see, the physical read size is way smaller than fetching the uncompressed block, but it still transfers more than the requested record.

If you choose a larger compression unit, you can improve compression while making small accesses less selective. If you go for smaller compression units, you get more targeted access. But you also need more metadata, and the compression may be less effective.

The Role of Caching

Cache reduces the need for repeated work by storing data or results for reuse. By using a cache, you can avoid executing a database query. A database block cache can avoid storage reads while the storage engine still runs the lookup.

Let’s say you have a query that needs four storage reads when uncached. If a cache serves 90% of the requests and cache misses have the same cost, the average becomes 0.4 storage reads per application request.

Though this is a good level of reduction in storage access, the cache also occupies memory. This is known as memory duplication. To keep cached values useful, you also need maintenance. If source-of-truth values are updated, you also need to refresh cached entries or invalidate them.

Adding a cache doesn’t always worsen the other types of amplifications. It might exchange storage reads for RAM and additional application work. A write-back cache can reduce downstream writes by combining several updates.

The Impact of Amplifications

Read amplification consumes read operations, bandwidth, and CPU. In contrast, write amplification takes up write bandwidth, maintenance CPU, and SSD endurance. Space amplification increases the capacity that must be used.

The impact on cost depends on the kind of service. Some systems charge for operations or transferred data. Others might charge for capacity, throughput, or the number of instances.

Latency depends on where the work is executed. If you have additional dependent reads, the request might be extended. If you run compaction activities in the background, you can have faster individual writes initially. However, as utilization goes up, queues can cause an increase in latency.

The access pattern of the data has an impact on the latency as well. If you transfer a larger amount sequentially, it might be faster than performing many smaller random accesses.

Lastly, you have space pressure that can affect performance by leaving less room for maintenance. If you have a system with a size only good enough for its compacted dataset, you might struggle to create the next compacted representation.
