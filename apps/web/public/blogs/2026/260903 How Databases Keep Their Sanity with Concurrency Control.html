How Databases Keep Their Sanity with Concurrency Control

Imagine a bank account with $100. Let’s assume that two separate withdrawal requests of $10 each arrive at the same moment. However, after the two withdrawals are made, the account still ends up $90.

On a purely technical level, both withdrawal requests completed successfully. There was no error. But the account balance is wrong. The remaining balance should have been $80.

On its own, both transactions were correct. Each read the correct balance and performed the correct calculations. And yet, there is a bug. The reason for this bug was the overlap between the two transactions.

You might think this type of overlap is a rare condition. However, this is not true. Overlapping transactions are more or less the normal condition in which databases operate. At any given point in time, multiple processes are trying to write something to a database, often on the same set of records. It just takes two of them to collide with each other inside a window of a few milliseconds for these types of bugs to show up.

So how do we handle such bugs?

How Data Gets Corrupted Due to Multiple Transactions?

A transaction is a group of database statements that are treated as a unit. A single transaction can have both reads and writes combined into a single unit. At the end of the transaction, either the changes are made permanent (committed), or everything goes back to the previous state (rolled back).

A transaction’s key promise is that all of it happens or none of it does. It’s a great property to have. You could have a power cut, a killed process, a bad disk, but the transaction maintains a consistent state.

However, things can get problematic when multiple transactions act on the same data concurrently. Let’s understand using the simple example from earlier:

  • Consider an initial account balance of $100.

  • Two withdrawal requests of $10 each arrive at almost the same instant. Let’s call these transactions W1 and W2.

  • W1 begins first and reads the balance. It gets $100.

  • A fraction of a millisecond later, before the W1 transaction has written anything to the database, the second transaction W2 starts and reads the balance as well. It also gets $100.

  • Then, W1 withdraws $10 from the account and writes the account balance as $90.

  • At the end, W2 also withdraws $10 from the account and writes the account balance as $90.

As you can see, the second write didn’t get combined with the first write. Though we had two withdrawals of $10 each, the remaining balance should be $80. Instead, we end up with $90. This is, of course, a pretty simple example, but it explains how data can get corrupted due to multiple transactions.

4 Ways Concurrency Causes Data Issues

Multiple transactions overlapping in time can cause different types of issues. Let us look at each of them in more detail:

1 - Lost Update

This is more or less the example we saw earlier. The diagram below shows it more clearly:

Here’s what happens:

  • An account holds $1000.

  • Transaction A deposits $200 and Transaction B withdraws $100.

  • Both read the balance at roughly the same time and get the account balance as $1000.

  • A calculates the balance as $1200 and updates the same value to the database.

  • B calculates the balance as $900 and updates the same to the database.

Both are wrong because the actual account balance should have been $1100. Technically, both the transactions computed correctly based on the value they fetched from the database. But still, it appears that the second transaction erased the impact of the first transaction. This is why we call it the “lost update” scenario.

2 - Dirty Read

Assume that we have a product with 10 units in stock. Transaction A starts reducing that to 3 units, but has not committed yet. While Transaction A is still working, Transaction B reads the stock information and finds out that there are only 3 units available. Based on that, it sends a message to the user that says “only 3 units left”.

Then, transaction A rolls back because of some issue, and the stock units revert back to their original value of 10.

As such, nothing is wrong with the database. The rollback worked fine. The stored value is also correct. But incorrect information was sent out during this time, resulting in reporting errors and other business impact. This happened because transaction B fetched a value that existed only for a brief moment. In other words, it was a “dirty read”.

3 - Non-Repeatable Read

Consider a scenario where transaction A is building a monthly product report. As part of its requirement, it fetches the details of product XYZ and gets a price of $500. It carries on doing other work.

Meanwhile, transaction B comes along and modifies the price of product XYZ to $650. It also commits the data. Later on, the reporting transaction (Transaction A) fetches the data for product XYZ for some more calculations. It is the same row and the same query. But this time, it gets the price as $650.

In other words, the same transaction got two different answers for the same data point.

You might think this scenario is similar to a dirty read. But it has one important difference. It is the fact that transaction B actually committed. This means that both $500 and $650 were actual committed price points for the product XYZ. It’s just that they were across different time periods. This is why this scenario is called “non-repeatable read”.

The impact of this scenario can show up in reporting aspects. Let’s say a report uses $500 for some sort of summation operation on a bunch of products and $650 for printing information about a specific line item. In such a case, the total won’t match the individual line items.

4 - Phantom Read

Consider a scenario where we have a transaction that runs a query to fetch all orders above $1000.

Assume that it fetches two rows: Row#1 at $1250 and Row#2 at $1800. Later on, the same transaction runs the same query once more. This time it gets three rows. This is because another transaction inserted another order of $1400 and committed it. In other words, now three rows satisfy the query’s requirements.

This case is different because neither of the existing records was modified. But a new record came into the picture that matched the search condition. This scenario is called “phantom-read,” and it is much harder to prevent.

To stop a non-repeatable read, the database can put a lock on the rows that are read and not allow any other transaction to change them. But in a phantom read, the row cannot be locked because it doesn’t exist yet.

Different Ways to Handle Data Conflicts

All of the data conflicts we discussed in the previous section arise from the same core reason. A transaction reads a value, spends some time doing something with it, and then writes it to the database. In the period between the read and the write, another transaction comes in and does something with the data.

The solution is to close this gap. There are two popular ways of closing this gap. Both involve using locks.

The lock is not a physical thing attached to the data record. Think of it more like a note that the database keeps for itself that helps it remember if a particular record is being used by some other transaction.

Let us look at the two types of locking approaches in more detail.

Block Everyone Up Front (Pessimistic Locking)

This approach assumes that conflicts are highly likely. Therefore, it pays an upfront cost to prevent them from causing issues. Here’s how it works:

  • Assume that two customers are being served against the same account.

  • Transaction A runs “SELECT … FOR UPDATE”, which tells the database that the transaction is going to write this row. Therefore, the database can lock the record exclusively for Transaction A.

  • Transaction B runs the same statement on the same row. It does not fail or receive an error. It waits. In other words, from the perspective of transaction B, the database has gone silent.

  • Transaction A finishes its update and commits. The lock is released.

  • Now, transaction B is granted the lock, and it is able to read the data value.

  • Since transaction A has already finished, the value transaction B reads is not stale. In other words, B never gets the chance to read an out-of-date value.

The trade-off with pessimistic locking is the wait time. Every transaction that is queued behind a lock is waiting. One slow transaction holding the lock can bring many other transactions to a halt. Ultimately, throughput goes down.

Another problem that can occur in pessimistic locking is around deadlocks. Let’s say transaction A locks row XYZ and then asks for row PQR, while transaction B locks row PQR and then asks for row XYZ. Both are asking for something that the other is holding. Both end up waiting forever. In this case, the database picks one transaction and terminates it with an error that has to be handled by the code.

Pessimistic locking is a good choice when transactions are short-lived, and lots of them hit the same rows.

Gamble and Check Afterwards (Optimistic Locking)

The optimistic locking approach assumes that conflicts are rare. Therefore, it avoids paying an upfront cost to prevent them. But to handle things, this approach uses version numbers.

Let us take the same example of an account having a balance of $1000 with a version number of 7. Here’s how it works:

  • Transaction A reads the record and gets the value $1000 with version 7.

  • Transaction B reads the same record and gets the same value and version. In other words, neither transaction waits because there is no locking.

  • Both transactions now do their work. Let’s say transaction A adds $200 and transaction B subtracts $100 from the account balance.

  • Now, transaction A writes the updated value first. But this time it is not a plain update. It writes $1200 where the version number is equal to 7. Since the version number is still 7, the row matches and the write operation is successful. The version number now becomes 8.

  • Next, transaction B writes $900 where the version number is equal to 7. However, the version number is no longer 7. There is a mismatch and no rows are updated.

The database does not raise an error. Both statements ran perfectly, but they didn’t conflict with each other. It’s just that transaction B would then need to read the row against. This time it gets $1200 and version 8. It once again performs the calculation and tries to update the record with the new version number.

The trade-off in optimistic locking is mainly around wasted work. Every rejected work means that we have to redo all that work once more. For a workload with lots of transactions, more time can be spent retrying rather than waiting in a queue.

Optimistic locking is the right approach to use when conflicts are rare. It also resembles how humans work more closely. A user opens an edit form for a record and might walk away for a meeting. It is impractical to lock that record for the entire time the user is away. It is better to let other transactions update the record. Later on, when the user comes back and tries to update, the system can prompt that the record has been modified and reload the new version for the user.

How Databases Stopped Making Readers and Writers Wait for Each Other?

Pessimistic and optimistic locking work quite well for scenarios where two transactions are trying to update the same record. But there is another common source of conflict: one transaction that only reads, but reads a lot.

If we use locks, a sample report that scans a large table for several minutes might hold read locks on a bunch of records for quite a long time. Every write transaction has to wait. In other words, a query to build a dashboard can take the database offline for all other work.

Fixing this requires thinking about rows in a different way. We need to account for the fact that a row can hold more than one value at different points in time. If we only consider one value, then a read transaction and a write transaction have to wait for each other.

This is why many databases stopped overwriting rows. They use an approach known as MVCC or Multi-Version Concurrency Control.

In the case of MVCC, an update operation doesn’t change the existing record. It writes a new version of the record and leaves the old version as it is. Each version carries a tag specifying which transaction was used to create it. This means that over time, a record can end up with a chain of versions. The current value happens to be the latest value that was committed to the chain.

But this is not the complete picture.

In MVCC, when a new transaction starts, it also takes a snapshot. Think of it like a note that explains which transactions have committed as of the exact instant. Every subsequent read operation uses this note to only fetch data from versions that were committed before the snapshot was taken. Any versions that may get created after the snapshot are invisible to this transaction.

Here’s how it works:

  • Let’s say Reader R1 begins at t20. The balance is $1000. It is stored as version 1. Therefore, R1’s snapshot is fixed at t20.

  • At t24, the Writer W does something. It doesn’t touch version 1 but creates a version 2 that has the account balance as $1200. The version is committed.

  • The record now has two versions in its chain. However, Writer W didn’t have to wait for R1 to finish. Also, it wasn’t like R1 was holding a read lock.

  • Meanwhile, R1 is still running. Every time it reads the record, it still gets $1000. This is because version 2 was created after its snapshot was taken. It is basically referring to a correct and consistent picture of the database as it existed at t20. This is great for reporting purposes.

  • Let’s say Reader R2 begins at t30. This is after Writer W has committed. Therefore, R2’s snapshot includes the commits made by W. It can see version 2 and reads the account balance as $1200.

With MVCC, readers never block writers, and writers never block readers.

Many modern databases, such as PostgreSQL, MySQL’s InnoDB, Oracle, and SQL Server in snapshot mode, work in this way. The trade-off here is around the need for additional storage to store multiple versions. A version is labelled as garbage only when no active transaction can possibly see a version. Such garbage versions are cleaned up by a background job.

Also, write operations can still block other write operations. Two transactions that want to update the same record have to be put in the correct order. MVCC doesn’t solve this.

Picking the Right Level of Data Protection With Isolation Levels

Ultimately, protecting data from conflicts is a setting with multiple controls. We need to choose the right level of data protection. This is done using isolation levels.

There are four main isolation levels:

  • Read Uncommitted: This offers no protection. One transaction can see another transaction’s unfinished work. This includes work that might get rolled back a moment later. Everything is possible here, including the dirty-read scenario.

  • Read Committed: This isolation level guarantees that we only see values that are actually committed. It is done by taking a fresh snapshot for every single statement. This removes the dirty-read scenario from the picture. However, since each statement gets its own snapshot, two statements inside the same transaction can get different values. This is mostly the default setting in databases like PostgreSQL, Oracle, and SQL Server.

  • Repeatable Read: In this isolation level, one snapshot is taken at the start of the transaction. The same snapshot works till the end of the transaction. Every read within the transaction gets the same data. This means that a row that has already been read cannot change. It can still allow phantom reads when new rows appear.

  • Serializable: In this isolation level, the outcome is the same as if each transaction has run one at a time. This is the strictest isolation level.

Serializable prevents all sorts of issues. But it also suggested locking everything, blocking all transactions, and accepting the slowness. From a practical point of view, this wasn’t acceptable.

PostgreSQL, however, shipped a better approach known as Serializable Snapshot Isolation (SSI) for this particular isolation level. Think of it as serializability that is optimistic. It runs on top of ordinary MVCC snapshot isolation. Therefore, readers don’t block writers, and there’s no waiting. Instead, the database tracks the dependencies between them. For example:

  • Which rows or range of rows did each transaction read?

  • Did another transaction write to a record that a running transaction had already read?

The second question indicates that a transaction is working with stale data. This way, it can abort one of the transactions. Such transactions can then be retried. However, the application needs to handle these retries.

Summary

In this article, we’ve looked at concurrency in a database in detail along with various techniques. Here are the key learning points in brief:

  • A transaction can protect from a crash. But it doesn’t protect the data from another transaction running at roughly the same moment.

  • When two transactions read the same value and perform calculations from it, they can end up overwriting each other’s updates.

  • These types of conflicts usually appear only in production environments when real traffic causes a few milliseconds of overlap.

  • There are different types of anomalies when it comes to transaction overlap: reading uncommitted data (dirty read), a row changing while being used (non-repeatable read). New rows appearing in a result set (phantom read).

  • Pessimistic locking prevents conflicts by locking a record explicitly. Other transactions have to wait. This is safe but slow. It can also cause deadlocks.

  • Optimistic locking does not hold a lock on a record. It uses a version number to find out if a record being updated is stale.

  • MVCC is a technique that stops databases from overwriting rows. An update writes a new version while keeping the old version. This way, readers never block writers and writers never block readers.

  • The trade-off with MVCC is cleanup. Old versions cannot be removed while some transactions might still need them.

  • Isolation levels are a ladder. Read Committed only guarantees committed values, Repeatable Read keeps your rows stable, and Serializable promises the result will match some order of running everything one at a time.
