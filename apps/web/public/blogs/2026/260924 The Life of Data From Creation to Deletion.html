The Life of Data: From Creation to Deletion

A web application can appear quite simple from the outside. A user submits a form, the application saves the information within the form, and a screen displays it later when the user wants to see the information. When the information is no longer needed, the information can be deleted from the system.

However, inside a growing system, the same information or data point can exist in several places. For example, a database holds the original record. A cache might store a copy of that original record for faster access. A search engine index can store some fields of that record to make search more intuitive. An analytics pipeline might produce reports from it. Lastly, backups may preserve earlier versions of that record.

Each of these copies has its own purpose, update schedule, and overall lifetime within the system.

The lifecycle of data shows how information can enter a system, become useful, spread to other components, become old or stale, and eventually be deleted. Thinking about this lifecycle helps connect decisions that might otherwise seem separate, such as database design, performance, reporting, storage costs, recovery, and privacy.

In this article, we are going to look at the entire data lifecycle from creation to deletion and the decisions that need to be taken at each step.

Creation: Deciding What Information Should Exist

Data starts to exist in a system when we need to record an observation, action, or decision. For example, a user may want to store a delivery address, a temperature sensor takes a measurement, or a service wants to record that a background task it was monitoring has failed.

The first design decision is what to collect. It comes even before the choice of storage. Let’s say an application needs to determine whether someone meets a specific age requirement. So should it store the complete date of birth of the person or just whether the person meets the age requirement? Storing the person’s complete date of birth creates different responsibilities from storing a verified eligibility result. The right choice simply depends on what the application actually needs to do.

If we collect additional information, we end up creating additional work through the lifetime of that information. That information needs validation, protection, documentation, storage, and eventual deletion. Therefore, every field or data point that we choose to store should have an understandable purpose.

The next decision deals with meaning. For example, a field called amount is ambiguous unless the system establishes its currency, whether it includes tax, and whether its value represents whole currency units or smaller units such as cents. Similarly, a timestamp needs a clear interpretation and time zone to make sense.

These meaning-related definitions are part of a schema, which describes the structure of data. A schema might specify that a record contains an identifier, a numeric measurement, a unit, and a timestamp.

Data also needs context about itself. This is called metadata. Useful metadata includes the source system, creation time, schema version, and ownership team. Recording this context early makes it easier to investigate any future potential issues.

Ingestion: Bringing Data Into the System

Ingestion is the process of receiving data from a source and bringing it into a system that will process or store it. The amount of data that can be ingested depends on the type of request:

  • An HTTP request can ingest a single record.

  • A file upload can ingest thousands of records.

  • A messaging system can continuously deliver events from other applications.

Two common approaches are batch ingestion and streaming ingestion:

  • Batch ingestion collects data into groups. For example, a supplier’s nightly inventory file.

  • Streaming ingestion processes a continuing flow. For example, location updates from multiple delivery vehicles.

The approach we choose for ingestion largely depends on how quickly the receiving application needs the information.

Also, receiving data reliably involves more than just parsing it. Let’s say we have a service that sends a notification that a payment has completed. The receiving application stores the notification. But its response never reaches the sender because of some network problem. This means that the sender has no way of knowing whether the notification was processed. With no other option left, it sends the notification again.

If the system we’ve built cannot handle duplicates, the receiver might end up recording the same payment twice. A simple solution to handle this assigns each event a stable identifier and makes processing idempotent. This means that processing the same event again has the same effect as processing it once.

Ingestion also needs clear acknowledgment rules. An acknowledgment saying “Accepted” might mean that the data has reached a durable queue and will be processed later. It might instead mean the final database update has completed. Applications need to clearly distinguish between these promises so that there are no grey areas.

Finally, the time an event occurs can differ from the time it arrives at the receiver application. For example, a sensor device that reconnects after an outage may upload yesterday’s measurements today. We should keep both event time and ingestion time so that the reports don’t confuse delayed information with new activity.

Validation: Deciding Whether the Data is Usable

Once data has been ingested, the application still needs to determine whether it is acceptable for its intended use. Different types of validations help with this.

Structural validation checks the shape of the data. It answers questions like:

  • Are required fields present?

  • Is a quantity a number?

  • Does a date have a supported format?

  • Is an uploaded file of an allowed type and size?

Business validation checks whether the information makes sense within the context of the application. For example, a valid return request must address an existing purchase. A booking’s end time must be after its start time.

These checks serve different purposes. Even if we have a perfectly structured request, it can still describe an invalid operation.

Validation also has limits. For example, an email address can have a valid format while belonging to someone else. A sensor reading can fall within an acceptable range while being inaccurate because the sensor is faulty.

Passing through the validation stage means the data satisfies specified checks. However, it doesn’t prove that every claim made by that data is valid in the context of the system.

If a validation fails, we also need a specific outcome. An interactive form can immediately return an error to the user. However, during a large import, invalid records might have to be put into a restricted quarantine area so that they can be investigated and corrected. This quarantine area needs its own retention policy, because rejected records can still contain sensitive information.

Validation also continues after the initial ingestion of data. This is because a transformation on the data can introduce errors, and a previously reliable source can change its behavior. A daily feed that suddenly contains mostly missing values may be technically readable but operationally useless.

We need to have checks on completeness, freshness, duplicates, and unexpected changes to detect these problems.

Storage: Choosing a Home that Matches How Data is Used

After the data has been accepted, it needs storage appropriate to its purpose. Some points worth keeping in mind are as follows:

  • A relational database suits many applications that manage structured records and relationships.

  • Object storage commonly holds files such as images, recordings, and exports.

  • A data warehouse supports analysis across large datasets.

  • A cache keeps selected information readily available to reduce repeated work.

These storage mediums organize information differently because the expectations differ. For example, looking up one customer’s current subscription details is a different task from calculating subscription trends across several years.

This is why there is often a distinction made between operational data and analytical data. Operational data supports an application’s everyday actions. On the other hand, analytical data supports investigation and reporting. A service that has to respond quickly to individual requests can struggle if the same database also performs large historical scans.

The design also needs an authoritative location for each important kind of information. This location is often called the source of truth. For example, a product service may own the current product description. A search engine contains a representation of that description to support searching. If the values are not the same, the system needs a defined rule for which one takes precedence in a particular scenario. We can also distribute authority across services.

Lastly, storage design also includes concerns such as durability, access permissions, and recovery. A stored record should be able to survive the failures the system is designed to handle, and only appropriate users and services should access it. These responsibilities continue even when the record moves into another storage system.

Transformation: Creating Useful Information From Existing Data

Data within a system is not static. Stored data often needs to change into different forms before another part of the system can use it.

Data transformation includes functions like converting formats, standardizing units, joining datasets, removing duplicates, calculating values, and generating summaries. Often, many smaller components come together to perform these functions. A sequence of such programs is commonly called a data pipeline. For example, electricity meters might produce readings every few seconds. Next, a reporting pipeline groups those readings by household and calculates hourly consumption. Another pipeline might combine the hourly results into monthly totals.

In the above example, the hourly and monthly datasets are derived data. This is because they originated from other lower-level data. But eventually, they turn into datasets with their own storage, users, and lifecycle decisions.

Transformations also introduce an important question: what happens to the derived data when the original data changes?

If a faulty meter reading is corrected at some point, the hourly calculation done before the correction may need to be updated. Next, we need to also correct the monthly total. In other words, correcting the original record alone doesn’t automatically repair every derived result that uses that original record. This is why pipelines often support reprocessing, which means running the transformation again over existing inputs. However, reprocessing needs to avoid adding duplicate results or accidentally mixing outputs produced by different calculation rules.

Two common terms describe where transformation occurs:

  • ETL means extract, transform, and load. Data is transformed before entering the destination.

  • ELT means extract, load, and transform: Data enters the destination first and is transformed there.

If we retain the original inputs, it can make corrections and reprocessing easier. However, raw data still needs a defined purpose and lifetime. The possibility of future reprocessing doesn’t automatically justify keeping every input data forever within the system, as storage costs money.

Replication and Copying: How One Record Becomes Several Responsibilities

Replication maintains additional copies of data so that a system can tolerate failures or distribute reads. If one database server becomes unavailable, another server may continue serving requests.

There are two main ways to replicate data:

  • With synchronous replication, a write waits for specified replicas to acknowledge it before the system reports success to the client or user.

  • With asynchronous replication, the primary server can acknowledge the write before replicas catch up.

The latter reduces waiting but allows a period during which different servers may hold different versions. That time period is called replication lag. It explains why recently updated data can occasionally appear unchanged when a subsequent request reads from a lagging replica.

Other types of copying data serve different purposes:

  • A cache avoids repeatedly fetching or calculating information.

  • A search index organizes selected fields for searching.

  • A warehouse copy supports analysis.

  • A backup preserves information needed to recover from damage or mistakes.

A live replica usually receives valid delete operations from its source. However, it offers limited protection against an application accidentally deleting the wrong records. A backup from before the mistake serves a different recovery purpose.

Copies also need reliable update mechanisms.

One approach is change data capture (CDC). In this approach, we capture database changes and make them available to other systems. For example, tools like Debezium can capture database changes and feed pipelines that update search engines, warehouses, or caches.

However, receiving a change doesn’t guarantee that a destination applies it correctly. For example, a pipeline might handle inserts but overlook deletions, or stop updating after an error.

Lineage: Informing the True Source of a Field

As data moves through multiple pipelines, it can become quite difficult to determine its origin.

Imagine a dashboard containing a field called net_spend. It might originate from purchase amounts, subtract refunds, exclude canceled transactions, and group the result by customer.

Finding the table that contains net_spend answers where the value is stored. Explaining how it was produced requires a lot more information.

Data lineage records the relationships between sources, transformations, and outputs. This helps them supports investigation in both directions. Starting at the dashboard, a developer can trace backward to the source inputs. Similarly, starting at refund records, the developer can also trace forward to the outputs affected by a change.

Lineage can exist at different levels:

  • Dataset lineage identifies the tables or files that feed another dataset.

  • Column lineage identifies which input fields contribute to a particular output field and how they are used.

Real data-related investigations also need to know about transformation version, execution time, and relevant business definitions. For example, a field calculated under last year’s rules may differ from the same field calculated today.

But why is this information hard to recover?

Let’s say one team copies a table. Another team renames its columns. A scheduled script adds calculations. Someone exports a spreadsheet and manually adjusts it. Eventually, the connection between an output and its origin exists only in scattered code and people’s minds.

To prevent this, we need properly documented ownership and definitions. We also need records of pipeline inputs and outputs. Automated lineage collection helps, but manual exports and unsupported processing tools can still leave gaps.

Lineage also has a limit. Knowing that one table depends on another doesn’t necessarily identify every row belonging to a particular person. Deletion of data can require additional identifiers and mappings across systems.

Hot, Warm, and Cold: How Access Needs Change

Data often becomes less frequently accessed as it ages. For example, the latest application logs may be searched repeatedly during an incident. However, logs from several months ago may be consulted occasionally. Older logs might be retained only for a specific historical need.

It’s not a great idea to keep all three groups in equally expensive storage. This is where we can divide the data storage into tiers.

  • Hot Tier is for frequent reads or updates, often with immediate responses required. The design priority is for fast access and sufficient processing capacity.

  • Warm Tier can be used for occasional access, with less demanding performance needs. The design priority is around lower costs while remaining accessible.

  • Cold Tier is for rare access, often for historical retrieval. The priority is around low ongoing storage cost with accepted retrieval tradeoffs.

Keep in mind that these are relative categories, not universal hardware types or fixed age ranges. Different systems may implement them differently. For example, cold storage doesn’t always mean slow retrieval. Some storage classes support immediate access while charging differently for retrieval. Others require a restoration step.

Moving between tiers requires considering total cost. Lower storage charges may come with retrieval charges, minimum storage durations, or additional operational work.

Lastly, age is only a convenient signal for likely usage. A 10-year-old document can become heavily accessed during an investigation. On the other hand, a newly uploaded file may rarely be read.

Retention: Deciding How Long Data Should Live

A retention policy defines how long a type of data is kept, why it is kept, and what happens when that period ends.

Different categories need different policies. For example, temporary processing files, diagnostic logs, customer profiles, and accounting records each serve different purposes. Assigning one lifetime policy to everything is not a great idea.

A good policy also needs a clear starting event. “Keep for 90 days” is incomplete unless the system specifies 90 days after creation, last activity, contract completion, or another event.

For example, an illustrative policy might keep diagnostic logs for 30 days after creation and temporary exports for 24 hours after generation.

When we copy or transform a record, we should not accidentally restart its original retention clock. Otherwise, a pipeline that regularly rewrites data might end up keeping the data indefinitely.

Retention decisions need to balance operational needs, recovery needs, contractual requirements, and legal obligations. Some requirements might establish a minimum period for keeping particular records. Others may require deletion when a purpose ends.

Once the policy is decided upon, it needs robust implementation. Common mechanisms include scheduled deletion jobs, object-storage lifecycle rules, and time-to-live (TTL) settings. At larger scales, retention can also influence physical organization. Grouping records into daily or monthly partitions, which are separately managed portions of a dataset, can make bulk expiration efficient. Removing a whole partition is appropriate only when all its contents are eligible for deletion, and any required exceptions are handled.

Archival: Preserving Information for Occasional Use

Archival moves information out of everyday operational use while preserving it for a future need. For example, documentation for a completed engineering project may be moved out of an active collaboration system but remain available for later maintenance work.

An archive needs more than just inexpensive storage. It needs a way to locate information, understand its format, establish its origin, and retrieve it within an acceptable time. For example, a file named export_final_7.csv is difficult to use years later without a description of what this file is about.

An archive also differs from a backup. An archive is needed to support deliberate access to selected historical information. In contrast, a backup supports recovery after failure, corruption, or mistakes. They may use similar storage technologies, but their organization and retrieval workflows can differ substantially.

Archival also needs verification. Before removing an operational copy, a migration process can check that the archived records are complete and readable. A checksum, which is a calculated fingerprint of content, can help detect unintended changes during transfer. Lastly, archived information still needs ownership and access control.

Deletion: Why Removing a Record Has Several Meanings

A delete action can mean several different things depending on the layer involved.

For example, soft deletion preserves the record. With soft deletion, the application marks a record as deleted while retaining it:

UPDATE documents
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = 42;

In this case, ordinary application queries exclude records with a deletion timestamp. This supports features such as a recycle bin or an undo period.

The information remains stored and can still be accessible to administrative tools or queries that don’t apply the filter. Soft deletion therefore needs a separate process if permanent removal is required after the recovery period.

Database deletion changes what current queries can see. A database delete removes the record from the current logical contents of the table:

DELETE FROM documents
WHERE id = 42;

This still does not guarantee that every underlying byte disappears immediately. A successful delete and an immediate reduction in disk usage are therefore different outcomes.

Tombstones record that a deletion has occurred. Some storage systems represent deletion by writing a tombstone, which is a marker indicating that an earlier value is deleted.

This is a useful approach when copies can temporarily disagree. If one replica misses a deletion while offline, the remaining replicas need evidence that the record was deliberately deleted. Simply finding the record absent can be ambiguous. The tombstone allows the deletion to propagate when replicas synchronize. Removing that marker too early can allow an outdated replica to reintroduce the old value.

Object storage introduces another variation. In a versioning-enabled object store, expiration of the current object can create a delete marker while preserving previous versions. Removing those older versions requires the relevant version-deletion actions or lifecycle rules.

Completing Deletion Across Downstream Systems

Deleting from the authoritative database is only one part of deletion when information has spread. Let’s say a publishing platform removes an author profile. However, a search index may still contain the biography. Also, a cache may still serve the profile page. An analytics table may contain the author’s contact details. An earlier export may contain another copy.

These are downstream copies because they received information from an earlier source or pipeline.

A reliable deletion process must identify relevant destinations and apply the appropriate action in each. Some destinations remove records directly. Others rebuild a derived dataset without them. Related records may need deletion or field-level removal while preserving information that has a separate justified purpose.

The workflow must also survive partial failure. If the database deletion succeeds but the search service is unavailable, the deletion may remain incomplete. Recording progress allows the system to retry the unfinished work safely later on.

Old events can create another problem. A delayed profile-update message might arrive after the profile has been removed. If the receiving service blindly applies it, the profile can reappear. Version checks, deletion state, or other ordering controls need to prevent stale activity from reversing completed deletion.

Lastly, we also need to carefully deal with derived data. For example, replacing a person’s name with a stable code is pseudonymization if the information can still be linked back to them. It doesn’t automatically make the dataset anonymous. Aggregated results also require consideration of whether individuals remain identifiable.

Backups: Preventing Recovery from Reversing Deletion

Backups are particularly challenging because they intentionally preserve earlier states of the data.

Let’s say we take a backup on Monday, followed by a valid deletion on Tuesday. If the system restores Monday’s backup on Wednesday, the deleted information can return.

Selective removal from a backup may be difficult, especially when the backup is a large snapshot or is designed to remain unchanged. Therefore, we need an explicit policy for how backups interact with deletion.

One approach is to use a bounded backup lifetime. It tightly restricts access and ensures that deleted information doesn’t return to ordinary use. A specific design can maintain a restricted record of completed deletions and reapply them while restoring data from the backup before reopening the restored system to normal access.

Recovery testing should therefore check more than whether an application starts successfully. It should also verify that previously deleted information stays unavailable after restoration, replay, and rebuilding of downstream systems.

Summary

In this article, we’ve looked at the lifecycle of data from creation to deletion in detail. Here are the key learning points in brief:

  • Data starts to exist in a system when we need to record an observation, action, or decision.

  • Ingestion is the process of receiving data from a source and bringing it into a system that will process or store it.

  • Once data has been ingested, the application still needs to determine whether it is acceptable for its intended use.

  • After the data has been accepted, it needs storage appropriate to its purpose.

  • Data transformation includes functions like converting formats, standardizing units, joining datasets, removing duplicates, calculating values, and generating summaries.

  • Replication maintains additional copies of data so that a system can tolerate failures or distribute reads.

  • Data lineage records the relationships between sources, transformations, and outputs.

  • A retention policy defines how long a type of data is kept, why it is kept, and what happens when that period ends.

  • Archival moves information out of everyday operational use while preserving it for a future need.

  • The lifecycle of data becomes manageable when its decisions are explicit, and its behavior is observable.
