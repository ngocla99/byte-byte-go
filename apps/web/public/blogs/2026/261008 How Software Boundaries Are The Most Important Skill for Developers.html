How Software Boundaries Are The Most Important Skill for Developers

No matter how big a software system gets, it will still have a boundary. This boundary separates things inside the system from those outside it. In fact, you’d have noticed that dividing a large system into multiple components can have some great benefits. However, deciding how the system should be divided requires skill and understanding. Experience is the best teacher in such cases. But there are also some strategies that can help.

But what exactly does a boundary do?

A good software boundary keeps an application’s responsibilities, its rules, and the details needed to apply those rules together. Parts of the system outside this boundary can talk to things inside the boundary only through a clear pathway. This means that the skill of deciding boundaries requires you to have an idea of which responsibilities should be bunched together. Also, which dependencies should exist between them.

In this article, we’ll learn some key strategies that can help a developer make the right boundary-related decisions for the systems they are working on.

What Does a Software Boundary Control

As we talked about earlier, a software boundary separates a set of responsibilities from the rest of the system. It defines the permissible ways for components outside that boundary to talk to things inside the boundary.

For example, you can have a document storage component that exposes operations to save, retrieve, and delete documents. Internally, it does many things, such as choosing filenames. Or managing storage locations. Or handling file compression. However, other components outside this boundary can use it without depending on whatever internal choices have been made. For them, it’s just like a service that helps them store documents.

The good thing with this approach is that you can change the storage component without any impact on the other components. For example, you can modify the compression algorithm of the storage component. But there is no impact on the external components using this compression feature. You can think of this interface as a sort of agreement about what that feature will do. No need to expose any internal details.

Different boundaries can help with different types of agreements:

  • Module Boundary: It controls which implementation details can be accessed by other code. For example, you can have a payroll module that exposes pay calculations. But it keeps the calculation internals and rules private.

  • Service Boundary: It controls how components that run independently communicate and evolve. For example, you can have a video processing service that takes in new jobs through an API or queue.

  • Data Ownership Boundary: This type of boundary controls who owns a piece of data and their update rules. For example, the catalog owns product descriptions. Inventory owns available quantities.

  • Transaction Boundary: It controls which database changes succeed or fail together. For example, a flight booking transaction might create a flight booking and record its seat allocation together.

  • Security Trust Boundary: It controls which identities, permissions, and user inputs require verification. For example, you might have a server that verifies a browser request before letting users access a specific document.

  • Team boundary: It controls who owns decisions, delivery, and operation. For example, you can have a billing team that owns everything billing-related and all its interfaces.

In a production system, these boundaries can sometimes overlap. For example, we can have one service made up of several modules. It might execute many different transactions. Similarly, we can have a team that owns several services. A security boundary can exist between customers using the same application.

The main thing that you should take away is that we can’t expect one architectural division to solve every kind of separation need.

How Cohesion and Coupling Help Draw Boundaries

Before any sort of implementation, we need to make sure that a boundary makes sense. And for this, we need to know about two important concepts: cohesion and coupling.

Cohesion talks about how strongly the responsibilities inside a component belong together. For example, we can have a payroll module that calculates earnings, applies payroll deductions, and produces payment slips. All of these features have a single purpose. All the concepts and rules take care of the same goal. We can think of it as a module with high cohesion.

On the other hand, a module that bundles features like payroll calculations, image resizing, and password reset logic has weak cohesion. Though we might implement all of these responsibilities using the same programming language or framework, their business purposes are totally different.

Therefore, cohesion is all about building meaningful relationships. You cannot group everything that uses a database into one module. It can create a technical grouping. But it’s not like all those responsibilities belong together logically.

Coupling deals with the dependencies between components. Let’s say you have a reporting component that calls a payroll operation to get a completed payment result. This makes the reporting component depend on the payroll operation. Now let’s say we have built the reporting component in a way that it can directly read payroll’s internal tables. It can make deductions and interpret payroll status and so on. Suddenly, we’ve made it quite hard to change the payroll module without changing the reporting module as well. In other words, we can say that the reporting module and payment module have a high coupling.

As you may have noticed, an ideal setup would strive for high cohesion and low coupling. It’s better to keep related rules inside one boundary. This reduces the amount of internal knowledge that leaks outside the boundary. We should build modules that hide design decisions. Especially decisions that are likely to change. This allows the impact of changes to stay local.

A good question to ask is this: when a rule changes, how much of the system needs to understand the change? If you’ve implemented the boundaries in the right way, the scope of the answer will be quite small.

The Right Approach to Implement Interfaces

Components expose specific capabilities using an interface. In an ideal world, the user of a capability should not have to understand how a component provides that capability. Everything is taken care of internally. These are known as “thin interfaces”. And they are an ideal way to build interfaces.

A thin interface exposes a capability in such a way that anyone calling it needs to understand very few internal details. You can think of thinness as the degree of knowledge that can cross an interface boundary.

Let’s say we have an inventory component that exposes the following functions:

getAvailableQuantity(productId)
setAvailableQuantity(productId, newQuantity)

Now, let’s assume you have a caller that wants to reserve some stock. If the caller uses these functions, they must first fetch the quantity. Next, they should decide whether enough quantity is available for them to reserve stock. They should then calculate the new value and write it back.

As you can see, it’s like the caller is now participating in the task of inventory management. Moreover, it must also handle the possibility that another caller can change the quantity between the time it reads the quantity and when it comes back to reserve the stock.

On the other hand, the following operation gives a more complete responsibility to the inventory component.

reserveStock(productId, quantity, requestId)

Now, inventory management can decide whether a stock reservation request is valid. It can do all the necessary updates. The caller just receives a reservation identifier or a failure result.

As you can see, this type of interface can hide a good amount of implementation details while still giving the caller all the information that it needs. However, you need to have good documentation that explains what the operation does. And what happens when there’s not enough stock. Or how multiple requests are handled.

Therefore, we can say that a thin interface brings together a limited set of concepts with precise behavior. In contrast, a single generic operation such as execute(anything) may require callers to understand dozens of hidden conventions. Even though we just have one method, there is little protection. To summarize, a boundary gets leaky when callers must know a ton of internal details to use it correctly.

Module Versus Service Boundaries

Module boundaries and service boundaries have different costs.

You can think of a module as a logical division within code. Depending on the programming language, you can implement a module through packages, namespaces, or libraries. A module boundary defines public entry points and private internals. Visibility rules, dependency checks, or build rules make this boundary stronger. For example, you can have a publishing application that has separate editorial, subscription, and delivery modules. It can still be one deployed application. This is known as a modular monolith.

Modules can have multiple technical layers. For example, let’s say there’s a subscription module that contains features such as request handling, business rules, and database access. Same for other modules. These technical layers manage implementation responsibilities. But the module groups a business capability.

On the other hand, a service boundary separates the runtime. We can have various components that talk to each other using network requests or messages. Deployments become independent of each other. When building microservices, you can commonly organize services around business capabilities. The idea is to reduce the change size for coordinated releases that touch large parts of the system.

You can unlock a lot of options due to this separation. For example, you can scale a video transcoding service based on demand. No need for the rest of the application to scale in the same way. It also changes the way failures take place. A local function call usually returns or throws an error within the same process. But a network request hits another service, completes successfully, and loses its response. The caller has an uncertain response.

All of this means that when you have network boundaries, you need to make decisions about timeouts, retries, and duplicate requests. Also, dependencies may be unavailable. With separate services, you also have to do more for deployment.

Implementing Boundaries Based on Meaning

Domain-driven design (DDD) is a technique that can help you create boundaries based around meaning. DDD starts with the business domain. This involves the activities, concepts, and rules a particular piece of software represents.

For DDD, you have to first create a domain model. You can think of a domain model as the software’s representation of all the concepts and rules that make up a system. A bounded context defines the scope of a particular domain model. The vocabulary inside this context is consistent. For reference, let’s say you have the word “product”. In merchandising, a product might have a title, images, descriptions, and promotional categories. But when taken to a warehouse, the same product might have other details like the storage location, physical dimensions, and handling requirements.

Both of these views belong to the same “product”. But they have different purposes. If you force both of them into a universal Product object, you end up with a large data structure that is filled with a bunch of fields and several rules that only a few consumers understand.

This is where you can have separate bounded contexts. For example, different contexts like merchandising and warehousing can maintain specific models that are more aligned to their work. These contexts can exchange identifiers and other information through some clear mapping rules.

To summarize, DDD allows the same business term to have different models in different contexts.

How Data Ownership Handles Responsibility

You cannot enforce ownership of code when other components can freely make changes to the data on which the code depends.

Let’s say you have a subscription service that controls the subscription status field. The status field has some transition rules. For example, we can have a trial subscription that becomes active. An active subscription might get cancelled. Or an expired subscription may require a new payment. If multiple applications (such as an admin app, a billing process, or a support tool) can update the subscription table directly, all these transition rules have to be implemented in all those applications. You cannot have a single enforcement point for these rules. Each component can add a status that the other components might not expect. This opens up the application to multiple issues and high-impact scenarios.

To prevent this risk, you need to create data ownership boundaries that package the responsibilities within a concrete wrapper. With such a boundary, you can give one component absolute authority over a specific data point. Other components can only request changes that go through the operations supported by the owner.

We can also have ownership applied to specific facts. For example, identity management owns login credentials. Billing owns an invoicing address. However, a broad label such as “customer data” can conceal several separate responsibilities.

The database-per-service pattern makes persistent data private to its owning service. You can implement this privacy using separate tables or schemas. You can also restrict database permissions. We don’t need to have a dedicated database server for every service.

This is different from the shared database pattern, in which you have several services that depend on table structure, update behavior, and locking. Any change to the schema can have a big impact on many services.

Multiple services can also use isolated schemas on a single database server. In this case, you get logical ownership of data. But infrastructure is still shared, and you have to deal with infrastructure failure risk.

One thing to note is that data ownership allows us to make copies of data. For example, you can have a search system maintain an index of product descriptions in a separate place. The catalog is still the authoritative source for those descriptions. Similarly, you can have an invoice show the price at the time of purchase, which is different from the price in the catalog.

How Transaction Boundaries Enforce Correctness

Transaction boundaries encapsulate the various database activities that should happen. A transaction groups database operations so that their changes commit together or are rolled back together. This way, we can protect against a process failing halfway through a set of updates that are related.

The main task for a developer is to decide which set of changes requires this guarantee. For example, let’s say you have a theatre booking system. Confirming a booking and recording its seat allocation are part of the same transaction. But sending the confirmation email can happen afterward.

To implement this correctly, you need suitable database constraints and concurrency control. You can’t just put a read and a write inside a transaction and hope for the best. It doesn’t prevent every race condition. The protection depends on the operations and isolation guarantees involved.

DDD uses aggregates to group domain objects whose consistency rules should be protected together. You can think of an aggregate as a more focused boundary than an entire bounded context or service. A service manages many aggregates and many individual transactions. When a rule needs immediate, coordinated changes on both sides of a boundary, you need to check whether that boundary is correct.

One way to handle such cases is distributed transactions. But they introduce many coordination and operational constraints. Another approach is to divide a large business workflow into local transactions and handle partial progress. For example, you can have a travel booking workflow that reserves a hotel and then attempts a flight reservation. If the flight reservation fails due to seat unavailability, the workflow might cancel the hotel reservation as well. This is known as the saga approach.

Following on from this, choosing transaction boundaries can also shape the entity. For example, in the case of a “product” entity, some workflows may need states such as “pending,” “confirmed,” or “cancellation in progress.” The design of the boundary determines which outcomes can be immediate and which ones require a process.

How Events Move Across Boundaries

Events change the dependency structure in a big way. But you cannot completely get rid of contracts.

Once components own their data, other components often need to learn when that data has been changed. For example, you might have a learning platform that publishes a “CourseCompleted” event. Certificate generation and analytics can process this event independently. The course completion operation doesn’t need to wait for both consumers to finish.

This gives a lot of flexibility. All the services don’t have to be available at the same moment. No temporal coupling. But the consumers still depend on the shared meaning of the event. You can think of this event as a public contract. So it’s not a great idea to publish an internal database row as an event. It can expose storage decisions just like direct database access can. We also need to cross a reliability boundary between updating a database and publishing the event. If the application commits the update, but crashes before publishing, consumers may never know that there was a change.

To handle this, you can use the transactional outbox pattern. In this pattern, you store the outgoing event in the same local transaction as the business update. A separate process can publish the event afterward. You can also publish the event multiple times so that there’s no chance a consumer misses the event. But the consumer needs to be able to handle duplicate events.

The Role of Security Boundaries

Security trust boundaries enforce authority and trust. They check which claims can be accepted.

In a typical flow, you can have a browser submit a document identifier, a customer identifier, or a requested operation. The server must make sure that the caller is allowed to perform the incoming operation on that particular resource. For example, if we have a user who can open one document, they must not automatically gain access to another document by simply submitting a different identifier.

Authentication is for verifying identity. Authorization is to check which actions a user can make. You need to have authorization checks for each relevant request and resource.

We have trust boundaries inside an organization’s infrastructure. For example, you can have an authenticated reporting service read selected records without being able to change payroll.

A code boundary and a security boundary need to be enforced in different ways. Private module members help us avoid accidental implementation-related dependencies. Credentials, authorization policies, database permissions, and process isolation restrict what a caller is capable of doing.

How Team Boundaries Impact Software Boundaries

Team boundaries can also have a big impact on the software boundaries.

Software changes take place because some person decided something about a system. Therefore, every technical dependency creates a communication dependency. Let’s say you have one team that owns all user interfaces, another owns all business logic, and a third owns all database changes. Even implementing a small feature might require planning and handoffs across all three teams.

Now consider another team that owns subscription management across all these technical areas. This way, many changes to the subscription management system can be handled within the team. There is a good amount of ownership.

Conway’s Law talks about the relationship between an organization’s communication structure and the structure of the systems it results in. The structure crystallizes who must communicate and coordinate. This can differ from the formal reporting hierarchy.

This creates pressure in both directions. We can have a tightly coupled system that forces teams to coordinate frequently. Also, a team setup that needs constant handoffs makes software ownership harder to manage. One way to reduce too many handoffs is to organize around a flow of work where responsibility is carried all the way to delivery.

The idea is to achieve a good level of coordination. You still need teams to share standards and agreements. They also need to collaborate sometimes. A sign of good alignment is that routine changes usually stay within one team’s decision-making scope. If there are constant negotiations over ordinary changes, it indicates that something is wrong in the way teams are structured.

How To Judge if a Boundary is Bad

Bad boundaries show up when there is friction. While we might have a design diagram that looks neat and clean, the running system is a mess. Only real changes and failures can reveal the true picture.

The following signs can help identify problems:

  • Two services exchange many small calls to complete one operation. A cohesive responsibility may be split, or the interface may expose too many small steps.

  • Callers reproduce another component’s business rules. The owning component’s interface may be incomplete or leaky.

  • A table change requires updates across several services. Storage details have become a shared contract.

  • There is a need to release services together. Their contracts or implementation dependencies prevent independent changes.

  • Several teams must be involved in approving even ordinary changes. This shows that technical responsibility and ownership may be poorly aligned.

  • Unrelated features end up modifying one common module. This indicates that the module may contain responsibilities with different reasons for changing.

  • A failure in an optional feature stops a critical workflow. This signals that runtime dependencies are not properly isolated.

These signals need to be interpreted. You can improve a chatty interface through batching or a more complete operation. It might also indicate that a rule belongs on the other side of the boundary. Or that two services would work better together. Similarly, coordinated releases might be because of a shared deployment process rather than unavoidable code coupling.

Summary

In this article, we’ve looked at boundaries in software design. Here are the main takeaways for developers:

  • Good boundaries emerge from understanding rules and observing change. A good design process starts with responsibilities and constraints.

  • First, we should identify the decisions each part of the system makes. For example, “calculate a shipping quote” is a much clearer responsibility than “handle shipping data.”

  • Next, we should identify requirements where immediate correctness is crucial. Rules that must be followed together have a big impact on transaction boundaries.

  • When different groups use the same term for different concepts, we may need to have separate models and a translation layer.

  • We should also check how changes happen, which team owns what, what the scaling needs are, and failure requirements. These help decide whether a logical module boundary should also be turned into a service boundary.

  • When the domain remains uncertain, we should keep a lot of responsibilities inside a modular application. This can make experiments less expensive.
