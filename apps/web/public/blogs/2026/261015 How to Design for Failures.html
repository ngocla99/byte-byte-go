How to Design for Failures

It is impossible to build a failure-proof software system. Sure, a system can go through its lifecycle without any failures. But you can’t provide a guarantee that it will never fail.

You might think that if we write perfect code, we can get rid of failures. But writing correct application code is just one part of the problem. Even perfectly written software depends on a physical computer, power availability, working storage, and so on. If the machine loses power, the software will fail no matter how good it is.

Therefore, you have to design for failure. This means deciding in advance how a system should behave when some of its parts are not working correctly. In this article, we’ll look at the various strategies that can help developers deal with failures in their systems. Here’s what we will cover:

  • Why adopt an “assume everything breaks” mindset

  • Avoiding faults vs tolerating faults

  • How to figure out the scope of a failure

  • How to reduce the impact of a failure

  • How to handle failures while running the system correctly

  • How to measure recovery from failures

Why Assume That Everything Can Break

As we talked about earlier, an application depends on more than its own code. You need processing capacity, storage, network connections, and many other services.

All of these are dependencies. And each dependency comes with its own set of conditions that can impact the application. For example, the database might respond slowly. Or an incorrect configuration change might send traffic to the wrong place. There could be a network problem that stops the response from reaching the caller. Or a dependency may respond with incomplete information. As you can see, every supporting component can fail in one way or the other.

To design for failure, you need a way to talk about the different ways a dependency can cause problems and how it might impact the users of the application. This is done using failure modes. Details are very important when defining a failure mode. For example, if you mention “the database fails”, it sounds too broad. “Database writes become unavailable while reads still work” gives a better idea to the developers.

It’s also important to determine the practical boundary for failures. You can build an application to tolerate the loss of one server, or an unavailable service, or a network interruption. But this doesn’t guarantee that the same application can handle the simultaneous loss of every server and every copy of its data.

All of these assumptions about failure modes and concrete details about them are known as a failure model. You can think of it as a set of conditions that a system can handle. Having such a model is much better than making vague claims such as “the application is highly available”.

Avoiding Faults vs Tolerating Faults

Failures occur because of one or more faults. But what is a fault?

You can think of a fault as a defect or abnormal condition that can make something go wrong. It might be a software bug, damaged hardware, or a broken network connection. A fault can be dormant for a long time before some condition triggers it to cause an application failure. For example, let’s say you have built a document processing service. There’s a bug in one of the processing workers that causes it to crash when it has to work with a particular file format. This bug is a fault. But it causes a failure only when a file of a specific type arrives.

There are two ways to deal with faults: avoiding faults and tolerating faults.

With fault avoidance, we try to reduce the likelihood of something going wrong. Some actions that can help are code reviews, validating inputs, planning for capacity, and configuration management.

In the case of fault tolerance, we try to build the system in such a way that it continues to work in an acceptable manner even when there’s a fault. For reference, in our document processing service, there might be other workers that can process the problematic file format. So, we can shift those types of files to other workers. The service as a whole works fine despite the fault in one of the workers.

To design for failure, you need both avoidance and tolerance. Preventing faults can help reduce the number of incidents. But you also need the system to have some tolerance to faults, along with ways of recovering. The overarching concern that deals with all of these aspects is known as resilience. It defines how the system deals with disruption, limits the effects of such disruptions, and recovers. We can hide some disruptions from users. For others, you may need to reduce functionality and wait for things to recover.

How to Figure Out the Scope of a Failure

To deal with a specific failure mode, you need to have a good idea about the scope of that failure. For example, let’s say two application processes are running on one machine. If that machine loses power, both processes disappear. You can move them onto separate machines. But those machines might still share the same power supply or network device. Or maybe they are hosted within the same data center.

This is where failure domains become useful. You can think of a failure domain as a group of components that can be affected by the same failure. They arise from software and operational dependencies. For example, ten servers might be running the same defective release of an application. They can all fail when they receive a specific input.

We also use the term blast radius to talk about the scope of a failure’s impact. It can be expressed in terms of customers, features, services, or data affected by the failure incident. While failure domains deal with shared exposure, blast radius gives an idea of how far the consequences might reach.

Let’s say you have an analytics platform. One customer submits a very expensive query. If every customer shares the same processing pool, the expensive query might slow down the entire platform and impact all the customers. But if the customers are divided into independent processing groups, the impact can stay within one group.

One of the architectural styles to support this is a cell-based architecture. It divides a workload into separate units known as cells. Each cell serves a subset of customers or requests. How to Reduce the Impact of a Failure

A key objective that drives the “design for failure” philosophy is to reduce the impact of a failure. One of the best ways to achieve that is isolation.

With the right isolation approach, we can create boundaries within a system that failures cannot easily cross. Let’s say you have an application that uses the same worker pool for online requests and large report exports. If exports run on every worker, ordinary requests might get stuck. By following the principle of isolation, you can separate the two workloads into different worker pools. One for online requests. Another for the exports. Now one type of work cannot consume all the resources.

This is also known as the bulkhead pattern. The idea behind this pattern is to partition resources in a way that even if resources are exhausted in one area, other parts can work.

You can also isolate the parts of an application based on customers. For example, in a multi-tenant setup, you can apply a limit on the number of concurrent jobs a tenant can run. Now, one tenant cannot monopolize the entire capacity.

This approach has some trade-offs. You can have reserved capacity sitting unused in one pool while another pool is struggling. Infrastructure costs are higher. Also, you need additional management to handle everything.

One more common approach for reducing the impact is to split an application into multiple services. But it also doesn’t automatically make everything isolated. You can still have separate services using the same database. They might depend on the same network resources. So a lot of work has to go into drawing the right boundaries.

Lastly, you need to pay attention to the change and deployment processes. New releases are one of the most common reasons faults get injected into a system. You might have code changes. Or configuration updates.

We can use canary deployments to reduce the impact of these faults. In this type of deployment, you expose a small amount of traffic to a change. This way, you can evaluate how things work before letting everyone access the change. If the new version behaves poorly, the rollout can be stopped. Of course, the change reversal process has to be also designed carefully.

How to Recover from Failures

After we’ve limited the spread of a failure using isolation, the next question is how the system can recover from a failure. We can use strategies like redundancy, replication, and backups.

Redundancy is having additional resources that can take over when needed. We want to avoid the situation where a capability depends on just one resource. If that resource becomes unavailable for some reason, the whole system goes down. We want to make things redundant. For example, you can have two application servers instead of one to make an application redundant.

However, redundancy works only when the remaining resources can truly take over when needed. For everything to work, we must have proper routing logic, sufficient capacity, and separation from failures.

For data and state, you can use replication to make things redundant. In replication, we maintain copies of data across multiple instances. These copies are known as replicas. A replica receives changes from the primary database instance so that it can stay in sync. The advantage of replication is that it can provide continuous data availability even after a machine fails for some reason. We can also distribute read requests across the different replicas to share resources.

Replication has two variations. See the diagram below

First, we have asynchronous replication. In this type, the primary instance can acknowledge a database update before the data has reached the replicas. This means that a change might never make it to a replica if the replica fails after the primary has acknowledged the change. This might sound like a problem. But it increases availability. Even if a replica has failed, we don’t have a problem. Also, latency is lower.

The second variation is synchronous replication. In this type of replication, the primary instance waits for acknowledgments from the replica instances before sending a confirmation to the caller. If the replica has failed, the update doesn’t work. This sounds more reliable. But it increases latency. Also, availability goes down because a failure in the replica can stop the system

Lastly, we have backups as another way of recovering from failures. Backups are meant to restore data after loss or damage. With backups, you can combine periodic snapshots with more recent change logs. Even databases with replication need backups. Also, we can still have a system with great backups go through a long outage while the data gets restored.

How to Manage Dependency Failures

Failures have an impact on the system. This impact radius goes up if a component waits for its dependency for too long. Or if it makes new calls too aggressively. For example, let’s say you have a delivery application that calls a slow map service. Since the map service is slow, each request has to wait for the response. Each request blocks some resources. Over time, the requests keep piling up, and the delivery application becomes unavailable.

We can avoid such situations with retries and timeouts.

A timeout limits how long a caller has to wait for an operation to finish. We can also have an overall deadline that caps the time available for the request. It can include multiple calls and retries. All of these limits have to be decided sensibly. You can have several individual wait times come together to produce a big total delay.

On the other hand, a retry is another attempt that we can make after the initial call fails. It rests on the premise that a failure might have happened due to some temporary problem. For example, a network issue.

But we should not retry every failure immediately. It can make things worse for an already struggling dependency. The best way is to come up with a retry policy that limits the number of attempts and how long to wait between each attempt. We can also add random variation between calls so that many clients don’t retry at the same time. This random variation is known as jitter. Lastly, it’s not a good idea to retry when the failure took place due to a permanent error. For example, invalid input. Or a fault in the service.

Sometimes, we also have to stop the flow of requests to reduce the impact of a widespread outage. One way is to use a circuit breaker. It can temporarily stop calls to a dependency if a certain number of failures occur in quick succession.

Another way is load shedding. We can reject selected work when letting everything come through might stall the system. Techniques like backpressure expect producers to slow down while producing new messages. You can place a queue to absorb a temporary spike of incoming messages or requests. However, the queue’s capacity is also limited.

In a real production system, we can use all of these techniques together to build an ideal setup for handling failures.

How to Handle Failure While Keeping Things Correct

Even if our system operates continuously despite failures, it’s useless if we cannot trust the results.

For example, imagine a payment request that is sent to a provider. The provider records the payment, but the response is lost due to a network failure. The caller hits a timeout, and it submits another payment. If not handled properly, you can end up with two payments.

To handle this, we need to implement the payment operation in an idempotent manner. An idempotent operation is designed in a way that a duplicate request doesn’t repeat its effect if the earlier request succeeded. One way you could do that is to give every operation an ID value and record enough information to find out if an incoming request is a duplicate.

As we talked about earlier, keeping replicas of data can help us if the primary instance fails for some reason. We can use failover to route requests to the copy and keep things running. But this can also be the source of a correctness problem.

Let’s say the primary database didn’t fail, but just became unreachable due to a network problem. If you promote the replica to primary without stopping the old primary from accepting writes, it can create a split-brain situation. Two database instances act as the authoritative write database. A good failover process has to make sure that the old primary doesn’t compete with the new primary.

How to Measure Recovery From Failures

As you may have noticed by now, failures are an inevitable part of building software. Any system we build must have a way of recovering from these failures. But you need a way to measure this recovery to make important decisions. RTO and RPO are two data points that can help with this.

The RTO (Recovery Time Objective) is the max target time within which we want to restore the service after there is a failure. For example, if RTO is 30 minutes, we aim to get the service up and running within 30 minutes.

The RPO (Recovery Point Objective) is the acceptable data-loss window. But it is expressed in time. For example, if the RPO is 5 minutes, our aim is to not lose more than the most recent 5 minutes of data changes.

RTO and RPO are objectives. Not guarantees. You need to design the system and the recovery procedure in such a way that these objectives are met.

Summary

In this article, we’ve looked at the strategies that can help developers design for failures. The key learning points are as follows:

  • An application depends on more than its own code. You need processing capacity, storage, network connections, and many other services. All of these are dependencies, and each comes with its own set of conditions that can impact the application.

  • A fault is a defect or abnormal condition that can make something go wrong in an application.

  • There are two ways to deal with faults: avoiding faults and tolerating faults.

  • To deal with a specific failure mode, we need to have a good idea about the scope of that failure. This scope is known as a failure domain. Think of it as a group of components that can be affected by the same failure.

  • One of the best ways to fulfill the “design for failure” philosophy is to follow the principle of isolation.

  • With the right isolation approach, we can create boundaries within a system that failures cannot easily cross.

  • After we’ve limited the spread of a failure using isolation, the next question is how the system can recover from a failure. We can use strategies like redundancy, replication, and backups.

  • RTO and RPO are two data points that can help measure the effectiveness of the recovery process.
